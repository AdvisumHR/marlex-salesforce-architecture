MuleSoft — the integration layer, as a Decision Record

The MuleSoft build. Every edge where the recruitment system meets an outside world is mapped here — the ERP, the job board, e-signature, credit checks, the customer data platform, the sourcing tools — but the work MuleSoft actually takes on is narrower: the integrations we route through it, starting with the ones coupled to the retiring TargetRecruit data. Each is a decision, one per page: what was weighed, what was chosen, and what is still open.

Decision record · draft for peer review · 11 August 2026 · Nuvolar

What this is. The complete reasoning behind how Marlex's integrations are rebuilt and routed as TargetRecruit is replaced with a native Salesforce system — grounded in a read-only audit of the live production org, not estimates. It is a proposed approach for peer and governance review, not a settled plan.

The objectives. Four, in priority order. They are what the plan and its sequence are built to serve, so it is worth stating them before anything else:

  1. Own the switch point

    Put every integration behind an interface Marlex controls, so that where it points — at the retiring TargetRecruit objects or at the new native model, at one Salesforce environment or another — is a change made in configuration, not a Salesforce release. This is what makes the rebuild's cutover controllable, and it is the reason the sequence looks the way it does.

  2. Prioritise the integrations coupled to the retiring data

    Those are the only edges whose target has to change when the recruitment model is replaced. Routing them through the integration layer first is what puts that change under Marlex's control in time for the switch — which is why the ERP and the job board lead the order.

  3. Replace one-to-one wiring with reusable interfaces

    Move integration logic out of Salesforce into one shared, Marlex-owned layer so Salesforce goes back to running CRM, back-office and recruitment and stops being the group's integration hub. Each connection built is a named interface that Marlex Spain, Axxon and the rollout countries all call, so the second job board — or a new country's ERP — is a small addition, not a fresh build. A platform investment, not a project cost.

  4. Keep the go-live's timing in Marlex's hands

    Every edge is built so it has a working direct connection to fall back on, so a delay in the integration layer degrades the plan rather than stopping the switch.

How it's approached. Every rebuilt integration ships behind a Marlex-owned interface, and the switch behind that interface is what the programme owns. For the edges tied to the retiring TargetRecruit data — the ERP (NET4) first, then the job board (InfoJobs) — that switch lives in the integration layer: the interface each system calls keeps its address and its contract, and the target moves from the old model to the new underneath it. Those two lanes are therefore built before their cutovers, and each keeps a direct connection as its tested fallback. Everything else is adopted one edge at a time, by configuration, on its own schedule. Not everything routes through the layer — connections that only need a secure, direct link stay on Salesforce, and it is not a mandatory gateway. The platform choice and its commercial terms are settled; the architecture around it is proposed for review.

How to read an edge

Two jobs, and the two questions that decide the routing

Before the lanes, one distinction clears up what these edges actually are. Every integration is doing one of two jobs — and some do both:

  • Keeping data in step. A record kept in two systems stays consistent — a candidate, an account, an offer, an invoice lives on both sides and a change on one is copied across. The test is whether there is a second copy to reconcile. The ERP's bulk traffic, the job board's application intake, the customer-data-platform feed are all this.
  • Calling a service mid-process. The edge reaches an outside capability as a step inside a live process — publish a vacancy, send a contract to sign, look up a client's solvency, parse a CV — then uses the answer and moves on, keeping no second copy. Publishing to the job board, e-signature, the credit check and the matching engine are all this.

The same connection can do both: the ERP mostly keeps data in step but also serves a live screen lookup; the job board keeps applications in step while publishing vacancies is a service call. This is what the routing rule turns on — high-volume data-in-step traffic reused across countries is what earns a place on the shared platform; a single-consumer service call rarely does. Two further questions decide the cutover, not the platform: who owns the seam (a Marlex interface we can re-point, or a bought tool's fixed connector we cannot) and whether the edge touches the retiring records. Every edge, tagged on all of these, is on the measured surface.

The premise it rests on

What is fixed, and what can move

Most of this order can flex, and one part of it cannot. The flexibility comes from the swappable-adapter pattern: every edge ships behind a Marlex-owned interface with a direct connection available, so routing it through the platform later is an additive change — a second implementation behind the same interface, chosen by a configuration record, no redeployment. That is what keeps the platform's own build-out off the critical path for the great majority of the surface.

The fixed part is the two lanes coupled to the retiring data. Their switch from the old model to the new one lives in the layer rather than in Salesforce, which is the point of building them — so they have to be standing before their cutovers. That is affordable because the commercial terms are agreed and the environment is available from September 2026, and it is survivable because each keeps a direct connection to fall back on. The order below is therefore driven by coupling to the retiring data first, then reuse and dependency — not by a deadline.

Decision 1 · Why an integration platform

Integration logic lives outside Salesforce, behind Marlex-owned contracts

Should the connective tissue between Salesforce and the outside world sit inside Salesforce as custom code, be wired system-to-system with no layer in between, or run on an external integration platform behind interfaces Marlex owns?

Grounded in the July 2026 production-org integration audit · 11 August 2026 · architecture proposed for review

The decision. The rebuild — replacing TargetRecruit with Marlex's own Salesforce build — has to decide where the work of integration lives. Three shapes were on the table: all of it inside Salesforce as Apex, with no external layer; point-to-point, each system wired straight to each other system with no layer coordinating them; or an API-led, three-layer architecture in which Salesforce only exposes and consumes clean interfaces, and the transformation and orchestration between systems runs on an external integration platform (middleware).

What we propose. The API-led three-layer architecture, with integration, transformation and orchestration logic in an external middleware behind Marlex-owned canonical contracts. Salesforce exposes and consumes application programming interfaces (APIs — the defined request points a system offers) and holds no cross-system plumbing. This is the premise the whole integration set rests on, and it is proposed — the architecture records that fix it are drafted for review, not yet ratified. The concrete platform that plays the middleware role is a separate decision; the swappable-adapter pattern is what lets us hold this stance without the platform's timeline blocking the cutover.

What "three layers" means

Three layers, each with one job, is the shape being proposed

"API-led" is a way of arranging integrations into three layers, each doing one thing. It is worth stating plainly, because the whole set assumes it. A system layer speaks each end system's own language — the enterprise resource planning system (NET4, the ERP that holds finance and placements), the job board, the e-signature service — and exposes each as a clean interface, hiding that system's quirks. A process layer orchestrates: it combines those system interfaces into a business flow and transforms data between shapes. An experience layer tailors an interface to a specific consumer — a portal, a partner. Salesforce sits at the edge of this picture: it calls in through these interfaces and exposes its own, and it never holds the plumbing that stitches systems together.

The point of the arrangement is not the diagram. It is that the wire between any two systems stops being a private, hand-built connection and becomes a reusable, named interface anyone can call — so the second consumer of the ERP, or the second job board, is a small addition rather than a fresh build.

Why the premise matters now

The rebuild is exactly the moment to fix this

The org being retired is a lesson in the cost of the wrong shape. The TargetRecruit managed package's deepest expense was never the wire — it was business logic that knew vendor specifics, so every swap became open-heart surgery on code. The one genuinely modern corner of the current org shows the alternative already working: the ERP client is a cleanly separated family where the business logic calls a Marlex-owned interface and has no idea what sits behind it. The rebuild is the moment to apply that shape to every edge, because the edges are being rebuilt anyway — building them behind clean contracts costs little more than building them hard-wired, and building them hard-wired re-plants exactly the coupling the rebuild exists to pay down.

Ownership is the load-bearing word

"Behind Marlex-owned canonical contracts" is the part that survives every vendor and platform change. A canonical contract is a Marlex-defined shape for a business concept — what a candidate, a job or an invoice looks like at the boundary — that outside systems and Salesforce both speak to, instead of speaking to each other's raw formats. Own the contract and the transport becomes a detail: direct today, on a platform tomorrow, swapped without touching business logic. Skip the contract and the transport is the coupling, and every change reopens it.

And it is where the switch lives

There is a second reason the layer earns its place, and for this programme it is the sharper one. When an interface stands between the outside system and the data, the interface is where the target is set — so moving an integration from the retiring TargetRecruit objects to the new native model, or pointing it at a different Salesforce environment, becomes a configuration change in the layer instead of a Salesforce release. Without that layer, every such move is a code deployment, made under exactly the time pressure a cutover creates. This is why the edges coupled to the retiring data are the ones routed through the layer first: they are the edges whose target actually has to change.

Point-to-point, each system wired to each other, no orchestration layerRejected

Wire each system straight to each other system. Cheapest per connection on the day it is built — and it grows into the tangle every integration programme regrets: many private, one-off connections, no single place to change a transform, no shared contract, and a re-point at cutover that has to be repeated connection by connection with no seam to switch behind. This is the shape the current org's package coupling already is; rebuilding into it would spend the rebuild's budget to arrive back where it started.

API-led three layers, middleware behind Marlex-owned contractsProposed

Salesforce exposes and consumes clean interfaces; integration, transformation and orchestration live in an external middleware behind canonical contracts Marlex owns. Each edge gets a named, reusable interface instead of a private wire; the recruitment org stops being the group's integration hub; and a second consumer — another org, another job board — is an addition, not a rebuild. The cost is real and named: a platform to license and operate, and the discipline of actually keeping the contracts clean. This is the proposed premise; it is deliberately paired with the swappable-adapter pattern so that the platform's readiness never gates a go-live.

Point-to-point and all-in-Apex are the same failure at different scales — no owned contract, so the transport is the coupling. The API-led shape is the only one of the three that puts a Marlex-owned seam between business logic and every outside system.

Decision 3 · The swappable adapter

The port is what we own; the transport is a setting

How the rebuild ships every edge to the outside world, decides which side of the seam holds each edge's switch — and gets its rollback for free in the bargain.

Grounded in the July 2026 production-org audit · pattern proposed for peer review · 11 August 2026

The decision. The rebuild has to touch every integration edge, and each one needs an answer to two questions: what does it connect through, and where does its switch live — the point at which it can be re-aimed from the retiring TargetRecruit objects at the new native model, or from one Salesforce environment at another. Get the second answer wrong and the cutover's most delicate moves become code changes under time pressure.

What we chose proposed. Every rebuilt edge ships behind a Marlex-owned interface — a "port" — with a direct adapter and, where the layer carries it, a middleware adapter behind the same port, a runtime selector — a configuration record — choosing which one runs. Switching an edge from direct to middleware, or back, is a configuration change, not a redeployment.

And the seam has two sides. The switch can sit in the Salesforce-side adapter or in the system interface the integration layer publishes, and the choice is made per edge. For the edges coupled to the retiring data — the ERP and the job board — it sits in the layer: the outside system keeps calling one address with one contract while the target moves underneath, changed by configuration in the layer rather than by a Salesforce release. For every other edge the Salesforce-side adapter holds it, because there is nothing to gain from the hop. Either way the direct connection stays as the fallback — which is what makes this pattern the rebuild's rollback mechanism as well as its switching one.

The principle

What makes an integration expensive to change is never the wire

The cost of changing an integration is almost never the network call itself. It is business logic knowing vendor specifics — a recruiter workflow that names an endpoint, hard-codes an authentication scheme, or assumes a particular payload shape. The retiring package's deepest cost was exactly that coupling, spread across hundreds of classes. The org's one genuinely modern corner proves the alternative already works: the ERP client (MA_Net4Client) is a cleanly separated family — the business logic calls a Marlex-owned interface and has no idea what sits behind it. The rebuild applies that shape to every edge.

A port is that interface: a small, stable, Marlex-authored contract that says what an edge does (publish this offer, fetch this document, parse this CV) and never how or where. An adapter is one concrete way of honouring the port — a direct call to the vendor today, a call routed through MuleSoft tomorrow. Once the port exists, "direct or via the platform?" stops being an architecture decision and becomes a configuration choice, reversible either way. That is the whole move.

For the developersThe port is an Apex interface (or a small set of them, one per edge capability), authored under the MA_ namespace and depended on by the domain/service layer. Each adapter is a class implementing that interface — a direct adapter that makes the callout itself (Named Credential, Remote Site) and, later, a middleware adapter that calls the MuleSoft system API for the same capability. The selector is a Custom Metadata record read at runtime (a factory returns the adapter the record names), so which adapter runs is a deployable-and-editable configuration value, not a code path chosen at compile time. The existing MA_Net4Client family is the reference shape to copy; nothing about the pattern requires the platform to exist before the direct adapter ships.

The corollary that pays for the cutover

A lane built before cutover survives by "re-point, not rebuild"

The pattern earns its keep twice. The first payoff is transport independence, above. The second is that an edge already behind a port does not have to be rebuilt at cutover — it only has to be re-pointed. Because the business logic addresses the port and the port addresses the data through an adapter, moving from the retiring TargetRecruit schema (AVTRRT__) to the native model (MA_*) is a change inside the adapter, not a rebuild of the edge. The ERP link is the living example: it is preserved through cutover untouched above the port, and only its reads of the old model re-point beneath it.

Re-point, not rebuild

Building the seam before cutover converts a rebuild into a re-point. The System API that a lane exposes keeps its address and its contract; underneath, the adapter is re-aimed from the AVTRRT__ schema at the MA_* model. The outside system sees no change, the business logic sees no change, and the cutover cost of that edge collapses from "rewrite it" to "change one adapter's target". This is the port discipline paying back the coupling the rebuild exists to pay down.

Which side of the seam holds the switch

Two places the target can change — and how we pick

"Re-point" is one word for two different operations, and the difference matters enough to decide per edge. The target can be changed in the Salesforce-side adapter — Marlex's own Apex, deployed on a Salesforce release — or in the system interface the integration layer publishes, where it is a configuration change in the layer and the outside system never sees a thing. Both are re-points. They differ in who has to act, how fast it can be reversed, and whether an outside party is involved at all.

Alternatives considered

Three ways to sequence the edges — two of them rebuild twice

The rebuild has to reach a working integration surface eventually, and the platform will eventually carry the edges that earn the hop. The real question is the order of operations. Three sequences are possible; two of them make the same mistake in different places.

Clean up every edge on the old platform — put ports around them while they still talk to the AVTRRT__ model — and only then rebuild the model underneath. It sounds orderly, but it pays for the seam twice: once against the schema that is about to be deleted, and again after the rebuild changes what the adapters point at. Work invested in wrapping the dying model is thrown away when the model dies. A double rebuild.

B · Direct callouts now with no seam, then refactor to middleware after the rebuildRejected

Rebuild each edge as a hard-wired direct connection with no port, ship it, and come back later to lift every edge onto the platform. Cheapest per edge on the day it is written — and it re-plants the exact coupling the package removal is paying down. When the platform is ready, each edge is opened up again and its business logic surgically separated from its transport, one class at a time. The seam gets built either way; doing it after the fact means building the edge, then rebuilding it. A double rebuild, moved to the other end.

Where the platform earns its hop for a class of edge, add a middleware adapter behind the same port and flip the selector. The edge is built once; the transport changes by configuration, never by rebuild. The direct adapter stays as a permanent fallback, which is where the rollback comes from. For the two lanes coupled to the retiring data the middleware adapter is built ahead of the cutover rather than after it, because that is where their switch lives.

Why A and B are the same mistake

Both A and B build an edge, then rebuild it — A because it wraps a schema that is about to be deleted, B because it hard-wires a transport that is about to be replaced. C builds the edge exactly once and lets configuration absorb both changes: the schema move becomes an adapter re-point, and the transport move becomes a selector flip. The seam is the thing that makes both future changes cheap, so the seam is what you build first.

The honest cost

What the seam actually costs to build

The chosen pattern is not free, and pretending it is would undermine the case for it. There are three real costs, and they are worth naming plainly:

  • The ports themselves: roughly 3–5 developer-days. Defining the interfaces, the selector, and the factory that reads it — a one-time foundation shared across every edge.
  • The fallback direct adapters: roughly 10–15 developer-days. Each edge needs its day-one direct implementation. This is not overhead the other options avoid — B builds these too, and A builds an equivalent — but it is real work that ships before any middleware exists.
  • Dual-adapter maintenance during coexistence. For any edge that has both a direct and a middleware adapter live at once, both must be kept working until one is retired. This is a genuine carrying cost for the period an edge runs on the platform while its direct adapter is held as the fallback — deliberate, and bounded by when the fallback is stood down.

Set against those costs is the thing the pattern buys: the cutover sheds its dependency on an open platform decision, every pre-built lane becomes a re-point rather than a rebuild, and the rollback is a configuration flip. The seam is cheap relative to a coupled go-live, and it is permanent — it does not get thrown away when the old system does.

  • Work invested in the old model (A) or the hard-wired transport (B) is redone after the change it ignored lands. almost certain
  • Hard-wired edges (B) re-plant the coupling the package removal exists to pay down. probably
  • The second pass is deferred under delivery pressure and simply never happens, leaving the edge coupled for good. more likely than not

Upside, and how big Cheapest on the single day each edge is first written — a real but small and short-lived saving.

Worst case Every edge paid for twice, and the coupling the whole programme exists to remove quietly re-established.

Build the edge once; let configuration absorb the change. A and B both look cheaper up front and both end in a second rebuild — A of the schema wrapping, B of the transport wiring. C spends a little more now to build the one thing that makes every later change a configuration flip: the port. The preference this serves is a cutover whose switches Marlex controls, each with a real way back — and only the chosen sequence delivers both without paying for the edge twice.

Rollback for this choice

This pattern is the rollback mechanism

Most decisions in the record need a rollback plan bolted on. This one supplies its own. Because every edge sits behind a port with a runtime selector, a transport switch — direct to middleware, or middleware back to direct — is a two-way door: a configuration change, rehearsable and reversible in minutes, taken per edge, with no redeployment. A middleware adapter that misbehaves in production falls back to its direct adapter by flipping one configuration record. The direct adapter is kept for exactly this reason; it is not scaffolding to demolish once the platform is in.

The exception: commercial data connectors

This two-way door does not exist for the commercial data connectors — the bought sourcing and screening tools that ship a fixed Salesforce connector, log in through Salesforce's own authentication and read through its standard interface. There is no Marlex-owned port to swap behind them, so there is no adapter to re-point and no selector to flip. Their only lever is the Salesforce side — which data each is allowed to reach — and their rollback is the external owner re-pointing their own connector, on a signal and in a window that must be agreed before the fallback opens. The full handling of that class is on the commercial data connectors page.

Residual risk & open items

What we still carry

  • The concrete port interfaces are not yet defined. The pattern is settled in principle; the actual interface for each edge capability — its methods, its data contract, its error shape — still has to be written, edge by edge, before the direct adapters can be built against it.
  • The runtime selector is not yet implemented. The Custom Metadata type, the factory that reads it, and the wiring that lets a flip take effect without a deployment are proposed, not built. Until the selector exists, the "switch is config, not redeploy" promise is a design, not a fact.
  • The discipline is cultural, not structural. Nothing in the platform physically prevents a hurried edge from bypassing its port and calling a vendor directly. One hard-wired "temporary" shortcut kept under pressure and the two-way door starts rusting shut. This is held by a standing code-review rule and an edge register, not by a runtime guard — which means it depends on people, every time.
  • Two lanes now depend on the platform being ready in time. Putting the switch in the layer for the ERP and job-board lanes means those two have to be standing before their cutovers — the one place the platform sits on the critical path. The commercial terms are agreed and the environment is available from September 2026, so this is a scheduling risk rather than an open decision; if it slips, those edges switch in their Salesforce-side adapter instead and give up the control the design was chosen for.
  • Commercial data connectors have no port and no config-flip rollback. Who re-points each one, in what window, on what signal must be agreed with each external owner before any fallback window opens — tracked on the connectors page, not solved here.

Why login counts mislead

The tempting shortcut is to rank integrations by how often they sign in. It is wrong, and two live examples show it clearly. What the edge actually is

Three flows, one of which writes

"The InfoJobs integration" is really three separate flows, and only one of them touches the write path that gates the cutover. Keeping them apart is what lets the harmless parts move early and forces only the webhook to wait for the core.

Offer publication Out

When a recruiter publishes a vacancy, Salesforce calls out to InfoJobs to post it. This flow only reads a handful of job fields to build the posting and sends them over the wire — it writes nothing back into the recruitment model. Because it is outbound and read-only on our side, it can move behind the new lane ahead of the core cutover without waiting for it.

CV retrieval Out

When a candidate applies, the system fetches their CV back out from InfoJobs over a plain web request. This flow is also outbound — but it carries a hidden dependency: the CV it pulls is still parsed by the old package's parser, not the native one already live elsewhere (worked below). So this flow can move behind the lane early, but the parser it feeds cannot retire until the job-board cutover.

Application webhook In — writes

Every application a candidate submits arrives in through a public web service and creates records in the old model — the job, the application and the candidate objects. This is the write-coupled flow. It runs through a guest-user public site, is verified by a signed digest, and is the only one of the three that has to re-point in step with the core go-live.

Why the webhook gates the cutover

A write edge cannot lead or lag the model it writes into

The core go-live moves the candidate, job and application backbone from the old objects to the new ones in a single rehearsed window. The application webhook writes exactly those objects. So there are only two ways the webhook and the core can be timed, and only one is safe:

  • In lockstep with the core — chosen. The moment the core's applications live on the new model, the webhook writes the new model too. No application is orphaned; nothing lands in a retired object. This is the only timing that keeps the ~27,000-a-week inbound flow intact across the switch.
  • Out of step — impossible to make safe. If the webhook re-points before the core, it writes new objects that the live desk cannot yet see. If it re-points after, every application submitted in the gap lands in a dead model and is lost. Either way the busiest inbound flow in the system silently breaks during the one week the desk can least afford it.
This is what "gates" means, precisely

The webhook does not delay the cutover — it is bound to it. The core cannot go live until the webhook is ready to re-point in the same window, and the webhook re-point is only valid once the core has moved. They are one atomic event on the runbook, rehearsed as one. Every other Salesforce-owned edge is either already on the new model or read-only and forgiving; this is the single edge whose timing is welded to the core's.

The middleware lane

The second lane — heavier than the ERP, and it must land before the portals

Under the port rule set on the swappable adapter page, the job board ships behind a Marlex-owned interface with a direct connection first, and moves behind MuleSoft on its own schedule. In the build order it is the second lane — after the ERP lane, before the portals proposed. Two reasons place it there:

It is the heavier build

The lane needs protocol mediation the ERP lane does not: InfoJobs publishes over an older SOAP-style contract, and the middleware has to translate that to the modern REST-style interface the rest of the layer uses. It is the larger of the first two lanes — heavier than the ERP lane — so it is built second, once the shared foundation the ERP lane establishes is in place.

It must precede the portals

The candidate, recruiting and staffing portals expose the same application pipe to the outside world. The portals cannot be built until the job-board pipe they sit on top of exists and is proven, so the job board lane lands before them. The portals also depend on a partner-built front end that does not exist yet, which pushes them later regardless (see the portals).

The lane is also the re-point

Building the lane and re-pointing the webhook are not two jobs. The same work that stands the job board up behind MuleSoft is the work that aims its write path at the new model. So the lane's completion and the cutover gate are the same milestone — which is why the estimate carries the cutover's weight, not just a lane's.

The platform is settled; its footprint here is proposed

MuleSoft was selected as the integration platform on 3 July 2026 decided, its commercial terms have since been agreed, and the working environment is available from September 2026. The lane ordering, the lane's sizing and the SOAP-to-REST mediation plan are proposed for review proposed — part of a delivery proposal covering the first two lanes plus shared foundation.

Where this lane's switch lives. Because the webhook writes the retiring records, the plan is for the system interface the layer publishes to hold the switch: the job board keeps posting to one unchanged address across the cutover while the target moves from the old objects to the new underneath it. That is the whole reason this lane is built before its cutover rather than after. The Salesforce-side service remains as the tested fallback — if the lane is not ready, the webhook re-points in Marlex's own Apex instead, and the cutover still happens on a mechanism that costs a release rather than a configuration change.

The big open question

The InfoJobs–Orbio boundary decides how much this lane carries

The largest uncertainty on this lane is not technical mediation — it is a scope question about a second product. Orbio is an AI candidate pre-screening service (a Madrid HRTech firm) being wired up to sit between InfoJobs and Salesforce: it takes the vacancy and the incoming candidates, scores and evaluates them, and writes the result back onto the recruitment objects. Runs alongside Baseline assumption

A dependency hiding in the CV flow

The timing of that closure is therefore bound to this lane, not to the parser's own page.

So this is not a cutover risk in the usual sense; it is a capability-restoration effort that runs on its own track, starting whenever the partner application starts and finishing whenever LinkedIn certifies. Axxon reuses the shared NET4 lane rather than building its own

A second company on the same ERP: does it plug into the lane Spain already built, or get a point-to-point connection of its own?

Grounded in the July 2026 production-org audit · lane reuse proposed for review · 11 August 2026

The decision. Axxon is a separate company — its own Salesforce org, its own Spanish operations — acquired by Marlex. Why this is a reuse case, not a new build

NET4 is the group ERP, not a Spain-only tool. Both companies push the same kind of traffic to it — placements and invoices out, finance data back — against the same finance platform. When two callers want the same destination for the same purpose, the cheap and durable answer is one service that knows how to talk to that destination, with a routing layer in front that tags each message with the company it belongs to. That routing — tenant routing at the integration layer — is what lets a single lane serve both orgs without either knowing the other exists.

Reusing the lane is also what proves the whole port-and-middleware thesis was worth the effort. The NET4 lane earns its cost twice precisely because a second company plugs into it without a second build. If Axxon needed its own connection anyway, the argument for building NET4 first as a shared service would be much weaker. Axxon's own systems today

Where Axxon is moving from, and why NET4 is the shared anchor

Axxon runs a different toolset today. Its applicant-tracking system is Eolia, an external French recruitment system; its finance and back office run on e-Oer, which is moving onto NET4. So the ERP is the point where the two companies converge first: harmonising on NET4 is the near-term shared anchor, while the recruitment side of Axxon is a separate, later conversation. That is why the ERP lane is the sensible first place the two companies share plumbing — the finance destination is common ground before anything else is.

The load-bearing assumption

If it holds, the second company is a routing and configuration exercise on the Marlex side. If it does not — if NET4 needs per-company endpoints, or any server-side change to tell the two tenants apart — then reuse turns into a dependency on the NET4 team's own change schedule, outside Marlex's control. That dependency is the one thing that could threaten the January-2027 target for the shared ERP integration. That target is an ideal, not a hard deadline; but it is the reason this assumption has to be confirmed with the NET4 team early rather than discovered late.

The near-term bridge, before any reuse

The ERP moves on its date; the automated link waits for the rebuild

On its fiscal cutover, Axxon switches its finance and back-office operation onto NET4 — its consultants do the labour-management work directly in NET4, and Axxon keeps its existing recruitment system in place for the time being. Decision 9 · Edges proposed to stay direct

Two edges are proposed to stay directly connected, for good

The rule routes rebuilt edges behind the platform on a schedule. Which edges should never take that hop at all — and are those calls settled?

Grounded in live production usage logs · 11 August 2026 · both calls open

The decision. The governing rule for rebuilt integrations is that every Marlex-built edge gets a direct connection first and moves behind the middleware layer — MuleSoft — later, per edge, on a schedule that never blocks the cutover. This page covers the edges that are the exception to the second half of that rule — proposed to stay direct rather than route through the platform: the CV parser (the native document-reading service) and the finance write feed that lands calculated figures on native objects. It also covers the connection that carries them, the "Data Source" identity, because that same identity runs a second job — the Power BI extract — which is not stay-direct: it reads the retiring model and must be re-pointed at the cutover.

What we chose. Propose the CV parser and the finance write as stay-direct; treat the Power BI extract as a cutover re-point — and be honest that none of it is closed proposed. The CV parser is latency-sensitive synchronous work with no canonical contract to own, so a middleware hop would add delay and cost for no orchestration gain. The finance write touches only native objects, so it has no rebuild work of its own. The Power BI extract, by contrast, reads retiring objects out to an analytics database, so it has to move to the native model when they retire — by one of two routes, both still open. Ownership of the "Data Source" jobs is still to be confirmed, and the CV parser's stay-direct verdict does not by itself close the old package's parser, which the job board still uses.

Where these two sit in the rule

Stay-direct is a named exception, not a gap

The swappable-adapter pattern lets any Marlex-built edge flip between a direct connection and a middleware-behind one by changing a single configuration record, with no redeployment. That is what lets most edges start direct and move behind MuleSoft on their own schedule. "Stay direct" means we propose to leave that selector pointed at the direct connection for these two edges indefinitely — not because we can't move them, but because moving them buys nothing. It is a deliberate choice per edge, recorded here so it is a decision and not an oversight.

This is different from the commercial data connectors covered on the connectors page. Those are exempt because there is physically nothing for the platform to front — a bought tool ships a fixed Salesforce connector with no address to re-aim. The two edges here are Marlex-built and could be routed through the platform; we are proposing not to.

Edge 1 — the CV parser

The native document reader is live, and proposed to stay direct

The CV parser is the native replacement for the document-reading engine the retiring TargetRecruit package used to provide (optical character recognition — OCR — and structured extraction from a CV). It is already live in production, and it has been extended well past CVs: it now also reads identity documents and bank details, filling native fields directly (for example the account number field, verified present in production). It is a Marlex-owned service calling out to two AI inference providers over managed credentials.

It is proposed to stay direct proposed for one reason: it is synchronous artificial-intelligence inference inside a user's flow. A recruiter uploads a document and waits for the fields to come back on screen. That makes it acutely latency-sensitive, and there is no canonical contract for the platform to own — the call goes straight to a model and returns extracted text, with nothing to orchestrate, transform or fan out. A middleware hop would add a network round trip and a running cost to every call, in exchange for no orchestration benefit. Fronting it would make a fast, simple edge slower and more expensive for no gain.

The native parser being live does not mean the old parser is gone

An important nuance: the CV path from the job board (InfoJobs) still routes to the old package's parser today, on the job board's own instruction. So this native parser being live is not one fewer package dependency yet. The old reader stays in use on that one path until the job-board feed is re-pointed to the new model — closing that dependency is part of the job-board cutover, not a switch already thrown here. Two parsers run side by side until then, by design.

Edge 2 — the "Data Source" identity (two jobs)

One identity runs two jobs — and one of them reads the retiring model

The connection carrying the generic name "Data Source" turns out to be one identity fronting two different jobs, only one of which is a stay-direct candidate:

  • A finance write feed that pushes calculated figures (incentives and monthly margin per client) into native custom objects — far more writes than reads. This touches only new native objects, so it is not coupled to the retiring model and can stay direct.
  • A Power BI extract that reads Salesforce out to an external analytics database on a schedule. This is the pipeline that actually feeds the Power BI dashboards, and it reads objects from the retiring TargetRecruit model among the roughly forty it pulls — so, unlike the finance write, it is coupled to the cutover and must be re-pointed.

Because both run under the same identity, the earlier reading of this connection as a single "finance feed, no retiring-model coupling" was incomplete: the write half is uncoupled, but the extract half reads the old model and cannot simply carry across the cutover untouched. The two must be treated separately.

The extract is a re-point, not a stay-direct edge

The Power BI extract reads the retiring recruitment objects directly. When those objects are retired, the extract stops returning that data unless it is re-pointed to the native model. It does not gate the go-live the way the job board does — Power BI dashboards can lag briefly without breaking the live desk — but it is a known re-point, and it belongs on the cutover checklist rather than in the "survives untouched" column.

Two ways to carry the extract across the cutover were weighed, and the choice is open:

Route the extract through MuleSoft

The extract becomes a middleware-mediated feed, so the mapping from Salesforce objects to the analytics database lives in the platform alongside the other lanes.

  • One place to own the object-to-table mapping, consistent with how every other rebuilt edge is treated.
  • But the extract is a bulk read into a database Marlex already owns end to end — there is no third party and no shared contract to mediate, so the middleware buys little here beyond consistency.

New extract script at cutover, keep the analytics tables

Replace the current extract with a new one that reads the native model, introduce mapping tables from old objects to their native successors, and keep the target analytics tables the dashboards already read from.

  • The Power BI layer is untouched: the same database tables feed the same dashboards, so nothing downstream of the extract has to change.
  • The work is contained to the extraction step — re-map which Salesforce objects and fields fill each table — and it is entirely Marlex-owned on both ends.

Rollback for this choice

How this decision fails back

Rollback here is trivial, because there is nothing to fail back. These edges already run on the native or standard model, so the cutover does not change what they touch. There is no re-point to reverse, no old endpoint that has to stay answerable for their sake, and no external owner who has to act. The only pre-flight obligation is the sweep that confirms each preserved edge still resolves to a live object once the vendor package is removed — and for these that check is a formality, since none of them depends on a vendor object in the first place.

Decision 11 · Commercial data connectors

These connectors are exempt from the platform — for a product reason, not a preference

Three bought SaaS tools read the recruitment data through a fixed Salesforce connector. Can MuleSoft, the chosen integration platform, front them, and if not, who rolls them back?

Grounded in the live production-org measured surface · 11 August 2026

The decision. Three bought tools — Taleva (candidate sourcing), Orbio (an artificial-intelligence candidate pre-screening service) and Rainmakers (a business-to-business lead marketplace) — sit together as a class because a bought SaaS tool typically connects with a fixed vendor connector: it logs in through Salesforce's own sign-in and reads through its standard interface, with no setting to aim the connector at a Marlex-owned address instead. The question is whether the "route it behind the integration platform later" option — the rule that governs every Marlex-built edge — applies to tools like these.

What we chose. Where a tool connects through a fixed vendor connector, the rule does not apply and cannot be made to. There is no Marlex-owned port to place in front of a packaged connector, and MuleSoft cannot impersonate Salesforce to it, so a fixed-connector tool is exempt from the platform hop. Its only lever is on the Salesforce side — which data it is permitted to reach — and its rollback is the one integration risk on the whole programme that Marlex does not control: the external owner, not Marlex, must re-point the connector back to the old objects if the cutover is reversed. Rainmakers is a fixed-connector tool of exactly this kind, and Taleva is provisionally treated as one pending confirmation.

Orbio is not in this class. As of the 2026-07-21 technical weekly this is resolved: Orbio connects through API calls, not a fixed vendor connector — so it is routable behind a Marlex-owned interface, and because it reads and writes the retiring recruitment objects it should be sequenced behind a MuleSoft System API before the cutover, like the other edges coupled to those objects. This reverses the earlier written position (a 2026-07-14 reconciliation had provisionally called it a commercial connector, exempt). Two facts hold either way: Orbio is sandbox-only, not live, and it writes the retiring objects by design — so once it goes live (date still open, expected before cutover) it is a third write-coupled edge to plan for. Taleva is now the only tool whose connection type is still uncertain.

Why the platform rule stops here

You cannot put a Marlex port in front of a packaged connector

Every Marlex-built integration has a Marlex-owned interface — a "port" — in front of it. That is what lets a rebuilt edge move behind MuleSoft later, on its own schedule, without the outside system ever noticing: the swap from old objects to new happens inside a layer Marlex owns. That whole mechanism depends on there being something Marlex controls between the outside system and the data.

A bought SaaS connector removes exactly that thing. Rainmakers is a commercial product that ships its own Salesforce connector, and Taleva is provisionally treated as one pending confirmation (see the open question at the foot of this page). Orbio is not in this class — it connects by API and is routed behind a Marlex-owned interface (see the note below). A fixed-connector tool signs in through Salesforce's native authentication and reads and writes through Salesforce's own standard interface — the same interface any logged-in tool uses. Inside such a product there is no field to type a middleware address into; the connection target is Salesforce, and that is fixed by the vendor. So two things follow, and both are product facts rather than choices:

  • There is no port to route them behind. The connection terminates at Salesforce directly. Marlex owns no seam in that path to re-point, because the vendor's connector never touches a Marlex-built endpoint.
  • MuleSoft cannot stand in for Salesforce. Even if Marlex wanted to insert MuleSoft in the middle, it cannot impersonate Salesforce's authentication and standard interface to a packaged connector that expects to talk to Salesforce itself. There is no way to fool a product into calling middleware when its connector is built to call Salesforce.
So the one lever that remains is the Salesforce side

Because the connection cannot be intercepted or moved, the only control Marlex holds over these connectors is which data each one is allowed to reach — the object and field permissions granted to the account the connector signs in as. That is the whole toolkit: not routing, not mediation, just scope. It is why least-privilege scoping (a connector reaching only the objects it needs) matters more here than anywhere else on the integration surface.

This rollback is not Marlex's to flip

Commercial connectors are the exception, and it is the one that matters most.

The one integration risk that is not ours to flip

If the cutover is reversed, a fixed-connector tool must be pointed back at the old objects — and Marlex cannot do it. The connection and the field mapping both live inside the vendor's product, and the platform cannot front them, so the external owner has to re-point their own connector. By the time the cutover comes, Taleva is expected to be reading — and possibly writing — the old objects; if it is confirmed to be a fixed connector, its owner would need to reverse the mapping on their side, on Marlex's signal, inside the fallback window. Where a tool is a fixed connector, three things are a hard prerequisite before the fallback window opens, agreed with the owner in advance:

  • Who re-points — the named party on the connector owner's side responsible for the reversal.
  • In what window — how quickly they can act once Marlex calls the rollback, measured against how long the old objects stay answerable.
  • On what signal — the exact trigger and channel by which Marlex tells them to reverse.

The mitigation that makes any of this executable is a living substitution inventory: for every old object and field left behind, the native object and field that replaces it — kept current and shared. With that map in hand, any owner (including an external connector's) knows exactly which old object to point their connector back at. The map already exists; the discipline is keeping it current as the native model changes, because a stale map at rollback time is as bad as no map at all.

Decision 12 · Package-bundled edges

The edges that ship inside TargetRecruit disappear when it does

A handful of connectors live inside the retiring package, not in Marlex's own code. They are invisible until the day it is uninstalled — and on that day they simply leave. What replaces each, and what is dropped.

Grounded in a read-only census of the live production org · 11 August 2026

The decision. The TargetRecruit managed package ships its own integration connectors — CV parsing, several job boards, e-signature and a scatter of utilities. They are not Marlex-built edges with a Marlex-owned interface in front of them; they belong to the package. When the package is removed, every one of them goes with it. The question is which of these capabilities Marlex still needs, and for each of those, what native replacement stands in — because there is nothing to re-point, only something to rebuild or let go.

What we chose. Each bundled capability is either rebuilt natively before the package leaves, or explicitly dropped — decided one by one on a KEEP/DROP checklist owned by the product owners. Keeping the package's own connectors alive after the package is gone is not an option; they are part of what is deleted. So the checklist must be complete, and every capability marked KEEP must have a live native replacement, before the uninstall. The uninstall itself is the rollback boundary — a one-way door held to the very end of the programme.

What makes these different

Invisible until uninstall, gone the moment it happens

Most of the integration edges in this record are Marlex's own: they run on Marlex code, behind a Marlex-owned interface, and cutover re-points them from the old model to the new. The bundled edges are the opposite. They are shipped, owned and hosted by the TargetRecruit package. Nothing in Marlex's layer sits in front of them, so there is no seam to re-point and no switch to flip. They keep working right up to the moment the package is removed, and then they are simply not there any more — every connector, its configuration and its wiring deleted along with the package.

That is why they read as a consequence of the rebuild rather than an integration to migrate. The work is not moving them; it is deciding, ahead of time, which capabilities Marlex still wants and building native replacements for those — so that when the package leaves, nothing the business relies on leaves with it unexpectedly.

The trap: these do not announce themselves

Because a bundled connector holds no formal reference from Marlex's own metadata, it will never appear on a list of things blocking the uninstall. It passes every check and then vanishes. The only defence is to enumerate them deliberately, in advance — which is exactly what the KEEP/DROP checklist is for. Discovering a needed capability only after the package is gone is the failure mode this page exists to prevent.

How the options compare

Rebuild-then-drop-with-the-package versus keep the connectors alive

There is a real fork worth stating plainly: rebuild each needed capability natively and let the whole set drop with the package, or try to preserve the package's own connectors past the uninstall. Below are the reasonable outcomes of each and how likely each is.

Likelihoods below are educated guesses, not measured facts, on a calibrated scale from rarely to almost certain (defined on the overview); a measured tag marks a counted figure, not a guess.

Rebuild per capability, then drop with the package Chosen

Each needed capability gets a native replacement before the uninstall; the bundled connectors leave with the package they belong to.

  • Every capability the business keeps has a clean native replacement, and the rest is retired deliberately. probably
  • A capability is judged droppable but a quiet consumer surfaces after the checklist closes. unlikely
  • A native replacement for a KEEP item is not ready in time and holds up the uninstall window. possibly

Upside, and how big No dependence on the departing package survives, and each retained capability runs on Marlex's own code — the whole point of the rebuild, applied to the edges the package hid.

Worst case A KEEP item's replacement slips and the uninstall waits for it — a scheduling cost, not a data loss, and the uninstall is already the last step of the programme.

Keep the package's connectors alive after uninstall Rejected

Try to preserve the bundled connectors as a standalone capability once the package is removed.

  • The connectors are deleted with the package regardless — they cannot be detached from it. almost certain
  • Effort is spent trying to salvage package-internal code that was never Marlex's to keep. probably

Upside, and how big If it were possible, it would save rebuilding the capabilities Marlex still needs — but it is not possible, so the upside is theoretical.

Worst case Wasted effort and a false sense of continuity, ending in the same deletion — the connectors leave with the package no matter what.

This fork is not close, because one side is impossible. A bundled connector cannot outlive the package that ships it. So the only real question is per capability — rebuild it natively because the business still needs it, or drop it because it does not. The chosen route makes that a deliberate decision on a checklist rather than a discovery made the morning the package is gone.

Rollback for this choice

The uninstall is the boundary — after it, these edges are gone

For the Marlex-built edges, rollback means pointing an interface back at the old model. There is no equivalent here, and that is the defining fact of this page. The uninstall itself is the rollback boundary. Before it, everything is reversible: the package still holds its connectors, the old model still answers, and any premature decision can be undone. After it, these bundled edges are deleted and cannot be brought back — the door only opens one way.

So the safeguard is entirely about sequencing before the door closes, not about a switch to flip after. Two conditions must hold at the moment of uninstall: the KEEP/DROP checklist is complete, with every capability decided rather than left implicit; and every capability marked KEEP has a live native replacement already running in production. If either is not true, the uninstall waits. Because it is the last step of the programme — held to the very end, after the new model is proven and the rollback window on the core cutover has closed — there is room to hold it until both conditions are met.

DocsMadeEasy — the document-merge product actually granted by the mislabelled permission set above (also known as HIC DocMerge) — looks at first glance like it might be coupled to the retiring recruitment model, because it works with object and field structure. It is not. The census measured what kind of call it makes, and every one of them is a describe call — a request that asks the platform "what fields does this object have?" to build its merge templates. It never reads a record and never writes one.

That distinction is the whole verdict. A tool that reads or writes the retiring objects has to be re-pointed at cutover; a tool that only inspects the shape of the data model simply sees the new objects once they exist. So DocsMadeEasy has no data coupling to move — the only work is to re-map its merge templates onto the new objects and fields, a configuration task inside the product, not an integration change. It is a managed package in its own right, distinct from the connections bundled inside the retiring vendor package, which disappear when that package is uninstalled — DocsMadeEasy stays.

The docsmadeasy.app Remote Site Setting has no referencing Apex class in the 418 scanned; it is a vestigial outbound-address permission and a retire candidate. The permission set labelled "DocsMadeEasy" grants the HIC DocMerge managed-package components, not DocsMadeEasy — a label correction, not a functional change. Merge-template re-mapping is a product-side config task once the native objects exist.

A caution that runs through the whole census

Logins are a misleading proxy for how live a connection is

No verdict on this page rests on the login count alone: login volume and real call volume do not track each other, so liveness is judged by the measured calls a connection makes, not by how often it signs in — the full attribution is on the measured surface. On this page a login figure is used only as a rough presence signal: a genuine zero, like OIQ_Integration's, is a strong hint of a dead app, but never the measure of how much a live connection matters.

Where the evidence runs out

What the logs cannot tell us

The census is complete on evidence: it can prove that OIQ_Integration has made no logins since 2024 and that the CPQ app supports a capability the org does not use. What it cannot do is supply the last mile of each verdict — ownership and intent. The logs show that a connection is silent; they cannot say whether it is silent because it is dead or because it fires once a year for a process no one has run yet this cycle. Only an owner can close that gap.

So the drops on this page are drop candidates, confirmed by a person, not by a query. That is deliberate: switching off an integration user or deleting an app is cheap to do and awkward to undo if it turns out something quiet still needed it. The safe order is to record the counted fact — zero logins, unused capability — and hand each one to Marlex IT to confirm the owner and the intent before anything is removed.

Rollback for this choice

How this decision fails back

Rollback here is negligible, because none of the tail gates the cutover. These are cleanup items, not go-live actions. Dropping a dead app, retiring a vestigial remote site, and renaming a mislabelled permission set change nothing about whether the core can cross from the old model to the new — they can be done before or after the window, and reversing any of them is a matter of recreating a small piece of configuration, not replaying data.

The one item with any cutover coupling is the ProcessJobApplicantEmail service, which writes the retiring model today and re-points with the core. Its rollback is the same as any other Marlex-owned re-point covered on the adapter page: it is our switch to flip, so if the wider cutover reverses, this service points back at the old objects with it. Everything else on this page is untethered from the go-live entirely.

Residual risk & open items

What we still carry

  • Risk — a "dead" app is dropped while something quiet still needs it. A zero-login app could serve a rare, scheduled process rather than nothing at all. Mitigated by never dropping on the query alone: each drop waits for an owner to confirm the app is genuinely dead before it is switched off.
  • Risk — the mislabelled permission set misleads an administrator. A permission set labelled "DocsMadeEasy" that actually grants HIC DocMerge invites a wrong grant or a wrong revoke. Low-impact but real; closed by the rename, which is a label change with no functional effect.
  • Open: confirm OIQ_Integration is truly dead before dropping it — its purpose is unknown and its owner unidentified, so the zero-login evidence needs a person to stand behind it.
  • Open: confirm the CPQ integration user app is unused in any process before dropping it — the org not using CPQ is a strong signal, but the app's owner should confirm nothing else rides on it.
  • Open: retire the vestigial docsmadeasy.app remote site — a permission with no Apex consumer, safe to remove once confirmed no future work is about to add one.
  • Open: rename the mislabelled "DocsMadeEasy" permission set to reflect that it grants HIC DocMerge.
