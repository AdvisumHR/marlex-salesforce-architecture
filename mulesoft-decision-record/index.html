The integration layer

Where the code that connects Salesforce to the outside world lives, what happens to each connection when TargetRecruit is replaced, and what is still undecided.

Four pages · about fourteen minutes

Salesforce is the group's integration hub by accident. The code that talks to the ERP, the job board, e-signature and the rest lives inside it. This project moves that traffic onto MuleSoft so Salesforce goes back to running recruitment.

The work is forced anyway. The bought recruitment package is being replaced by Marlex's own build, so every connection reading or writing its data has to be re-aimed regardless — and an integration being touched anyway is the cheapest one to move.

Twelve of the twenty-three connections need that change. Which page you want: the edges for what happens to each one, the decisions for why, and the plan for the order.

The finding that shapes everything

Twelve connections touch the data being retired

The sharpest question is not who talks to Salesforce — it is who touches the old recruitment records, because that set, and only that set, has to be re-aimed as the model beneath it moves. A read-only census counted it.

What the cutover waits on. Not the middleware. It waits for every coupled connection to be aimed at the new records the moment the data moves — a change of target, not a change of route.

That change can be made whether or not the middleware is carrying the connection yet, so no interface running late can move the date. Three of the twelve will never move onto it at all: there is no point in their path where a middleware could sit.

What the middleware order is driven by, then. Reuse and volume. The ERP goes first because a second country reuses the same interface, the job board second because it carries the heaviest traffic, and the rest follow as capacity allows.

If you have seen an earlier version of this. An earlier assessment counted the coupled connections by asking which objects each caller touched. That test returned several clean verdicts that were wrong.

It cannot see a package field on a surviving record, a call into package code, or a dependency stored in configuration. This page is the re-check at field level; where a finding changed, both readings are stated.

Writes are unforgiving, reads are not. If a write lands in a dead model, applications are lost; if a read misses, a report goes stale. That difference decides which connections set the date and which merely need doing.

How the census was done, and what it cannot see — method, sample and the one blind spot

The count comes from the platform's own call logs over a 21-day sample taken in July 2026 and reaching back to December, wide enough to catch monthly and quarterly jobs. Every caller was resolved to the connected application behind it and then to the objects it touched.

Logins are not a volume proxy. An integration signs in once and then works for hours, so login counts measure liveness, not traffic. Volume comes from the call logs.

The blind spot. A census of traffic can only see what ran. An integration that is built but not yet carrying production traffic is invisible to it — which is exactly the case of the campaign landing page on the next page. A second one could exist on the same terms.

What counts as "touches the retiring data" — the test, stated. This is the question the whole register turns on, and an earlier pass answered it too narrowly, so it is worth writing down rather than leaving to be re-derived. An integration is coupled if any of the following is true, and a "no" is only a "no" when all four have been checked:

  1. It reads or writes a retiring object. The obvious case, and the only one an object-level traffic census can see.
  2. It reads or writes a retiring field on an object that survives. The candidate record is ordinary and stays, but 141 of its 369 fields belong to the retiring package — so "it only touches the candidate" settles nothing.
  3. It calls code inside the package. Not a field that can be re-aimed but a class that stops existing at uninstall, taking the calling job with it.
  4. It names the retiring model in stored configuration. Saved queries, ingest field maps, mapping tables read at run time. This is invisible to both a traffic census and a scan of the code.

Two consequences worth being explicit about. A negative from network traffic alone is not a negative — a tool installed inside the org makes no calls to observe, and reads from within. And a permission granted is not a dependency used: one edge here can reach four retiring fields and measurably never does, which is recorded as a question for its owner rather than as work to schedule.

Three things logs cannot resolve. Where a tool signs in as named people, its own writes cannot be separated from its users'. Where a tool's field mapping lives in configuration rather than code, a scan of the code misses the coupling entirely — that is how the ERP's coupling was initially missed and later corrected.

And the census resolved which objects each caller touched, not which fields — so a caller reading a surviving object could still be reading a retiring field on it.

For the developers

Evidence gathered read-only from EventLogFile (194-day retention; the 21-day sample is 14 consecutive days plus 7 monthly checkpoints back to December, 888,709 rows), plus ListMetadata, Tooling ApexClass bodies, LoginHistory, User, Site, ConnectedApplication and ExternalClientApplication. 50,391 rows touched AVTRRT__ objects and 418 custom Apex classes were scanned. No writes to any Marlex org.

Traffic is attributed by connection (CONNECTED_APP_ID), never by user, because a single integration user fronts several connections. The delivery-backlog cross-read is what catches the in-build edge that carries no log traffic at all.

The method's own lesson. A namespace grep over Apex misses any integration whose field set is resolved from a custom setting rather than written in code — which is exactly how the ERP's coupling was missed on the first pass and corrected on 2026-08-12.

The field-level re-check, 14 August 2026. Every edge previously recorded as touching no retiring data was re-verified read-only against production at field and record-type level, not just object level. Contact carries 141 package fields of 369, Account 24, Opportunity 1; Campaign, Lead, Case and OpportunityContactRole carry none.

Contact has two record types, and 1,085,882 of 1,120,625 Contacts are candidates — so "reads Contact" usually means "reads candidates".

The re-check cleared three edges outright — e-signature, credit checks and document management: zero package references in any of their code.

It reclassified four edges that an object-level scan had recorded as uncoupled. The CV parser writes seven package fields and creates retiring records; geocoding calls a class inside the package itself.

The customer data platform ingests four package fields, though none reaches the profile it builds. And the document generator keeps its dependency in saved configuration rather than in code — 35 package fields named in the queries behind its candidate reports.

All four were settled from evidence, not left open. The lesson is the method's: counting which objects a caller touches cannot see a package field sitting on a surviving object, nor a call into package code — and counting network traffic cannot see a tool that reads from inside the org, which is how the document generator was missed twice.

Before the register

The words this set uses precisely

Ten terms carry specific meanings here, and several are easy to conflate. The register on the next page assumes all of them.

  • Edge — one integration: Salesforce and one outside system, and the traffic between them. Every integration is an edge.
  • Interface — a piece of middleware built to carry an edge. Only some edges get one. "The first interface" always means the first thing MuleSoft builds, not the first edge to change.
  • Re-point — changing which data an edge reads or writes, from the retiring objects to the new ones. A change of target.
  • Route — moving an edge to travel through the middleware instead of connecting directly. A change of transport. Re-pointing and routing are separate jobs on separate clocks.
  • The core cutover — the single rehearsed weekend when candidates, vacancies and applications move to the new model. It is its own milestone: the only thing it requires of the integrations is that each one is aimed at the new records by the end of that weekend.
  • Reaching production — one interface going live. Each has its own date; the ERP's interface can be live months before the job board's, and either can be live after the cutover. This is not the core cutover, and the cutover does not wait for it.
  • The rebuild — the programme replacing the bought recruitment package with Marlex's own Salesforce build. It is the reason the old objects retire, and the reason every edge on them has to be re-pointed.
  • Coupled — an edge that touches the retiring model, by any of the four tests set out above. Coupled edges re-point; the rest cross the cutover untouched.
  • Waves — the rebuild moves in stages, and each stage moves a set of records. The capabilities that separate cleanly go first: interviews, then the talent pool, then placements — each is a wave. The core wave is the last and largest: candidates, vacancies and applications, moved together in the single weekend the core cutover names. So "re-points with the core wave" means the records it touches move that weekend, and "re-points early" means they move in one of the earlier waves.
  • The switch — a setting in front of a thin layer of indirection, deciding which data model a connection resolves to: the retiring package objects, or the new native ones. Both exist side by side through the rebuild, so any connection running in that window needs one in order to change target without being redeployed. Where it lives follows from timing — in the middleware interface if that is built before the cutover, in Marlex's own Salesforce code if not. An interface built after the cutover needs no switch: only one model is left to point at.
  • A seam — a deliberate joint in the design: the point where what an integration does is separated from who it talks to, so the transport behind it can change by configuration rather than by rewrite. An edge with no seam cannot be routed at all.

Four things in the table are easy to misread. Each is worth a line.

The cutover waits on targets, not on the middleware. Every coupled edge has to be pointing at the new records the moment the data moves — that is the only integration condition the date genuinely depends on, and it is true whether the call arrives through the middleware or straight from Salesforce as it does today. So no interface being late can move the cutover: the switch can be thrown in Marlex's own code instead, which is what the fallback connection exists for.

Being built first is about value, not about the date. The ERP and the job board are the first two interfaces because one is reused by a second country and the other carries the heaviest traffic — not because the cutover is waiting for them. Everything after them is sequenced by whatever capacity is free.

"Direct for now" means later, not never. Every edge Marlex builds itself is expected to move onto the middleware eventually. Where the table says direct for now, the move has simply been deferred — that edge is not an exception to the rule.

"Never routes" is the real exception, and it is permanent. Three edges can never move onto the middleware, because in none of them is there a point in the path where one could sit.

The customer data platform arrives through Salesforce's own built-in connector. The document generator is installed inside the org and never sends anything across a network. The sourcing browser extension runs in each recruiter's own browser, on their own session.

Never routing is not the same as nothing to do. Both of those two still read data that is being retired, so both still have to be re-pointed at the new model. Only one column of the table changes for them — the middleware one.

How each edge authenticates

The identity behind each connection, in both directions

Same edges as the register above, same names, one row each — so a row here can be read against its verdict there. What this table adds is who each connection signs in as, which is what decides whether its activity can be attributed and its access scoped.

The two directions use different mechanisms and are not interchangeable. An inbound call — an outside system calling Salesforce — authenticates against a ConnectedApplication or its modern replacement, an ExternalClientApplication, and then runs as a Salesforce user that the app itself nominates. An outbound call — Salesforce calling out — goes through a NamedCredential, optionally backed by an ExternalCredential holding the secret, and carries no Salesforce user at all.

So a bidirectional edge has two independent identities, and fixing one does nothing for the other. Read from the org and its metadata, 18 August 2026.

The shared service user is a configuration choice, not a platform constraint. Each app nominates its own run-as user, so three of them pointing at the same one was decided rather than imposed — and it can be undone by giving each its own service account. Until it is, traffic on that user has to be split by connection (CONNECTED_APP_ID) or the ERP and the finance feed read as one meaningless row.

Two different problems look alike in the last group but are not. Where an integration signs in as one named person, there is a single login to replace with a service account. Where it signs in as each user who runs it — a browser extension, an in-org package — there is no single identity to scope at all, and the only lever is the profile those people share.

Every inbound app but one holds the Full OAuth scope. That is far wider than any needs, and narrowing it is the single most useful hardening job on this page. The security log collector shows it is possible.

The run-as user is not in the metadata. clientCredentialsUser is absent from every policy file, so it is assigned by hand in Setup after a deploy. A fresh org gets the app but not its identity — which puts the assignment in the runbook, not the deployment.

The four inbound Apex endpoints, each an @RestResource: /infojobsHook, /Api/ERP_SF_Integration, /Api/Humact/Certificado/* and /SG_subscriptionsEvents. The Remote Site behind the training platform is named Humact_Lectio — the only place that second name appears anywhere in the org.

One limit worth knowing. The call log records the entity a call touched, not the fields inside it. An edge writing Contact may still carry a package field on that record, which is exactly how the ERP's own AVTRRT__Gender__c mapping stays invisible to a traffic census. Traffic proves which objects are touched; only metadata proves which fields are.

What each edge actually does

Only the edges with work to do get a block. That is every edge that is re-pointed, built on the middleware, or both — plus the three that retire, because retiring is work too. Nothing here changes a verdict above.

The edges in the last group have no block, and that is the point: no retiring object appears in their traffic, so there is nothing to describe beyond the row.

NET4 — the ERP — the first interface, 13 documented flows

The group's finance, billing and back-office platform. Salesforce sends placements, offers, accounts and candidates out; invoices come back. It is the first interface MuleSoft builds, because it has no dependency on anything else and a second country plugs straight into it.

The coupling is two things, both live. The candidate sync reads AVTRRT__Gender__c and sends it to the ERP as Sexo. Separately, writing the integration log fires a Salesforce automation chain that reads the candidate's applications on the retiring model — a read only. The finance traffic is clean. Both fixes are inside Marlex; nothing changes on the ERP side.

Neither of the two shows up in the traffic, which is worth knowing before anyone re-checks this edge and concludes it is clean. The candidate sync writes the ordinary contact record, so the package field it carries rides inside a record that survives.

The second coupling is not the ERP calling at all — it is Salesforce automation firing afterwards. Both were found by reading the configuration, and confirmed there again on 17 August 2026: the field, the rule that requires it and the automation that writes it are all still active.

Measured: about 7,059 data calls over 7 days; 23,619 candidate syncs in 30 days; 33,448 logins in 30 days. Exactly 1 of the 19 mapped fields in the candidate mapping is a managed-package field — which is the whole of the direct coupling.

The mapping lives in configuration, not code, which is why an early scan of the Apex missed this coupling entirely. It is also why the re-point is a configuration change rather than a rewrite.

For the developers

Two plumbing generations, and only one is live. The live path is the older raw-endpoint classes (MA_APEX_IntegrationSYNC_ERP, MA_SendOfferToN4, MA_Net4SectionCtrl) reading the endpoint from ERP_Connection__c.EndpointIntegration__c through remote site N4_Integration_Site — OAuth2 resource-owner-password-credentials grant, 12-hour bearer token.

The newer MA_Net4Client family resolves its endpoint through the MA_Net4 named credential, but that credential's production endpoint is still a placeholder — so this client cannot be carrying live traffic today. Which generation the wider candidate integration is being built on is an open question, and it decides whether the placeholder is its first blocker.

Candidate sync mandatory fields. FirstName, LastName, Tipo_De_Identificacion__c, Identificacion__c, MobilePhone, Email. The payload also applies a nationality ISO2 conversion, a gender mapping and field-length truncation — all three are contract behaviour, not incidental code.

What suppresses a call. The account and candidate syncs skip when MA_bypass__c.MA_skip_trigger__c is set or MA_TriggerHelper.byPassTrigger('Account') says so. The account sync also skips a record inserted with MA_Codigo_Cliente__c already populated — that is the inbound integration's own write, and the guard is what stops the two directions echoing each other.

The candidate sync skips when the MA_Integration_MX custom permission is active, and on update fires only if a mapped field changed and MA_Codigo_Candidato_NET4__c is already set.

The vendor's read supports more than Marlex calls. The candidate read endpoint accepts CodCandidato, DNI, Nombre and Email; the Apex uses only the first. A Marlex-owned interface should expose all four, because narrowing to one is an accident of the implementation rather than a constraint of the contract.

Attribute by connection, not by login. The shared ERP login fronts at least two distinct integrations, so grouping logs by user conflates them — split by CONNECTED_APP_ID. That is why NET4 shows 33,448 logins against only ~7,059 calls: the 12-hour token forces frequent re-auth.

The decisions · Six choices, with the options weighed

Why the programme integrates this way

Each decision states what was chosen, what else was considered, and the one reason the winner won. The working behind each is one click away.

Grounded in the July 2026 production-org audit · about four minutes, plus detail on demand

Read this first. Decisions 1 to 3 set the shape: integration logic moves out of Salesforce, MuleSoft is the platform, and every edge ships behind a Marlex-owned seam so the transport can change later without a rebuild.

One word used throughout. A seam is a deliberate joint in the design — the point where what an integration does is separated from who it talks to. Marlex's own code calls the seam; behind it sits an interchangeable piece that decides whether the call goes straight out to the supplier or through the middleware. Changing which one is a setting, not a rewrite. The name is the sewing sense: a seam is where a garment can be unpicked and re-joined without remaking it.

Decisions 4 to 6 handle the exceptions: the one edge argued to stay direct forever, the class of bought tools that cannot be routed at all, and the connectors that die with the retiring package.

Status matters here. Only the platform choice is settled. The rest are proposed — argued, written down, not ratified.

The shape

Decisions 1 to 3 — where the logic lives

1 · Why an integration platform proposed

Integration logic runs on an external middleware, in three layers, behind contracts Marlex owns. Salesforce only exposes and consumes interfaces and holds no cross-system plumbing.

It is the only shape that puts a Marlex-owned seam between business logic and every outside system — which is what makes an edge reusable across Marlex and Axxon, and a vendor swap invisible to business logic.

  • Chosen API-led three layers, behind Marlex-owned contracts
  • Rejected All of it inside Salesforce as Apex — makes the recruitment org the group's integration hub, and Axxon cannot reuse any of it
  • Rejected Point-to-point, no layer — grows into many private connections with no shared contract, and the re-point must be repeated one by one
What the three layers are, and how this fails back — the mechanism, and the one thing holding it together

A system layer speaks each end system's own language and exposes it as one clean interface, hiding that system's quirks. A process layer combines those into a business flow and transforms data between shapes. An experience layer tailors an interface to one consumer — a portal, a partner.

The order matters, and it is the part most often drawn wrongly. A consumer enters at the experience layer; that calls process; process calls system. Nobody reaches past a layer to the one beneath it — which is exactly what makes each system's clean face reusable, because every consumer arrives through the same door rather than cutting its own.

How it fails back. There is no switch to throw. Any single edge simply runs direct behind its own contract, so no cutover waits on the platform being ready.

The honest weakness. The discipline is cultural, not structural. Nothing physically stops a hurried edge bypassing its contract — it is held by a code-review rule and a catalogue of agreed data shapes, not by a runtime guard.

And that catalogue does not exist yet. The canonical-contract catalogue — the shared, vendor-neutral data shapes the middleware would standardise on — has not been drawn up. The first interfaces will define it in practice, which means the control this decision leans on is still to be built.

2 · Which platform decided

MuleSoft, selected 3 July 2026, commercial terms since agreed. The working environment arrives September 2026, run by Marlex IT with partner support.

Completeness and API-led fit won. Five candidates were weighed; the operability concern was answered by staffing rather than by holding a fallback open.

  • Chosen MuleSoft — the most complete toolchain and connector breadth
  • Runner-up Azure Integration Services — already inside Marlex's identity, but lost on API-led tooling breadth, not on cost
  • Rejected Amazon Web Services — cheaper infrastructure, but more assembly to reach an API-led shape
  • Rejected Custom Java microservices — maximum flexibility, highest ongoing operational burden
What was not tested, and what to watch — the risk the selection accepted knowingly

No proof-of-concept was run before selection. The first two interfaces are therefore the first real evidence of the platform in Marlex's hands.

What the environment date actually puts at risk. Not the cutover — that has a fallback and keeps its date regardless. What slips is where the switch is thrown: with the interfaces standing, it is a setting inside the middleware, which is the safer place for a change made during a freeze; without them, the same switch is a Salesforce deployment in that window. So a slip costs control and weekend risk, not the milestone.

Worth stating plainly, because it is easy to assume otherwise. No interface reaching production is a precondition of the data move. The interfaces are sequenced by reuse and volume; the cutover is its own milestone, and the two schedules meet only at the moment each coupled connection changes target.

Proportion is the signal to watch. The completeness that won MuleSoft may prove heavier than the current edge count needs. That is now managed through staffing rather than by reopening the platform choice.

Boomi and Workato were named for completeness but never taken to deep analysis or a demonstration.

3 · The swappable adapter proposed

Every rebuilt edge ships behind a Marlex-owned seam, with a direct connection first and a middleware connection later behind the same seam, selected by a configuration record rather than a code change.

It builds the edge once. Both later changes — moving to the new data model, and moving onto the platform — become configuration flips instead of rebuilds.

  • Chosen Seams now with direct connections; a middleware connection per edge later, chosen by configuration
  • Rejected Refactor the existing callouts first, then rebuild — pays for the seam twice, and the first payment wraps a dying model
  • Rejected Direct callouts now with no seam, refactor later — re-plants the exact coupling the rebuild is paying down
Cost, and where each edge's switch lives — the relative cost, and the three homes a switch can have

Cost. Building the seam is a small fraction of building the fallback direct connection behind it — the seam is an interface and a selector, the fallback is the working integration. Running both during coexistence is a genuine carrying cost, bounded by when the fallback is stood down.

What the switch is, first. It is a thin layer of indirection with a setting in front of it: the integration asks for "the candidate", and the setting decides whether that resolves to the retiring package object or to the new native one. Two models exist side by side through the rebuild, so the setting is what lets a connection change which one it uses without being redeployed. Think of it as a feature flag over a choice of target — and, once the middleware is involved, over a choice of which system interface to call.

Who needs one, precisely. Any edge that will still be running while both models are live. That is every coupled edge, and it is especially every edge routed onto the middleware before the cutover: routing it does not change which records it writes, so a connection moved onto the middleware while the old model is still in use will need to change target later, and needs the setting to do it with.

And where it lives follows from timing, not preference. Build the middleware interface before the cutover and the setting lives there. Don't, and it lives on the Salesforce side, in the code that carries the connection today — which is where it already is for everything except the two interfaces being built first. Either is a working answer.

The case that needs no switch at all is the edge whose interface is built after the cutover. By then only the native model exists, so it is pointed straight at it and there is nothing to flip. That is the cheapest outcome available, and it is the reason routing an edge late is not a failure.

A switch has three possible homes, chosen per edge. In the middleware — for the ERP, the job board and Orbio, where the target must change at cutover and depending on a late-breaking Salesforce release would be worst. In the Salesforce-side adapter — the default everywhere else. Or neither, where a vendor's own connector holds it.

The rule: put the switch in the middleware when the switch itself is the risk.

Which is why only two interfaces are named as needed early. The ERP and the job board are the two whose switch we want held in the middleware — the ERP because a second country reuses the same interface, the job board because it is the heaviest writer and the switch has to land in a freeze window. For every other coupled edge the switch lives in Marlex's own Salesforce code, which works today and needs no middleware at all. Those edges move onto the middleware when there is capacity, and that move is a change of route, not of target.

A caveat on timing. Where an outside system calls a Marlex endpoint directly today, no middleware sits in that path, so the switch currently lives in the Apex behind the endpoint. It becomes middleware-held only once the interface exists and the caller's address points at it.

The switch table is therefore a target state, not a precondition. Until an interface exists, that edge's switch stays in the Apex behind the endpoint — which still works; it is a deployment rather than a setting, and a deployment inside a freeze window is the cost of not having the interface yet.

Not yet built. The seam interfaces are not defined and the configuration selector is not implemented — so "the switch is configuration, not a deployment" is a design, not yet a fact.

The exceptions

Decisions 4 to 6 — what sits outside the rule

4 · The one argued exception proposed

The CV parser stays directly connected, permanently — the only edge argued to stay off the platform for good. The call is open, not settled.

Staying direct does not mean uncoupled. Verified in production on 14 August 2026: the parser writes seven package fields on the candidate, queries the retiring vacancy object and creates application records. So it re-points with the core wave like any coupled edge — the argument here is only about transport, never about the data.

It is synchronous inference inside a flow a recruiter is waiting on, with no shared contract to own. A middleware hop would add delay and running cost per call for nothing to orchestrate.

  • Chosen Stay direct — keeps the fast path fast
  • Rejected Route through the platform — a network hop and a cost per call, in a flow a person is waiting on
The risk this accepts, and two edges often confused with it — why "direct forever" can quietly become wrong

The risk. If the parser later needs shared monitoring, rate-limiting or a canonical contract, "direct forever" quietly becomes the wrong answer. It is mitigated by the seam: routing it in later is a configuration flip, not a rebuild.

Two edges are often lumped in here and should not be. The finance write feed is not an exception — it routes like any other edge, on its owner's schedule; its owner decides when, not whether.

The Power BI extract is not an exception either. It is a cutover re-point whose route is genuinely open, either behind the middleware or as a fresh extract against the new model.

Measured: the finance feed does 636 writes and 22 reads over 30 days — small, and worth re-checking if that shifts, because a direct write feed has no middleware observing it and a bad push lands straight on incentive and margin records.

One consequence people miss. The native parser being live does not retire the old package parser. The job board's CV path still calls the old one, and closing it is part of the job-board cutover — two parsers run in parallel by design until then.

For the developers

The parser is CVParserCtrl, an Apex HTTP callout via named credentials Anthropic_API (Claude) and Groq_API. It replaces the package's OCR reader and is live in production. A document-intelligence extension reads identity documents and bank details into native fields — MA_IBAN__c and related identification and validity fields, verified present in production.

Synchronous, in-flow inference: no canonical contract, no fan-out, nothing to mediate. That is the whole argument for staying direct. The job board's CV path still calls the TRINTG__-bundled package parser until that feed re-points.

Its coupling, verified read-only in production on 14 August 2026. The parser writes AVTRRT__Gender__c, AVTRRT__Country__c, AVTRRT__Source__c, AVTRRT__Resume__c, AVTRRT__Resume_Received_Date__c, AVTRRT__AutoPopulate_Skillset__c and AVTRRT__Copilot_Summary__c onto the candidate. It also queries AVTRRT__Job__c and inserts AVTRRT__Job_Applicant__c with AVTRRT__Stage__c = 'Aplicacion'.

An object-level census missed this because the parser reads and writes standard Contact — the package fields sit on it. All seven re-point with the core wave.

5 · When a bought tool cannot be routed rule settled · membership open

Where a tool connects through a fixed vendor connector, the routing rule cannot apply — there is no Marlex-owned seam to put in front of it. Two tools are now confirmed to be in that class, on mechanisms verified in the live org.

The rule is a technical impossibility, not a judgement — the middleware cannot impersonate Salesforce to a packaged connector. The danger is using it to excuse an edge from routing before the mechanism is actually confirmed. Membership also says nothing about whether an edge needs re-pointing: both confirmed members do.

  • Confirmed The customer data platform — it ingests on Salesforce's own first-party connector, which nothing can be placed in front of
  • Confirmed The document generator — an installed package reading records inside the org, so there is no network hop to intercept
  • Provisional Taleva — treated as a member pending confirmation; its named-user sign-in hides its own writes
  • Unconfirmed Rainmakers — reaches the org as an external client app, which is a routable arrangement, the opposite of a fixed connector
  • Ruled out Orbio — confirmed 2026-07-21 to connect by ordinary API calls, so it is routed like any other edge
Why this class matters even if it turns out empty — the rollback nobody at Marlex can flip

This is the one rollback that is not Marlex's to flip. A fixed-connector tool must be re-pointed back at the old objects by its external owner. So the re-point party, the window and the signal have to be agreed in advance, before any fallback window opens, backed by a current old-to-new substitution map.

The two confirmed members are the easier half of this. Both are unroutable but Marlex owns both ends, so their re-point — an ingest mapping on one, saved report queries on the other — is Marlex's own to make and to reverse. The hard case is a tool whose connector an outside party controls, which is why membership is worth keeping separate from ownership.

Measured: Taleva read the application object about 110,000 times over 30 days and runs on a System-Administrator profile — far more access than it needs. Rainmakers has zero recorded logins and no measured traffic; it is a pilot.

The standing risk. A connector left pointed at a dead object after a rollback, because an external owner was slow or unavailable. The only lever Marlex holds over a tool it cannot route is least-privilege scoping.

6 · The connectors that die with the package checklist open

Each bundled capability is rebuilt natively before the package leaves, or explicitly dropped — decided one by one on a keep-or-drop checklist owned by the product owners.

The alternative is impossible: a bundled connector cannot outlive its package. So the only real choice is per capability, made deliberately rather than discovered the morning the package is gone.

  • Chosen Rebuild per capability, then drop the rest with the package
  • Impossible Keep the package's connectors alive after uninstall — they are deleted with it regardless
The seven capabilities, and the one-way door — what ships inside the package, and what already has a successor

Seven capabilities ship inside the package: CV parsing, job boards, e-signature, Prophecy, geocoding, Bitly and CallEmAll.

Two already have live native replacements — CV parsing and the InfoJobs job board. LinkedIn needs certified-partner status, which is commercial rather than technical. The remaining five are the product owners' keep-or-drop call.

Every "keep" needs its successor built, deployed and verified in production before the uninstall window. A keep with no live successor blocks the door.

There is no rollback after the fact. The uninstall is the boundary — a one-way door held to the very end of the programme. The whole safeguard is sequencing.

The hidden risk. A connector believed dormant may still feed a live process, and it will never appear on a dependency scan. Every bundled connector has to be enumerated from the package's own settings and confirmed before it is marked "drop".

The plan · Order of work, and what is open

What happens in what order, and what is still undecided

A sequence, not a schedule. It fixes what must come before what, and sets no dates — because the rebuild's own waves carry none either.

Sequence current as of 12 August 2026 · about three minutes

Two kinds of work, on two clocks. Re-points are forced by the rebuild's own waves and need no middleware built for them. Interfaces are what MuleSoft builds, in its own order. Confusing the two is the most common misreading of this plan.

Why there are no dates. The rebuild's waves carry none by deliberate choice: the work starts now, each wave lands when the people on it finish, and effort is aimed at finishing early rather than at hitting a date. So a re-point's deadline is an event — "when placements move" is the whole specification, and it is complete as written.

What sets the order

The rebuild's waves drive the integration order

The rebuild moves in waves. The capabilities that can be separated from the shared candidate record go first — interviews, then the talent pool, then placements — and the coupled core of candidates, vacancies and applications follows in a single rehearsed weekend.

So an integration is pulled forward by whichever wave first moves an object it touches, not by its size, its volume, or the final cutover. That is why a two-query training feed falls due before the two biggest interfaces.

The dual-read rule, and the three orders that were rejected — why interfaces may read both models, and where the hard line is

During the early waves, dual-read is allowed and expected. A middleware interface may read the retiring objects and the new ones while a wave is in flight. The two models genuinely co-exist then; this is a design requirement, not a compromise.

At the final cutover the rule is absolute — no middleware interface may read or write any retiring package object. It is testable: the interface either references those objects or it does not.

An interface may reach production still reading the retiring objects. That is a legitimate finished state, because what is published to the outside system does not change afterwards — a second implementation behind the same published interface reads the new objects later, selected by configuration.

Three alternative orders were weighed and rejected:

  • Wait for the rebuild to finish, then build the middleware — forces every interface to be built against a model already being dismantled, or leaves the platform idle for months, and the early-wave integrations would still be sitting in Salesforce when their objects move.
  • Build only against the new model, forbid dual-read — no interface could reach production before its wave, giving up the early ERP delivery and the multi-country reuse, and piling work into the one window with no slack.
  • Allow residual package reads after the final cutover — the uninstall deletes the package's data, so a reading left in place is a deferred failure with no warning.

How this fails back. If a wave slips, the affected interface keeps reading the retiring objects for longer — a supported state, because dual-read was designed in. The only hard line is the final cutover.

The weakness this order carries: integration dates now depend on rebuild dates, so a wave that slips moves interfaces with it.
