Ways of workingRelease management — keeping branches, environments and production in step

Product owners, the delivery partner and the in-house IT team all build on the same live Salesforce at once. The process in force is the one in 2.2, because the branches and their environments are not yet in step; the single-branch model in 2.1 is the target it protects. This page covers the environments and branches, how a change is promoted through them, and the roles and rules that apply throughout.

1 · Environments and branches

The repository has three long-lived branches, each mirroring one Salesforce environment, with production as the single source of truth that every change is cut from and released back to.

2 · Promotions and releases

Everything in this section answers one question: how does a change get from a developer’s sandbox into production without carrying anything it should not?

2.1 · The target: cut every change from production

This is the target, not today’s practice. It applies from the moment the reset in 2.3 has been done. Until then, follow 2.2.

Every change starts as a branch cut from production, so it always begins from the latest live version of the components it touches. The same branch is then promoted into each environment in turn — the development line, then the pre-production line where the mandatory review happens, then back into production as the release. Promoting the change itself, rather than merging one environment into the next, is what keeps each change independent: two changes in flight can go live in either order.

When several features must ship together

Sometimes a set of features has to go live as one deployment. For that, cut a release branch from production and collect the features there for a single deploy. The rule that must not bend: the pull request and the review stay at the feature level — each feature is reviewed on its own, never as a bundle. Grouping is for the deployment, not the review, so any one feature can still be dropped from the bundle without holding up the others.

2.2 · Today: the gap, and the branches it forces

A single pull request made the problem visible. It reported roughly 120 components as brand-new when about 17 of them already existed in production. The change was not describing real work; it was describing the gap between the branch and reality. Three layers of drift had stacked up: a branch no longer matched its own environment, the lower environments lagged production, and work built directly in an environment was being pushed down into the branch rather than the other way round. When the baseline is wrong like this, review is impossible, an automated check has nothing trustworthy to compare against, and a rollback cannot know what the “before” state was.

Measuring it gave one figure that matters more than the totals: the two lines last agreed on 21 May 2026, but the genuine overlap — the same component changed on both sides — is around 160 components, not the thousands a raw comparison suggests. So resolving the overlap is about a day’s careful work, and about half that overlap is configuration built through the screens rather than code, which is what makes it delicate rather than merely large.

One further finding limits how far the history can be trusted: where the same change reached both lines, it was almost always re-done by hand rather than copied. The two versions match in content while version control still treats them as unrelated — presenting them as new work, and later as conflicts. Reconciliation must be based on what the environments actually contain, not on what the branch history appears to say.

A clean merge is not evidence of a correct merge. That same re-doing by hand creates a quieter failure. If a change reached production and was later undone or replaced on the pre-production line, the tooling cannot see that the two are versions of one thing — so bringing the lines together raises nothing, and the undone version is the one that survives. No conflict, no marker, nothing for a reviewer to catch. This is why the combined result is always deployed and tested rather than the change on its own, and why an undo must be applied to both lines or recorded as a deliberate difference: the tooling will not remind anyone later.

Promoting a change while the gap exists

The target model assumes the pre-production line already reflects production. While it does not, where the branch is cut from only decides which promotion pays for the gap — one drowns the review, the other ships more than was agreed.

So while the gap exists, a change is carried on one branch per environment it passes through, each cut from the line it merges into: on the full path that is three — development, pre-production, release — and on the short path two, because there is no development line. That cost per change is the reason the reset in 2.3 is worth doing rather than living with.

Each branch after the first starts from its own line and then needs the change applied to it. There are two honest ways to do that, and the choice follows what the change touches — not which branch it is going to:

  • Copy the commits from the previous branch of the same change. The release branch can take its commits directly from the pre branch, and the pre branch from the dev branch. This is safe here, and it is worth being clear why, because copying commits is exactly what caused the reconciliation problem: the danger is a copy living on a long-lived branch, where the duplicate the tooling cannot recognise resurfaces later as an unexplained clash. These three branches are deleted the moment they merge, so there is no later merge between them for a duplicate to survive into. Use it for code: classes, components, tests.
  • Capture the components from the environment and commit them. The right choice for anything built through the Salesforce screens, and for work too large or long-running to replay. Two reasons. Their definitions cannot be safely combined by hand; and after validation the version in the pre-production environment is often not what was originally built — it was adjusted on screen during review — so copying the earlier commits would carry the pre-validation version to production. Capturing commits what the environment actually contains rather than what the history claims. Most work in flight falls here.

In short: copy the commits for code, capture from the environment for anything configured on screen — and where a change contains both, treat each part on its own terms. Delete each branch at its merge; if one is kept alive and reused, the copying stops being safe.

Access rights — profiles, permission sets, sharing rules — sit outside both: they are never combined automatically, but decided by one person.

Two rules hold throughout. Bring a change’s components up to date from production, never from the pre-production line — taking them from pre-production looks clean going in and quietly enlarges the release with work not approved to go live. And record every promotion as a genuine combination of the two branches: flattening it leaves them still looking apart, so the same gap returns and the same conflicts are resolved twice.

The development line does not need a third branch. Its sandboxes are refreshed from production, so once that is done they already match production and the release branch merges into them cleanly. Anyone taking the short path skips the development line entirely, so it does not arise for them at all.

Three cases that need naming

  • An urgent production fix. Cut it from production, ship it, and treat re-applying it to the pre-production line as a mandatory follow-up that keeps the item open until done. Nobody captures metadata mid-incident, so this is the one case where the fix is deliberately applied twice and the second pass is scheduled, not improvised.
  • Undoing something already live. The undo must reach both lines, or be written down as a difference both sides accept. Left to one line, it becomes the silent case above.
  • Work abandoned after review but before release. It is already on the pre-production line and will never be in production — new drift created by the process meant to prevent it. Either undo it there explicitly or resolve it before the reset; leaving it is how the gap quietly reopens.

Branch freshness matters too. Cut late and merge quickly. Because a pull request compares against the point where the branch and its target last agreed, a branch left to age shows the whole accumulated gap instead of its own change — which is exactly the symptom that opened this section. If a branch goes stale, cut it again rather than topping it up.

2.3 · Closing the gap, and keeping it closed

Two different jobs hide inside “fix the drift”. The one-off reset gets everything back to a production-true baseline now: retrieve each long-lived environment in full into its own branch, then back-promote the difference down to the pre-production line and refresh the development sandboxes from production. The ongoing rule keeps it there: before starting any change, bring just the components that change will touch from production into the pre-production branch and environment, then cut the feature branch. It is the back-promotion in miniature — instead of reconciling every drifted component at once, only the handful about to be worked on is brought up to the live version. The feature branch needs nothing itself: cut afterwards, it inherits the corrected baseline. A wholesale refresh of the pre-production environment is avoided — it would destroy in-progress work that only lives there.

The reset is what retires the extra branches in 2.2. Once the pre-production line reflects production, a single branch cut from production merges cleanly into both, one review covers it, and the second branch simply stops being necessary. That is the test of whether the reset has worked, and the point at which the temporary arrangement should be dropped rather than kept out of habit.

Two things make the back-promotion safe, and the first matters most. Retrieve first: before any merge, each environment is captured into its own branch — especially pre-production into its own — so live work that exists only in an environment is under version control and cannot be silently lost. Every in-progress change must sit on a branch before the reset starts; anything living only in an environment cannot be protected.

Then expect to decide, component by component. It is tempting to assume that merging in the right order makes production win for whatever has drifted while in-progress branches keep the components they own. It does not. Whichever order the merges are done in, the comparison is made against the point where the two lines last agreed, so for the components changed on both sides — the roughly 160 above — the tooling will not choose: it either stops and asks, on about 114 of them, or silently combines both versions into one that neither line ever had. Those decisions need a named owner per area and a record of what was chosen. Merging the in-progress branches in first actively makes this harder, because it mixes their work into the same decisions. Bring production in first, resolve the drift on its own, then re-apply each in-progress branch on top of a baseline that is already clean.

3 · Roles and rules

The hard case: two people editing the same Flow at once

Cutting every change from production keeps code clean, but it does not, on its own, solve the case the delivery partner raised: two people editing the same declarative component — a Flow, a page layout, a screen configuration — in parallel. These are built through the Salesforce screens, and their underlying definition cannot be safely merged or hand-edited afterwards; nobody edits a Flow on screen and then strips a colleague’s changes out of its definition by hand. So if two changes touch the same Flow, keeping their branches separate does not make them independent — whoever merges second inherits the other’s change and cannot ship without it.

Branch strategy cannot fix this; it is a matter of coordination and hygiene, handled by five practices both sides agreed:

  • A single owner for complex shared components. Heavily-shared Flows and core layouts have one person who makes or coordinates their changes, so two people are not editing the same one in parallel by default.
  • A shared environment for evolutions, an isolated one only for genuinely new work. When several people evolve the same existing capability, they share one development environment for that area and resolve any clash together, on screen — not by reconciling definitions at promotion time. A private environment is kept only for work that is genuinely new or independent, where no one else is touching the same components.
  • Deploy the merged result, never the change branch directly. A change is merged into its target branch first, and the combined result is what gets deployed and validated — because the version-control merge may not surface every conflict, so the deployment and tests must exercise the combination.
  • An overlap check before every pull request. Before raising a request, check whether recent changes or open requests against the target already touch the same components; if they overlap, the people involved resolve it first.
  • Dependencies made visible up front. When one change cannot go live until another does, that dependency is documented and visible at a glance, rather than living in a verbal “wait for my OK”.

This is the condition that makes cutting from production safe in practice, not just on paper: the branch model handles independent code, and these five practices carry the concurrent-declarative case it cannot.

Three settings to put in place, whichever process is in force

These are configuration, not practice, and they are the cheapest corrections available. Each needs an owner.

  • Stop access rights combining on their own. Profiles, permission sets and sharing rules are long machine-ordered lists, so where the same file changed on both lines the tooling merges two people’s grants without raising anything — and deploys access nobody chose. Twenty-two of these files are in that state: sixteen would stop and ask, which is safe, but six combine silently, the administrator profile among them. Mark these file types so they can never be combined automatically and always require a person to decide. Marking them the other way — to take both sides — is the opposite of the fix and produces a plausible-looking but invalid file.
  • Allow only a true combination when a request is completed. The other two ways of completing a request leave the two branches still looking apart afterwards, so the same gap is presented again and the same decisions are made twice. Turn those options off for the production and pre-production branches rather than relying on everyone remembering.
  • Let the tooling remember resolutions. It can record how a clash was resolved and reapply it next time. With the same components in the gap being resolved on every promotion until the reset, this saves the work being redone by hand each time. Switch it on before the reset, not after.

Who reviews, who releases, and what no partner may skip

A Release Manager in the in-house IT team groups changes into releases and coordinates the deployments. The hard rule is that no partner releases to production without an in-house review — a partner cannot approve its own change. The release into production itself needs no second review; it is a handover to the Release Manager, not a fresh change. Automation is staged: keep pull requests plus the mandatory review now, add automated checks on each pull request as the first step, and only adopt a dedicated deployment platform if the volume genuinely calls for it.

Still open.
  • Who runs the one-off reset, and when — it is cheapest during a quiet period, and the reset itself takes roughly two days, largely re-pointing production record references that the current recruitment package hard-codes.
  • Who owns each of the three settings above, and by when.
  • Which combined result the access-rights files should carry where both lines changed them, and who decides it.
  • Whether the release branch is prepared by the developer or by the Release Manager for partner-led changes while the extra branches are in force.
  • What happens to the long-running branches that pre-date the reset — re-cut from the new baseline, or abandoned.
  • Who owns the coordination of cross-change dependencies on the in-house side — today it tends to fall to one partner person by default, and the delivery partner asked for it to be owned and visible rather than verbal.
  • Whether every non-developer change is forced through the same build-and-review path, and whether the delivery partner releases independently or routes the deploy through the Release Manager. The review rule itself is settled.
