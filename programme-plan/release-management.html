Ways of workingRelease management — keeping branches, environments and production in step

Product owners, the delivery partner and the in-house IT team all build on the same live Salesforce at once. The process in force is the one in 2.2, because the branches and their environments are not yet in step; the single-branch model in 2.1 is the target it protects. This page covers the environments and branches, how a change is promoted through them, and the roles and rules that apply throughout.

1 · Environments and branches

The repository has two long-lived branches, each mirroring one shared Salesforce environment, with production as the single source of truth that every change is cut from and released back to. Below them sit the build environments: one sandbox per vertical — recruitment, CRM and back office — which is where the work is actually made. Those build sandboxes have no long-lived branch of their own: each change leaves them on a branch of its own and goes straight to pre-production.

A long-lived branch exists only where a shared environment sits behind it. Its whole job is to be the trusted record of what one environment contains — which is only worth recording where several people converge, so there is something to reconcile against. A single-vertical build sandbox has no convergence to record: what comes out of it is a change, and a change travels on its own branch. A permanent branch for such an environment creates a line nobody reconciles, which is precisely how the gap described in 2.2 opened. That is the test that leaves two branches here rather than three.

So pre-production is the first shared environment every change reaches — the verticals and the delivery partner alike, each building and testing in its own sandbox and joining there. It is therefore the first place all the work in flight is visible together, and the point where the mandatory review sits.

2 · Promotions and releases

Everything in this section answers one question: how does a change get from a developer’s sandbox into production without carrying anything it should not?

2.1 · The target: cut every change from production

This is the target, not today’s practice. It applies from the moment the reset in 2.3 has been done. Until then, follow 2.2.

Every change starts as a branch cut from production, so it always begins from the latest live version of the components it touches. The same branch is then promoted into each environment in turn — the development line, then the pre-production line where the mandatory review happens, then back into production as the release. Promoting the change itself, rather than merging one environment into the next, is what keeps each change independent: two changes in flight can go live in either order.

When several features must ship together

Sometimes a set of features has to go live as one deployment. For that, cut a release branch from production and collect the features there for a single deploy. The rule that must not bend: the pull request and the review stay at the feature level — each feature is reviewed on its own, never as a bundle. Grouping is for the deployment, not the review, so any one feature can still be dropped from the bundle without holding up the others.

2.2 · Today: the gap, and the branches it forces

A single pull request made the problem visible: it reported roughly 120 components as brand-new when about 17 already existed in production. It was not describing real work — it was describing the gap between the branch and reality. Three layers had stacked up: a branch no longer matched its own environment, the lower environments lagged production, and work built directly in an environment was pushed down into the branch. With a wrong baseline, review is impossible, automated checks have nothing trustworthy to compare against, and a rollback cannot know the “before” state.

The lines last agreed on 21 May 2026, but the figure that matters is the overlap — the same component changed on both sides — and that is around 160 components, not the thousands a raw comparison suggests. About half of it is configuration built through the screens, which is what makes it delicate rather than merely large.

One further finding limits how far the history can be trusted: where the same change reached both lines, it was almost always re-done by hand rather than copied. The two versions match in content while version control still treats them as unrelated — presenting them as new work, and later as conflicts. Reconciliation must be based on what the environments actually contain, not on what the branch history appears to say.

A clean merge is not evidence of a correct merge. If a change reached production and was later undone on the pre-production line, version control cannot see the two as versions of one thing — so bringing the lines together raises nothing and the undone version survives. No conflict, no marker, nothing for a reviewer to catch. Hence: deploy and test the combined result, and apply an undo to both lines or record it as a deliberate difference.

Promoting a change while the gap exists

The target model assumes the pre-production line already reflects production. While it does not, where the branch is cut from only decides which promotion pays for the gap — one drowns the review, the other ships more than was agreed.

So while the gap exists, a change is carried on one branch per environment it passes through, each cut from the line it merges into — two in all: one into pre-production, one for the release. That cost, paid on every single change, is the reason the reset in 2.3 is worth doing rather than living with.

The development itself still happens on a branch cut from production, whichever path is in use. That branch is what guarantees the change starts from the live version of everything it touches — but while the gap exists it is never merged into anything, because merging it would drag the whole gap along with it. It ends its life as a working branch, and its commits are copied onto each environment’s branch instead — only the ones that genuinely belong to the feature.

Each branch after the first needs the change applied to it. How depends on what the change touches:

What it touchesHow to apply itWhy
Codeclasses, components, testsCopy the commits from the previous branch of the same change — the pre-production branch from the branch it was built on, the release branch from the pre-production one.Safe because these branches are deleted at their merge, so no later merge exists for the unrecognised duplicate to survive into. On a long-lived branch it would be the reconciliation problem all over again.
Built on screenFlows, layouts, screen configurationsCapture the components from the environment and commit them.Their definitions cannot be safely combined by hand, and after validation the environment often holds a different version than the one first committed.
Access rightsprofiles, permission sets, sharing rulesOne person decides the combined result.Never combined automatically — see the settings in section 3.

Where a change contains both, treat each part on its own terms — and delete each branch at its merge, or the copying stops being safe.

Two rules hold throughout. Update a change’s components from production, never from the pre-production line — the latter looks clean going in and quietly enlarges the release. And record every promotion as a genuine combination of the two branches; flattening it leaves them still looking apart, so the same gap returns and the same conflicts are resolved twice.

The build sandboxes are brought up to production the same way — by refresh or back-promotion, with the in-flight work captured on a branch first either way, because both routes overwrite whatever exists only in the environment.

Three cases that need naming

CaseWhat to do
Urgent production fixCut from production and ship. Keep the item open until it is re-applied to the pre-production line — nobody captures metadata mid-incident, so that second pass is scheduled, not improvised.
Undoing something liveThe undo reaches both lines, or is recorded as an accepted difference. Left on one, it becomes the silent case above.
Work abandoned after reviewIt sits on the pre-production line and will never reach production. Undo it explicitly or resolve it before the reset.

Cut late and merge quickly. A pull request compares against the point where the branch and its target last agreed, so a branch left to age shows the whole accumulated gap instead of its own change — the symptom that opened this section. If one goes stale, cut it again rather than topping it up.

2.3 · Closing the gap, and keeping it closed

Two jobs hide inside “fix the drift”. The one-off reset restores a production-true baseline — the procedure below. The ongoing rule keeps it there. It starts as a check rather than an action: before touching a component that already exists live, confirm that the version in your development environment and in its branch matches production. Most of the time it does and there is nothing to do. Only where they differ do you bring the production version down into your environment and your branch first — and only then start building.

The reset takes two legitimate routes, and neither may touch an environment until the in-flight work is on a branch — both overwrite whatever exists only in the environment:

RouteGivesCostsUsed for
RefreshThe cleaner baselineDiscards the environment’s test dataA development environment, where that environment’s own team prefers a clean copy
Back-promotionKeeps the environment’s test data. In-flight work survives with no manual listSomeone decides every differing component, including the ones version control settles silentlyPre-production always
A refreshed environment is not yet a usable environment. A refresh copies the configuration. It does not restore working conditions. After every refresh someone must work through this list:
  • Re-enable the user accounts. They come back disabled, with altered email addresses.
  • Re-point every connection to another system. The copy keeps production’s targets, so the refreshed environment calls the live systems until someone changes it.
  • Re-check entitlements for installed products. These do not always survive the copy.
  • Re-point TargetRecruit’s stored production record identifiers — the case described after the table.
  • Mask the personal data. The copied environments hold real candidate records, so this is a legal obligation rather than housekeeping. It matters most in the full-size environment, which holds the complete set.

This list needs a named owner and a fixed place in the procedure. Without an owner it gets done partly.

Running a back-promotion, in order

The steps below are the whole procedure. The order is not a preference — each step exists because doing it later loses something that cannot be recovered.

Cut the working branch from the pre-production line, never from production. The rule is general: cut it from the line you will merge into. Cutting it from production inverts the safety: everything the environment holds must then be listed again by hand to survive, and whatever is missed disappears with no conflict raised. Measured on the repository, the same work built the wrong way round proposed 7,397 files and could not be merged at all; built from the pre-production line it proposed 1,494 and merged clean. The promotion tooling Salesforce teams use works the same way: it creates the promotion branch from the destination.

For the developers

The two capture passes (step 1). Pass one is a manifest listing explicit <members> per type — keep it. Profiles and permission sets are the reason: a category-wide request returns only the fragment relevant to the other components in the manifest, so naming the objects, classes, layouts and tabs is what makes an access-rights file come back whole. Measured here, one profile went from 34 KB to over 500 KB once the request named components. Pass two is the same manifest with <members>*</members>, retrieved to a scratch directory outside the package directories and deleted afterwards — it is diagnostic only.

The second source (step 2). Use a different API from the first, not the same query twice: the Metadata API listing and a query against the platform’s own definition objects disagree on totals, and that is expected — what matters is that both agree on the specific component. A component absent from one and present in the other is not a deletion candidate. Types whose whole category cannot be listed must be skipped rather than treated as empty, or every component of that type looks deletable.

Why step 6 is a step at all: deletion has to be asked for by name — an ordinary deployment will not action it, so the component survives and the reset never quite finishes. And there are three cases here, not two: production holds the right version, the lower environment does, or neither holds the component at all and it survives only in version control — invisible to a capture, which only ever adds and updates. Confirm against both environments before deciding.

For the developers

Deletions go in a destructiveChanges.xml alongside the package manifest, and a validation-only deploy of it is the reliable existence probe: if a component is not in the org, the validation says so by name, while nothing is removed. Run it with --dry-run and --target-org pointed at each side in turn.

Do not trust listMetadata for this. It does not report Custom Metadata records or Custom Settings correctly, so a component can be absent from its output and present in the org — which is exactly how metadata surviving only in version control gets mistaken for a deletion that already happened. The destructive-changes validation is the check that answers it.

On step 7, validate the combined result the same way before the real deploy and read the component count back. If it is far larger than what was authored, the scope is wrong — stop rather than deploy.

Why step 8 is a step at all: join the lines even when the result changes not one file — keep the contents already standing and let the record of the meeting be all the step produces. Two checks confirm it took: production sits in the branch’s own history, and a trial combination of a feature branch raises nothing.

For the developers

The point being moved is the merge base. Where the target branch already holds the content you want, join the histories without touching the tree: git merge -s ours production — it records the merge commit and keeps the current side’s tree verbatim. Do not confuse it with -X ours, which resolves conflicts file-by-file inside a real merge and does change the result.

The two checks:

  • git merge-base --is-ancestor production sandbox-pre — exits 0 once production is an ancestor. That is the assertion, and it belongs in the pipeline, not in someone’s memory.
  • git merge --no-commit --no-ff feature/x on a throwaway copy, then git merge --abort — a feature branch must now merge with no conflicts. If it still reports hundreds, the join did not take.

What step 5 preserves: four kinds, plus people. Step 5 keeps five categories of setting in the lower environment rather than carrying production’s version down.

  • Connection settings — the stored definitions of how the org reaches another system, and any configuration record holding an address or a target. Carry production’s version down and the lower environment starts calling the live systems, then writing test data into them. The measured case on this programme is TargetRecruit, which stores production record identifiers inside its own configuration records: re-pointing them is most of the reset’s two days, and it repeats every time an environment is copied or realigned.
  • Secrets and certificates — a capture never returns the secret itself, so what arrives in the branch is a setting with an empty secret. Leave the environment’s own in place.
  • Application registrations — an external application signs in with a key and a return address, and both can differ per environment.
  • Switches that turn things on — anything enabling email, notifications or automatic exchanges with another system.
  • References to particular people — the easiest to miss, because both routes carry it: the user a dashboard or report runs as, record owners, queue and group membership, and rules that show or hide part of a screen depending on who is looking. A refresh makes it obvious, since accounts arrive disabled. A back-promotion is quieter — it copies no people, but it still carries down configuration that names them. Preserve or re-point those references either way.
The test is what the value holds, not what kind of component it is. If it points at a system, an identifier or a particular person, or it switches something on, the lower environment keeps its own version. If it is a rule, a mapping, a business threshold or anything else functional, it aligns with production. So a category of configuration is not frozen wholesale — only the part of it that describes the environment. Everything else — code, automations, objects, screen layouts, access rights — aligns with production as normal.

So the name is not the test. Two configuration records can sit side by side under the same naming, one holding an address that differs per environment and the next differing only by the platform version it was written against — and the second aligns with production like anything else functional. Open the value.

The reset is what retires the extra branches. Once the pre-production line reflects production, one branch cut from production merges cleanly into both and one review covers it. That is the test of whether the reset worked — and the point to drop the temporary arrangement rather than keep it out of habit.

One case inside step 4 deserves naming. On a few components version control does not choose a side at all — it stitches both versions into one file, taking some lines from each. Sometimes joining both edits is exactly right; sometimes it produces a file that is valid, deployable and wrong. Those need reading one at a time, whichever side the record says should win.

For the developers

Cut from the target and combine production in, then impose the recorded decision on every differing path rather than only the conflicted ones:

  • git checkout -b backpromotion/prod-to-pre origin/sandbox-pre then git merge origin/production
  • production’s version → git checkout origin/production -- <path>; the environment’s → git checkout origin/sandbox-pre -- <path>; where the winning side no longer has the file, git rm
  • list the differing set with git diff --name-only origin/production origin/sandbox-pre — that, not the conflict list, is the worklist

Two traps measured here. Rename detection pairs byte-identical files that have nothing to do with each other — it silently dropped eighteen .cls-meta.xml companions and moved four fields to a different object. Assert every .cls has its .cls-meta.xml before opening the request. And a batch git checkout fails on paths containing accented characters, so those files go missing without an error; the merge itself handles them, so prefer it over scripted checkouts where you can.

3 · Roles and rules

A Release Manager in the in-house IT team groups changes into releases and coordinates deployments. Everything below holds whichever of the two processes is in force.

  • No partner releases to production without an in-house review. Nobody approves their own change. The release itself needs no second review — it is a handover, not a fresh change. This rule is settled.
  • One owner per complex shared component. Components built through the Salesforce screens — Flows, layouts, screen configurations — cannot be safely combined afterwards, so two changes touching the same Flow are never independent however their branches are arranged. One person makes or coordinates those changes.
  • Evolutions share a development environment; only genuinely new work gets an isolated one. Clashes are then resolved together on screen rather than reconciled at promotion time.
  • Deploy the merged result, never the branch. The merge may not surface every clash, so the deployment and tests must exercise the combination.
  • Check for overlap before raising a request, and document any dependency between changes up front rather than leaving it in a verbal “wait for my OK”.

Three settings, each needing an owner

  • Stop access rights combining on their own. Twenty-two profile and permission-set files changed on both lines; six combine silently, the administrator profile among them, granting access nobody chose. Mark these types so a person must always decide.
  • Allow only a true combination when a request is completed, on the production and pre-production branches. The alternatives leave the branches looking apart, so the same decisions get made twice.
  • Let version control remember resolutions, so the same clashes are not re-resolved by hand on every promotion. Switch it on before the reset.

Automation comes in stages: stage one is pull requests and the mandatory review; stage two adds automated checks on each request; stage three, only if volume justifies it, a dedicated deployment platform.

Still open.
  • Who runs the one-off reset, and when — it is cheapest during a quiet period, and the reset itself takes roughly two days.
  • Who owns each of the three settings above, and by when — including who decides the combined result for the access-rights files that changed on both lines.
  • Who masks the personal data in the copied environments, against which fields, and as part of which step — it gates using the full-size environment for the data rehearsal.
  • Whether the release branch is prepared by the developer or by the Release Manager for partner-led changes while the extra branches are in force.
  • What happens to the long-running branches that pre-date the reset — re-cut from the new baseline, or abandoned.
  • Formal retirement of the third branch. The model above has two long-lived branches, because no shared environment was ever identified behind the third. It is treated as retired and no longer appears on any promotion path. What remains is to confirm that with the Release Manager and give its outstanding commits a destination — re-cut onto the new baseline, or accepted as abandoned.
  • Who owns the coordination of cross-change dependencies on the in-house side — today it tends to fall to one partner person by default, and the delivery partner asked for it to be owned and visible rather than verbal.
  • Whether every non-developer change is forced through the same build-and-review path, and whether the delivery partner releases independently or routes the deploy through the Release Manager. The review rule itself is settled.
