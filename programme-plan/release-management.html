Ways of workingRelease management — keeping branches, environments and production in step

Product owners, the delivery partner and the in-house IT team all build on the same live Salesforce at once. The process in force is the one in 2.2, because the branches and their environments are not yet in step; the single-branch model in 2.1 is the target it protects. This page covers the environments and branches, how a change is promoted through them, and the roles and rules that apply throughout.

1 · Environments and branches

The repository has three long-lived branches, each mirroring one Salesforce environment, with production as the single source of truth that every change is cut from and released back to. Below them sit the build environments: one sandbox per vertical — recruitment, CRM and back office — which is where the work is actually made before it joins the integration line.

Two consequences worth stating. The verticals build separately but meet in the integration environment, so a change that crosses two of them is first seen together there, not in pre-production. And the delivery partner does not use the integration line at all — it builds and tests in its own sandbox and joins at pre-production, which is therefore the first environment where all the work in flight is visible in one place.

2 · Promotions and releases

Everything in this section answers one question: how does a change get from a developer’s sandbox into production without carrying anything it should not?

2.1 · The target: cut every change from production

This is the target, not today’s practice. It applies from the moment the reset in 2.3 has been done. Until then, follow 2.2.

Every change starts as a branch cut from production, so it always begins from the latest live version of the components it touches. The same branch is then promoted into each environment in turn — the development line, then the pre-production line where the mandatory review happens, then back into production as the release. Promoting the change itself, rather than merging one environment into the next, is what keeps each change independent: two changes in flight can go live in either order.

When several features must ship together

Sometimes a set of features has to go live as one deployment. For that, cut a release branch from production and collect the features there for a single deploy. The rule that must not bend: the pull request and the review stay at the feature level — each feature is reviewed on its own, never as a bundle. Grouping is for the deployment, not the review, so any one feature can still be dropped from the bundle without holding up the others.

2.2 · Today: the gap, and the branches it forces

A single pull request made the problem visible: it reported roughly 120 components as brand-new when about 17 already existed in production. It was not describing real work — it was describing the gap between the branch and reality. Three layers had stacked up: a branch no longer matched its own environment, the lower environments lagged production, and work built directly in an environment was pushed down into the branch. With a wrong baseline, review is impossible, automated checks have nothing trustworthy to compare against, and a rollback cannot know the “before” state.

The lines last agreed on 21 May 2026, but the figure that matters is the overlap — the same component changed on both sides — and that is around 160 components, not the thousands a raw comparison suggests. About half of it is configuration built through the screens, which is what makes it delicate rather than merely large.

One further finding limits how far the history can be trusted: where the same change reached both lines, it was almost always re-done by hand rather than copied. The two versions match in content while version control still treats them as unrelated — presenting them as new work, and later as conflicts. Reconciliation must be based on what the environments actually contain, not on what the branch history appears to say.

A clean merge is not evidence of a correct merge. If a change reached production and was later undone on the pre-production line, the tooling cannot see the two as versions of one thing — so bringing the lines together raises nothing and the undone version survives. No conflict, no marker, nothing for a reviewer to catch. Hence: deploy and test the combined result, and apply an undo to both lines or record it as a deliberate difference.

Promoting a change while the gap exists

The target model assumes the pre-production line already reflects production. While it does not, where the branch is cut from only decides which promotion pays for the gap — one drowns the review, the other ships more than was agreed.

So while the gap exists, a change is carried on one branch per environment it passes through, each cut from the line it merges into: on the full path that is three — integration, pre-production, release — and on the short path two, because the delivery partner does not use the integration line. That cost per change is the reason the reset in 2.3 is worth doing rather than living with.

The development itself still happens on a branch cut from production, whichever path is in use. That branch is what guarantees the change starts from the live version of everything it touches — but while the gap exists it is never merged into anything, because merging it would drag the whole gap along with it. It ends its life as a working branch, and its commits are copied onto each environment’s branch instead — only the ones that genuinely belong to the feature.

Each branch after the first needs the change applied to it. How depends on what the change touches:

What it touchesHow to apply itWhy
Codeclasses, components, testsCopy the commits from the previous branch of the same change — release from pre, pre from dev.Safe because these branches are deleted at their merge, so no later merge exists for the unrecognised duplicate to survive into. On a long-lived branch it would be the reconciliation problem all over again.

Where a change contains both, treat each part on its own terms — and delete each branch at its merge, or the copying stops being safe.

Two rules hold throughout. Update a change’s components from production, never from the pre-production line — the latter looks clean going in and quietly enlarges the release. And record every promotion as a genuine combination of the two branches; flattening it leaves them still looking apart, so the same gap returns and the same conflicts are resolved twice.

Each development line is brought up to production the same way — by refresh or back-promotion, with the in-flight work on a branch first either way. Anyone taking the short path skips the development line entirely, so it does not arise for them at all.

Three cases that need naming

CaseWhat to do
Urgent production fixCut from production and ship. Keep the item open until it is re-applied to the pre-production line — nobody captures metadata mid-incident, so that second pass is scheduled, not improvised.
Undoing something liveThe undo reaches both lines, or is recorded as an accepted difference. Left on one, it becomes the silent case above.
Work abandoned after reviewIt sits on the pre-production line and will never reach production. Undo it explicitly or resolve it before the reset.

Cut late and merge quickly. A pull request compares against the point where the branch and its target last agreed, so a branch left to age shows the whole accumulated gap instead of its own change — the symptom that opened this section. If one goes stale, cut it again rather than topping it up.

2.3 · Closing the gap, and keeping it closed

Two jobs hide inside “fix the drift”. The one-off reset restores a production-true baseline — the procedure below. The ongoing rule keeps it there, and it is a check before it is a move: before touching a component that already exists live, confirm that the version in your development environment and in its branch matches production. Most of the time it does and there is nothing to do. Only where they differ do you bring the production version down into your environment and your branch first — and only then start building.

The reset takes two legitimate routes, and neither may touch an environment until the in-flight work is on a branch — both overwrite whatever exists only in the environment:

RouteGivesCostsUsed for
RefreshThe cleaner baselineDiscards the environment’s test dataA development sandbox, if its team prefers
Back-promotionKeeps the data and re-applies the in-flight work on topThe drifted components must be decided one by onePre-production always
A refreshed environment is not yet a usable one. A copy restores the configuration, not the working conditions: user accounts come back disabled and their email addresses altered, connections to other systems still point where the copy said they did, and entitlements for installed products do not always come across — plus the TargetRecruit re-pointing described below. And because the copied environments hold real candidate records, masking the personal data after a copy is a legal obligation rather than housekeeping — most of all in the full-size environment, which holds the complete set. Both belong on a standing checklist with a named owner.

Running a back-promotion, in order

The steps below are the whole procedure. The order is not a preference — each step exists because doing it later loses something that cannot be recovered.

One condition makes step 2 cheap: the feature branch and the back-promotion branch must come from the same line. Measured on the repository, the same change touched three files from its own line and conflicted on 114 from the other.

Validate first because many failures will have nothing to do with the change — a report running as someone with no account there, configuration for an unlicensed product, references left by a retired integration — and meeting those mid-deployment leaves it half-applied.
7. Join the historiesCombine the lines once more even where the result changes nothing, so version control records them as having met.Aligning the contents is not the same as recording that they agree. Left undone, the next comparison starts from the old point again and the conflicts come back.

Why step 5 is a step at all: a component removed in production but still present in a lower environment is not taken out by an ordinary deployment. It survives, the next comparison reports it as a difference all over again, and the reset never quite finishes — the leftovers cannot be told apart from a step that was missed. Deletion has to be asked for by name. And there are three cases here, not two: production holds the right version, the lower environment does, or neither holds the component at all and it survives only in version control — invisible to a capture, which only ever adds and updates. Confirm against both environments before deciding.

Why step 7 is a step at all: aligning the contents does not move the point the lines are compared from, and while that point stays in the past every future comparison keeps re-reporting the same distance as conflicts. So join them even when the result changes not one file — keep the contents already standing and let the record of the meeting be all the step produces. Two checks confirm it took: production sits in the branch’s own history, and a trial combination of a feature branch raises nothing.

The four kinds step 4 leaves out. Connection settings — the stored definitions of how the org reaches other systems, and any configuration record holding an address or a target; overwrite those and the lower environment starts calling the live systems and writing test data into them. The measured case here is TargetRecruit, which hard-codes production record Ids into its custom settings: re-pointing them is most of the reset’s two days, and it has to happen every time an environment is copied or realigned. Secrets and certificates — these never come back when an environment is captured, so what arrives is a setting with the secret missing, which is its own reason to leave them alone. Application registrations — the keys and return addresses an external application uses to sign in can be particular to each environment. Switches that turn things on — anything enabling email, notifications or automatic exchanges with other systems.

A fifth is easy to miss because it survives both routes: references to particular people — the user a dashboard or report runs as, record owners, queue and group membership, and rules that show or hide parts of the screen depending on who is looking. A copy makes this obvious, as above. A back-promotion does not copy people at all, but it can still carry down metadata that names them, and those references need preserving or re-pointing just the same.

The test is what the value holds, not what kind of component it is. If it points at a system, an identifier or a particular person, or it switches something on, the lower environment keeps its own version. If it is a rule, a mapping, a business threshold or anything else functional, it aligns with production. So a category of configuration is not frozen wholesale — only the part of it that describes the environment. Everything else — code, automations, objects, screen layouts, access rights — aligns with production as normal.

So the name is not the test. Two configuration records can sit side by side under the same naming, one holding an address that differs per environment and the next differing only by the platform version it was written against — and the second aligns with production like anything else functional. Open the value.

The reset is what retires the extra branches. Once the pre-production line reflects production, one branch cut from production merges cleanly into both and one review covers it. That is the test of whether the reset worked — and the point to drop the temporary arrangement rather than keep it out of habit.

Inside that combination, expect to decide component by component. Ordering protects the in-flight work, but it does not decide the overlap for you: the comparison is always against the point where the lines last agreed, so for the ~160 components changed on both sides the tooling either stops and asks or silently combines both versions. Those are the decisions step 3 calls for — taken one at a time, not by a rule applied in bulk.

3 · Roles and rules

A Release Manager in the in-house IT team groups changes into releases and coordinates deployments. Everything below holds whichever of the two processes is in force.

  • No partner releases to production without an in-house review. Nobody approves their own change. The release itself needs no second review — it is a handover, not a fresh change. This rule is settled.
  • One owner per complex shared component. Components built through the Salesforce screens — Flows, layouts, screen configurations — cannot be safely combined afterwards, so two changes touching the same Flow are never independent however their branches are arranged. One person makes or coordinates those changes.
  • Evolutions share a development environment; only genuinely new work gets an isolated one. Clashes are then resolved together on screen rather than reconciled at promotion time.
  • Deploy the merged result, never the branch. The merge may not surface every clash, so the deployment and tests must exercise the combination.
  • Check for overlap before raising a request, and document any dependency between changes up front rather than leaving it in a verbal “wait for my OK”.

Three settings, each needing an owner

  • Stop access rights combining on their own. Twenty-two profile and permission-set files changed on both lines; six combine silently, the administrator profile among them, granting access nobody chose. Mark these types so a person must always decide.
  • Allow only a true combination when a request is completed, on the production and pre-production branches. The alternatives leave the branches looking apart, so the same decisions get made twice.
  • Let the tooling remember resolutions, so the same clashes are not re-resolved by hand on every promotion. Switch it on before the reset.

Automation comes in stages: pull requests and the mandatory review now, automated checks on each request next, a dedicated deployment platform only if the volume calls for it.

Still open.
  • Who runs the one-off reset, and when — it is cheapest during a quiet period, and the reset itself takes roughly two days.
  • Who owns each of the three settings above, and by when — including who decides the combined result for the access-rights files that changed on both lines.
  • Who masks the personal data in the copied environments, against which fields, and as part of which step — it gates using the full-size environment for the data rehearsal.
  • Whether the release branch is prepared by the developer or by the Release Manager for partner-led changes while the extra branches are in force.
  • What happens to the long-running branches that pre-date the reset — re-cut from the new baseline, or abandoned.
  • Who owns the coordination of cross-change dependencies on the in-house side — today it tends to fall to one partner person by default, and the delivery partner asked for it to be owned and visible rather than verbal.
  • Whether every non-developer change is forced through the same build-and-review path, and whether the delivery partner releases independently or routes the deploy through the Release Manager. The review rule itself is settled.
