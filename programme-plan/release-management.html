Ways of workingRelease management — keeping branches, environments and production in step

Product owners, the delivery partner and the in-house IT team all build on the same live Salesforce at once. Four choices keep that orderly: where a change’s branch is cut from, which environments it flows through, how those environments are kept in step with production, and how much of the checking is automated. This page records the model and the fix for the drift a recent review exposed.

Three branches, three environments, one source of truth

The repository has three long-lived branches, each mirroring one Salesforce environment, with production as the single source of truth that every change is cut from and released back to.

Cut every change from production, then promote the same branch forward

Every change starts as a branch cut from production, so it always begins from the latest live version of the components it touches. The same branch is then promoted into each environment in turn — the development line, then the pre-production line where the mandatory review happens, then back into production as the release. Promoting the change itself, rather than merging one environment into the next, is what keeps each change independent: two changes in flight can go live in either order.

A developer does not have to go through the development line at all. The short path skips it: develop and test on the Developer sandbox, then raise the feature’s pull request straight into the pre-production line. This is the path the delivery partner follows — and they only adopt cutting from production once the drift below is fixed; until then, cutting from the pre-production line is their defence against it, not a shortcut.

When several features must ship together

Sometimes a set of features has to go live as one deployment. For that, cut a release branch from production and collect the features there for a single deploy. The rule that must not bend: the pull request and the review stay at the feature level — each feature is reviewed on its own, never as a bundle. Grouping is for the deployment, not the review, so any one feature can still be dropped from the bundle without holding up the others.

The drift a recent review exposed

A single pull request made the problem visible. It reported roughly 120 components as brand-new when about 17 of them already existed in production. The change was not describing real work; it was describing the gap between the branch and reality. Three layers of drift had stacked up: a branch no longer matched its own environment, the lower environments lagged production, and work built directly in an environment was being pushed down into the branch rather than the other way round. When the baseline is wrong like this, review is impossible, an automated check has nothing trustworthy to compare against, and a rollback cannot know what the “before” state was.

Closing the drift, and keeping it closed

Two different jobs hide inside “fix the drift”. The one-off reset gets everything back to a production-true baseline now: retrieve each long-lived environment in full into its own branch, then back-promote the difference down to the pre-production line and refresh the development sandboxes from production. The ongoing rule keeps it there: before starting any change, sync just the components in its scope to the latest production version, then cut the branch. A wholesale refresh of the pre-production environment is avoided — it would destroy in-progress work that only lives there.

Two safeguards make the back-promotion safe. The retrieve-first step above matters most: before any merge, each environment is captured into its own branch — especially PRE into the sandbox-pre branch — so the live work that only exists in an environment is under version control and cannot be silently lost. Then the merge itself is done in two moves, in order: first merge every live feature branch into the back-promotion branch, so their components keep the in-progress version; then bring production in underneath, so production wins for everything that has drifted while the live branches win for the components they own. Doing the merge the other way round could silently overwrite work already committed to the pre-production line. The prerequisite is that every in-progress change sits on a live feature branch before the reset starts — anything living only in the environment cannot be protected.

Roles and what no partner may skip

A Release Manager in the in-house IT team groups changes into releases and coordinates the deployments. The hard rule is that no partner releases to production without an in-house review — a partner cannot approve its own change. The release into production itself needs no second review; it is a handover to the Release Manager, not a fresh change. Automation is staged: keep pull requests plus the mandatory review now, add automated checks on each pull request as the first step, and only adopt a dedicated deployment platform if the volume genuinely calls for it.

Still open. Who runs the one-off reset, and when — it is cheapest during a quiet period, and takes roughly two days, largely re-pointing production record references that the current recruitment package hard-codes. Also open: whether every non-developer change is forced through the same build-and-review path, and whether the delivery partner releases independently or routes the deploy through the Release Manager. The review rule itself is settled.
