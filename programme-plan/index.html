What this programme is

Marlex's recruitment system runs today on TargetRecruit, a product it licenses. The programme replaces it with a solution Marlex builds and owns itself, on the same Salesforce platform. Marlex stops renting the engine and owns it — no vendor lock-in, and its own roadmap. The aim is to match what the business does today and improve how people actually use it, not to copy the old tool screen-for-screen.

The rebuild happens inside the same Salesforce org that runs TargetRecruit today — not a new, separate system. The new and the old run side by side, and each part of recruitment switches over to the new build once it is proven, retiring the matching TargetRecruit piece. So the systems that already feed data into Salesforce keep working unchanged, and switching over means pointing a process at the new build rather than moving to a different system.

The recruitment rebuild is the priority; almost everything else follows it. Two tracks run in parallel with it and do not wait: the integration layer (MuleSoft), built one system at a time, and Marketing Cloud, which runs finite campaigns now and re-points onto the new model later. Three things come after the rebuild is live: the sharing-and-access model, Axxon's onboarding onto the standard, and the rollout to other Marlex countries.

Once the rebuilt platform is proven and Marlex is running on it, that same build is reused — Axxon adopts it on its own org, and Portugal, Italy and the Philippines roll out from it — so each new brand or country starts from a proven base rather than a fresh build.

See the programme roadmap for the full sequence and the gates between phases.

In words

The recruitment rebuild is the main sequence, and it is the programme's priority. It starts with foundations — the tooling, governance, glossary, and an inventory of what the current system does, which feeds everything after. Before the build begins, two things clear: a cleanup of the current org (removing dead functionality and technical debt so nothing broken is carried forward), and the design decisions and requirements the build needs to start — naming rules, how components are owned and kept configurable, the data-privacy model, and the business processes each area must follow. The exact build scope is sized by that requirements inventory rather than fixed up front. One thing about the starting point works in the programme's favour: the business already works inside a single standard Salesforce application today, rather than a patchwork of separate apps maintained per team — so the rebuild starts from a simple, single-app footprint with nothing to untangle.

The build then runs. The data model is set as the real foundation, and the CRM, recruitment and back-office areas are built against it. Each area is built, tested and validated with the business as it goes — testing is part of building each capability, not a separate phase bolted on afterwards — and moving the data across from the old TargetRecruit objects to the new ones is part of the rebuild too, rehearsed on a full copy of the data until it runs cleanly. Everything is built to be reusable across the group from the start (driven by configuration, with no hard-coded values) so it can later serve Axxon and other countries without rework.

As the build finishes, the whole solution is reviewed and classified — which parts are group-wide, which are Marlex-specific, which are country-specific. This is where the shared group standard is actually defined, on real proven components, rather than fixed up front. The business then signs the whole thing off in a single acceptance cycle — the data move, the experience and the reports together — so it signs exactly what it will receive. Go-live follows in place, with a short period of close support. At go-live, records keep the access model they have today — the switch moves no privacy boundary; tightening records to private and adding the country dimension is a deliberate, separately-rehearsed stage after go-live.

Two tracks run alongside the rebuild rather than behind it, with each integration timed against the rebuild stage that moves the data it touches. The integration layer (MuleSoft) is built one external system at a time and can be swapped in when each lane is ready. Marketing runs finite campaigns now to earn back its licence and re-points onto the new model after go-live, staying in the same org throughout.

Everything else waits until the rebuild is live. Once it is, the finishing work runs in order: the rented product is uninstalled, the lower-priority and evolutive features held back during the rebuild are built, and then the record-privacy model is tightened. Only after go-live do Axxon's onboarding onto the standard and the rollout to Portugal, Italy and the Philippines become actionable — they all build on the rebuilt platform and the classified standard. The one early exception on the Axxon side is its ERP move to NET4, which is independent of the rebuild and reuses the shared NET4 connection, so it can start sooner.

Three things carry the most risk. Most of the delivery sits with one implementation partner, with no fallback in place today. The matching-and-search engine is bought, not built, so feasibility depends on that engine. And there is a firm date to plan against: the contractual runway on TargetRecruit ends in November 2027 — a renewal-and-renegotiation point with a paid fallback, not a sudden switch-off — so the new solution should be live and TargetRecruit retired with margin before that runway is spent. The lower-coupling areas are already confirmed to go live ahead of the main switch-over; whether the tightly-coupled core crosses in one move or in stages is still open, pending the product team's analysis of how independent those areas really are.

Risks & assumptionsWhat could put the plan at risk

The handful of things most likely to put the programme's dates or outcome at risk — and how each is being managed.

These are the programme-level risks the roadmap is built around. They are watched and reviewed on a regular cadence; the mitigations below are the current plan, not a guarantee.

The main risks

Most delivery sits with one partner

The large majority of the build depends on a single delivery partner, with no fallback in place today. If that partner's capacity slips, much of the critical path slips with it.

How it's managed — Governance keeps the concentration visible and under review; a second-partner option is on the table if the load or the risk grows.

Source control and the live environments have drifted apart

The repository branches, their Salesforce environments and production no longer describe the same state. That makes ordinary pull requests misleading: existing production components appear as new, genuine differences are buried in noise, and reviewers cannot reliably tell what a release would change.

How it's managed — Use the low-activity August window for a controlled reset: retrieve the full production baseline, promote it back through the shared pre-production branch while protecting live work, then refresh developer environments. After that, every change starts from production and synchronises the components in its own scope before development begins.

The matching-and-search engine is bought, not built

The engine that parses CVs and matches candidates to roles is the hardest part to reproduce, so it is licensed rather than rebuilt. The rebuild's feasibility depends on that engine plugging in cleanly.

How it's managed — Treated as a buy decision from the start and assessed early as part of the feasibility work, rather than discovered late in the build.

Parallel tracks the cutover depends on may not be ready in time

The recruitment rebuild does not go live on its own. Several tracks run alongside it and have to be finished and working before the platform can be switched over — and each is a separate piece of work with its own risk of slipping. The candidate and recruiter portals have to be rebuilt and operational, because the current ones live on the platform being retired. The matching-and-search capability has to be plugged in and working, because recruitment cannot run without it. And every integration that reads and writes the current platform's data today has to be re-routed through the new middleware and pointed at the new data model, so nothing that depends on those data flows breaks at go-live. If any one of these is late, the switchover cannot safely happen — so the whole cutover date is exposed to the slowest of these parallel tracks, not just to the core build.

How it's managed — Each dependent track is planned and sequenced as its own line of work with its own readiness gate, rather than being assumed to fall into place around the core build. The integrations are moved behind the middleware on a schedule ahead of the switchover and rehearsed, the matching capability is assessed early as part of the feasibility work, and the portals are tracked as a distinct piece of work with their owner and timing made explicit. Cutover only proceeds once these are confirmed ready — the readiness of the parallel tracks is a gate on the date, not an afterthought.

Going live in pieces may leave the old components behind

The rebuild is delivered incrementally: as each capability is rebuilt on the new model, it goes live on the working system before the old platform is fully switched off. This is deliberate and keeps delivery moving — but it carries a risk. If the team publishes the new version of a capability without also switching off and removing what it replaces, the old and new versions end up running side by side. The result is two versions of the same information, and leftover screens, buttons, related lists, reports and connections such as Power BI still pointing at the parts being retired. Left unmanaged, that becomes two sources of the truth for the same data and a growing pile of half-retired components that nobody owns — harder and riskier to clean up the longer it is left.

How it's managed — Each incremental go-live is treated as a complete change, not just the new build: rebuild what is kept, and at the same moment switch off or hide what it replaces, so only one version is ever live. Final deletion of the retired components can be deferred to a clean-up after go-live, but that deferred work is written down, owned and dated rather than left open-ended — so “turn it off now, delete it later” does not quietly become “never delete it.” The end state to protect is a single live model with nothing visible still pointing at what has been retired.

The November-2027 runway

The contractual runway on TargetRecruit, the current recruitment product, ends in November 2027 — a renewal-and-renegotiation point with a paid fallback available, not a sudden switch-off. The rebuilt platform should be live and TargetRecruit retired with margin before that runway is spent; the date is firm enough to plan against, but there is real negotiation room and a fallback rather than a single hard cut-off.

How it's managed — Every target date for the rebuild is worked backwards from this runway, with a margin of close support after go-live built in — and the fallback (holding the old licence past the date) is available if the schedule needs it.

Running old and new systems side by side is expensive

While each area is switched over one at a time, the old and new systems run together. For Axxon in particular, keeping legacy systems alive alongside the new stack gets expensive after about a year, with a legacy-licence cliff in 2028.

How it's managed — The switch-over is sequenced to keep the overlap short, and the copy-the-standard approach for Axxon is faster to stand up than a bespoke build, shortening the time two systems run at once.

Working assumptions

The plan also rests on a set of working assumptions — the things taken as true for the roadmap to hold. They are tracked alongside the risks and firmed up as each phase becomes active; the ones that matter most to the shape of the programme are below.

The data moves cleanly to the new model

The candidate, job, placement and document data — including CVs and signed contracts — can be moved from the old objects onto the new ones without loss, and the automations built on the old data are rebuilt cleanly rather than carried over in their old shape.

Requirements are gathered before each area is built

Each part of the platform is built against confirmed business requirements captured just before that area starts, rather than everything being specified up front. The rebuild is a deliberate redesign for better adoption, not a like-for-like copy — so what “good” looks like is agreed area by area.

One delivery partner carries the build

The implementation partner has the capacity, knowledge and continuity to deliver the build across the programme. There is no second partner pre-qualified as a fallback today, so the plan assumes this one holds.

The small internal team can run the new middleware

The internal IT team can operate and develop the chosen integration platform alongside the delivery work, in line with the requirement that the platform be manageable in-house rather than depending on an outside operator.

The roadmap is a logical order, not yet a committed date plan

The sequence shows what must happen before what and the fixed external deadlines it has to respect. It is not yet backed by a full effort estimate and staffing plan, so the dates express logical order and external constraints rather than a costed, capacity-checked timeline.

How it fits together

This is the programme's core and its largest project. It re-creates, natively, every part of the recruitment platform that is tied to the rented product's objects and fields, plus the product features the business still needs — matching what works today and improving how people actually use it, not copying the old tool screen-for-screen. Nothing is dropped up front: the business keeps everything for now, and the requirements gate decides later what is genuinely no longer needed. The work moves fast — components are rebuilt in large numbers, often several in a day — so the real unit of tracking is not this list of headings but a component register: for each component being replaced, its native replacement, how it is switched on, and the exact end-to-end behaviour to test. There is no feature freeze while this runs; new work is built on the new model from day one so the rebuild never falls behind the live system.

One thing about today's setup makes the rebuild simpler than it might appear. Almost everyone already works inside a single standard Salesforce app and reaches the recruitment product as tabs within it, rather than the business running on a patchwork of separate applications maintained per team. There is no tangle of parallel apps to unwind, so the rebuild starts from a clean single-app footprint, and the main design question is simply how the new native experience takes the place of that one app.

The native data model is settled first and becomes the real foundation everything else is built against. Then the platform is rebuilt on top of it, in the same org as the rented product, while everyone keeps working on that product untouched — the existing screens, logic and data are not changed, and each new component is built alongside its old counterpart and left switched off. Rebuilding a component includes rebuilding its access: the same people keep the same access they have today, reproduced first so nobody gains or loses anything by the switch. As each component is finished it is tested to prove it matches the behaviour it replaces, deployed to a validation environment for the business to accept, and then released to production — where it sits dormant, in place, until activation.

Around the build sit the enablers. Foundation comes first — the tooling, the glossary, and the requirements inventory that sizes the whole rebuild and decides what is rebuilt, what is bought, and what is later evolution. The current org is cleaned of dead functionality and technical debt so nothing broken is carried forward, and the design decisions the build needs are settled (naming, ownership, the routing pattern, the build standards, the standard processes) without pre-locking a group-wide standard. The one capability deliberately not built is the matching-and-search engine — it is selected and bought, and plugged in behind a Marlex-owned interface. Monitoring is built into the rebuild itself, because today's visibility belongs to the rented product and would leave with it. Integrations ship with direct connections first and a switch that lets the integration platform join later, so nothing waits on it.

When everything is deployed and dormant, the switch is proven before it is taken. The build's correctness has already been proven continuously through the build — the full test suite runs automatically every night against the switched-off build, so drift is caught within a day rather than saved up for a single weekend. The rehearsal does not re-test the functionality; it proves the switch. A sandbox is refreshed from production, and the activation is rehearsed end to end; then a full roll-back is rehearsed the other way — until both the activation and the roll-back are timed and stable, at least twice. The data move is rehearsed the same way on a full copy of the data, so the load times are known before the real freeze. The business signs the whole thing off in a single acceptance cycle — running the critical-path scripts against the migrated data — then the switch happens in place: a freeze on every source that writes the old data, the data move, the identity switch, and endpoint re-targeting. Records carry today's access model forward unchanged at the switch — it moves no privacy boundary. The rented product is kept installed underneath as a real fallback with a dated expiry, so there is a clean way back, and close support runs until there are no critical incidents.

After go-live the work finishes in a deliberate order. First the rented product is uninstalled — its dependencies removed and its components deleted — as a separate, gated, later step against written criteria, never folded into the switch. Then the lower-priority and evolutive features that were held back are built on the now-native platform. Last comes the privacy tightening: making the records that matter private and adding the country dimension, as its own stage with its own rehearsal and its own roll-back. Two things gate the whole thing: the bought engine's quality against real Marlex data is a go/no-go criterion at the switch — it does not proceed on hope — and the rented product's contractual runway ending in November 2027 is the date the rebuild plans to beat with margin — a renewal point with a paid fallback, not a hard lights-out. Whether the switch is one go-live or staged by area is still open.

How it fits together

This project has two inseparable halves. The first is onboarding the internal HR team so they run internal recruitment — backfills, internal moves, onboarding — on the same platform the business uses for external hiring, instead of separate tools. The second is the access model that makes it safe: privatising the records that matter and giving each the right visibility, whether the boundary is a country or an internal business unit. They are one initiative because HR's work is confidential by nature — a hiring process can be to replace a specific manager, and must not be visible to the person being replaced — so the moment HR is on the platform, the open model everyone uses today is no longer acceptable for their records. The clearest case is the HR team's own records: salaries, interview notes, clock-ins, internal candidates, which the rest of the business should not see. Alongside it runs the country dimension: isolating records by country as the group grows into new markets.

Because it onboards a team, this is not only a sharing flip — it builds. HR needs their own kind of record set apart from external hiring, a management structure so a leader sees their team's internal processes and no one sees upward, their own access profile, and whatever onboarding-specific screens the requirements turn out to need. All of it is built on the new owned platform, never on the rented product being retired. The HR requirements are still being gathered, so the shape is set at the level of decisions with the details left open until the HR team confirms them.

The private, country-keyed model is the target, and one business decision governs when it lands. By default the switch to the new platform changes nothing about who sees what — the new records carry today's access model forward exactly as it is, so the move touches no boundary in the most sensitive window, and the tightening runs deliberately afterwards, on its own quiet timing with its own rehearsal and its own way back. But that default holds only while nothing confidential is on the platform. If the business chooses to bring the HR team on at the same moment as the switch, the private model has to be in place from day one — HR's records cannot be open even briefly — so the tightening moves into the switch rather than following it. The recommendation is to bring HR on after the switch, keeping that window clean; the decision belongs to the person responsible for People, and the platform is built so either path works. Opening access back up if something is wrong is cheap, which is what keeps both paths safe.

Everything follows a replicate-then-extend principle: reproduce today's access first so nobody loses anything, then narrow it and extend it deliberately. Two small pieces of access hygiene are the exception and do happen while the records are built, because neither depends on the open-versus-private choice: the records get real owners instead of the single placeholder that holds most of them today, and the inbound job-board door is rebuilt as a controlled entry. Everything else — the country field, the roles, the groups, the rules, and the per-record privatisation — is the post-go-live stage.

The dependency is clear: the doctrine and the per-record design can start early, but when the tightening and the HR onboarding land is a single business decision — after the switch by default, or at the switch if the HR need is immediate — and it must be owned and dated so that 'later' does not quietly become 'never'.

How it fits together

This project provides the integration layer for the systems that need orchestration — transforming, routing and combining data between Salesforce and external systems. MuleSoft is confirmed as the middleware (the analysis and the selection are done, made on a MuleSoft vendor demo rather than a Marlex-run proof of concept), the commercial terms are agreed, and the working environment becomes available in September 2026. The architecture is API-led, and the layer is run by Marlex IT with partner support. Not every external system is routed through it: systems that only need a straightforward, secure link — for example reporting or monitoring tools connecting over a Connected App with secure authentication — connect directly to Salesforce. MuleSoft is the layer for the integrations that genuinely need orchestration, not a mandatory gateway for everything.

The objective underneath it is control. Every integration sits behind an interface Marlex owns, so that where it points — at the recruitment data being retired or at the new model that replaces it, at one Salesforce environment or another — is a change made in configuration rather than a Salesforce release. That is what makes the rebuild's switch-over controllable, and it is what sets the order of the work. The rebuild does not arrive in one moment: the capabilities that can be separated from the shared candidate record move first — interviews, then the talent pool, then placements — and the tightly-coupled core of candidates, vacancies and applications crosses last. So each integration is scheduled against the stage that first moves the data it reads, which means several small integrations fall due before the large ones.

One rule keeps this work off the product owners' waiting list. Moving an integration so that it runs through the layer Marlex owns, without changing what it does, is a change of transport rather than a change of process: the same data moves between the same two systems for the same reason, and nobody's day-to-day work changes. Work of that kind needs no process decision and does not wait for one — the integration is routed exactly as it runs today. The layer then becomes the place where a future process change is made, and cheaply, because the connection point already exists. Designing something genuinely new is the different case, and that does wait for the business to confirm what it wants.

The organising principle is lanes: cross-cutting foundations first, then one lane per external system, so that a slow or blocked integration never holds up the rest. It opens with two foundational pieces — confirming the platform and licensing plus the cross-cutting groundwork (the API-led architecture, the canonical contract drafts, a reusable authentication pattern), and provisioning the middleware itself (the API gateway, the environments, Salesforce connectivity, and the re-authentication approach reusable per org).

The per-system lanes are then ordered by the rebuild stage that moves the data each one touches, with business priority as the tie-break inside a stage. The NET4 finance lane can start without waiting because it is the risk-heavy near-term flow, and anchoring it on the shared data model lets its contracts survive the recruitment cutover; it is reused by Axxon's NET4 lane. The job-board lane (InfoJobs) comes before portals because it exists today whereas the portals do not. The portals lane builds only the connection — the portal front-end itself is out of programme. LinkedIn is a special case: the rebuild loses the recruitment vendor's built-in LinkedIn connection, so Marlex must become a certified LinkedIn partner before the middleware can carry that traffic.

A cross-cutting lane holds the integration work not tied to one system: deciding what to do with the small carried-over integrations, retiring the temporary direct connections once the middleware is live, keeping the register of integration assets, and the process for onboarding a new region's integrations. It also produces the coverage map that reconciles every external system to a lane, proving nothing was missed.

The key relationship with the rebuild is the swappable-connection pattern: each integration ships behind an interface Marlex owns, with a simple direct connection available behind it, and a setting swaps in the MuleSoft version without a redeployment. For most integrations that means the layer is added in its own time and does not hold up the rebuild. The finance-system and job-board lanes are the deliberate exceptions: both are coupled to the data being retired, so the integration layer is where their switch from the old model to the new one is made — the outside system keeps calling one unchanged address while the target moves underneath it. Both are therefore built before the stage that moves their data, each keeping its direct connection as a tested fallback. Rebuilding an integration the way it already runs is treated the same way — live production traffic is reason enough to proceed.

The coupled set is wider than those two lanes, though, and that is the part most easily missed. The training-certificate exchange reads the vacancy and the placement records, so it is pulled forward by the placement stage. The sourcing connector lands profiles against the talent pool and is pulled forward too, carrying an unresolved question about whether its supplier or Marlex controls the change. The analytics extract reads records split across both stages, so it either re-points twice or once late — a choice still to be made.

Two rules govern the overlap, and they differ in kind. During the early stages an integration may read the retiring recruitment data and the new model at the same time, because while a stage is in flight both hold live data — a design requirement, not a workaround. At the final switch-over none may read or write any of the retiring product's data at all. An integration may also go live while still reading the retiring data: the interface published to the outside system does not change, so a second implementation behind it reads the new records later, chosen by configuration.

The trade this accepts is that the integration work is paced by the rebuild rather than by its own plan. No stage carries a committed date and none is being set — the work starts now and each stage lands when the team on it finishes, with the intent of finishing early. The practical consequence is that an early-stage integration may fall due before the middleware environment is available in September 2026, which is why the direct connections behind each interface are load-bearing rather than merely a fallback.

Project PORTALThe candidate & recruiter portals

The candidate and recruiter portals — the web front-ends that live today on the platform the programme is retiring. The Salesforce programme owns the connection to them, not the portals themselves; the build sits with an external partner, and its scope, owner and — above all — its timing against the platform switchover are still open.

What this track is

Marlex runs public-facing portals for candidates and recruiters. Today these portals are hosted on the recruitment platform that the rebuild replaces, so they cannot simply carry over untouched — when that platform is retired, whatever it was hosting goes with it. This makes the portals a distinct piece of work with its own owner and its own timing, not a detail inside the rebuild.

The division of labour is settled: the Salesforce programme owns the connection — the integration layer and the Salesforce-side that feed a portal with data and receive what a candidate or recruiter submits. It does not own the portals as products. Building the portals themselves is an external partner's job, on a front-end platform outside this programme. So this page tracks a track the programme depends on but does not itself deliver — which is exactly why its decisions need to be visible in one place.

Two things about the portals are still genuinely open. First, their shape: whether they are Spain-only or serve the wider group, and whether every country gets the same portal or a version tailored to local needs. Second — and this is the decision that drives the plan — when the new portals need to be built and operational relative to the platform switchover. That timing question is set out on its own below, because it is not yet decided and it changes the critical path either way.

When do the new portals have to be live?

The current portals disappear when the old platform is switched off. The new portals, built by the partner on the connection this programme provides, have to appear on the other side. The open question is how those two events line up — and it is a real choice, not a formality, because each option trades continuity against time and risk. This is the decision to close before the plan can commit a portal date.
Built and live before the switchover

The new portals are finished and operational first, then the platform switchover happens with the portals already in place. Candidates and recruiters see no interruption. The cost is that the portal build joins the critical path ahead of go-live: the switchover cannot happen until the partner has delivered, so a slip on the portals becomes a slip on the whole cutover.

Switched over at the same time

The portal switch happens inside the same cutover window as the platform switch — the old portals go dark and the new ones come up together. There is no separate portal go-live to schedule, but the window is tighter and carries more at once, so it needs the partner's delivery and the programme's cutover to be tightly synchronised.

Built and live after the switchover

The platform switches over first and the new portals follow later. This keeps the platform cutover simple and off the portal partner's timeline, but it accepts a gap: for a period after go-live there is no portal, or only a stop-gap, so candidate- and recruiter-facing self-service is interrupted until the partner delivers.

Open — No option is ratified yet, but the choice is leaning. On 2026-07-23 the product side signalled that the portal is not critical on day one and can follow the switchover — a short period without the rebuilt portal is acceptable to the business ('we can wait'), which points toward the built-and-live-after option. Treat that as a lean, not a decision: the portal's owner, the partner's schedule, and whether it serves Spain alone or the wider group are all still open, and the option needs product-owner sign-off to close. The choice still depends on when the partner can deliver, how much portal downtime the business will accept, and how much the programme is willing to add to the cutover's critical path. Once it is made, the roadmap gains a portal milestone and the critical chain may change with it.

Ways of workingHow specifications are defined

Before anything is built, each change is first analysed and given a clear decision — keep it, drop it, or reshape it — against the way the business wants to work, not against how today's tool happens to do it. Only then does it move on to be built and released.

Two boards, two jobs. Nothing reaches the build board until it has been analysed and its specification accepted — a board item is first “something to analyse”, not “something to build”.

Two stages, kept separate: decide, then build

The work runs through two distinct stages, each with its own owner. The first is an analysis stage, owned by the product side: every item from the functional inventory — and the parts of today's tool that only exist as vendor functionality with nothing to inspect — is walked through and given a disposition. Keep it as it is, drop it, or merge it into something else. The output of that stage is an agreed specification.

The second stage is build and release, owned by the delivery team: an accepted specification is taken through build, testing, business validation and go-live. The two are deliberately not merged into one queue — the mistake to avoid is letting a not-yet-analysed idea drop straight onto the build list. Something on the board is first 'something to analyse', and only becomes 'something to build' once the analysis is done.

The yardstick: fill vacancies faster

Every decision is measured against a single business objective — put the right candidate into the vacancy as quickly and cost-effectively as possible, and cover more vacancies faster. A change earns its place only if it moves that objective; otherwise it is dropped rather than rebuilt out of habit.

Recruitment is treated as a process with two kinds of step. The hygienic steps — data entry, generating reports, enrolments, parsing CVs — are pure friction and should be automated away. The human steps — the relationship with the candidate and the client, the judgement of fit — are the real value and must not be automated. The objective is also the filter that stops the target design inflating: an improvement that does not speed up filling vacancies is not an improvement, it is scope creep.

Current-state as a checklist, target-state as the lens

Each item is decided by walking the current way of working and judging every piece against the target way of working. The current state is not what gets rebuilt — it is the coverage checklist that stops anything being silently forgotten. The target state is not invented freely — it is the lens each 'does this still make sense?' decision is made against.

Rebuilding a piece unchanged should be the exception that has to justify itself, not the default. If something is kept as-is, that must be a conscious 'it still fits' decision, recorded as such — not inertia. The target process is captured once at the level of a whole capability, so the individual decisions stay coherent with it rather than becoming a patchwork.

What a specification captures

Work is described in units the business would recognise — a capability, not one entry per underlying technical component (mirroring the components one-for-one would produce thousands of meaningless items). Each specification captures four things: the information involved, the rules and automations behind it, the screens and behaviour people see, and — above all — the what and the why. The why is what stops the right thing being built the wrong way, or the wrong thing being built well.

The how — the technical design — is a separate step, taken only after the what and why are accepted. The business owns the outcome; the technical team owns the design that meets it. They are separated by a gate, not filled in on one form by everyone at once.

Toward a living, visual catalogue

Today the picture of how the business works lives largely in a few people's heads, and new joiners learn by trial and error. The ambition is a living, visual catalogue of the end-to-end processes — current and target — kept current by the way of working rather than by a manual refresh, and clear enough to onboard from.

2.1 · The target: cut every change from production

This is the target, not today’s practice. It applies from the moment the reset in 2.3 has been done. Until then, follow 2.2.

Every change starts as a branch cut from production, so it always begins from the latest live version of the components it touches. The same branch is then promoted into each environment in turn — the development line, then the pre-production line where the mandatory review happens, then back into production as the release. Promoting the change itself, rather than merging one environment into the next, is what keeps each change independent: two changes in flight can go live in either order.

When several features must ship together

Sometimes a set of features has to go live as one deployment. For that, cut a release branch from production and collect the features there for a single deploy. The rule that must not bend: the pull request and the review stay at the feature level — each feature is reviewed on its own, never as a bundle. Grouping is for the deployment, not the review, so any one feature can still be dropped from the bundle without holding up the others.

2.2 · Today: the gap, and the branches it forces

A single pull request made the problem visible: it reported roughly 120 components as brand-new when about 17 already existed in production. It was not describing real work — it was describing the gap between the branch and reality. Three layers had stacked up: a branch no longer matched its own environment, the lower environments lagged production, and work built directly in an environment was pushed down into the branch. With a wrong baseline, review is impossible, automated checks have nothing trustworthy to compare against, and a rollback cannot know the “before” state.

The lines last agreed on 21 May 2026, but the figure that matters is the overlap — the same component changed on both sides — and that is around 160 components, not the thousands a raw comparison suggests. About half of it is configuration built through the screens, which is what makes it delicate rather than merely large.

One further finding limits how far the history can be trusted: where the same change reached both lines, it was almost always re-done by hand rather than copied. The two versions match in content while version control still treats them as unrelated — presenting them as new work, and later as conflicts. Reconciliation must be based on what the environments actually contain, not on what the branch history appears to say.

A clean merge is not evidence of a correct merge. If a change reached production and was later undone on the pre-production line, version control cannot see the two as versions of one thing — so bringing the lines together raises nothing and the undone version survives. No conflict, no marker, nothing for a reviewer to catch. Hence: deploy and test the combined result, and apply an undo to both lines or record it as a deliberate difference.

Promoting a change while the gap exists

The target model assumes the pre-production line already reflects production. While it does not, where the branch is cut from only decides which promotion pays for the gap — one drowns the review, the other ships more than was agreed.

So while the gap exists, a change is carried on one branch per environment it passes through, each cut from the line it merges into: on the full path that is three — integration, pre-production, release — and on the short path two, because the delivery partner does not use the integration line. That cost per change is the reason the reset in 2.3 is worth doing rather than living with.

The development itself still happens on a branch cut from production, whichever path is in use. That branch is what guarantees the change starts from the live version of everything it touches — but while the gap exists it is never merged into anything, because merging it would drag the whole gap along with it. It ends its life as a working branch, and its commits are copied onto each environment’s branch instead — only the ones that genuinely belong to the feature.

Pass two is the same manifest with <members>*</members>, retrieved to a scratch directory outside the package directories and deleted afterwards — it is diagnostic only.

The second source (step 2). Use a different API from the first, not the same query twice: the Metadata API listing and a query against the platform’s own definition objects disagree on totals, and that is expected — what matters is that both agree on the specific component. A component absent from one and present in the other is not a deletion candidate. Types whose whole category cannot be listed must be skipped rather than treated as empty, or every component of that type looks deletable.

Why step 6 is a step at all: deletion has to be asked for by name — an ordinary deployment will not action it, so the component survives and the reset never quite finishes. And there are three cases here, not two: production holds the right version, the lower environment does, or neither holds the component at all and it survives only in version control — invisible to a capture, which only ever adds and updates. Confirm against both environments before deciding.

For the developers

Deletions go in a destructiveChanges.xml alongside the package manifest, and a validation-only deploy of it is the reliable existence probe: if a component is not in the org, the validation says so by name, while nothing is removed. Run it with --dry-run and --target-org pointed at each side in turn.

Do not trust listMetadata for this. It does not report Custom Metadata records or Custom Settings correctly, so a component can be absent from its output and present in the org — which is exactly how metadata surviving only in version control gets mistaken for a deletion that already happened. The destructive-changes validation is the check that answers it.

On step 7, validate the combined result the same way before the real deploy and read the component count back. If it is far larger than what was authored, the scope is wrong — stop rather than deploy.

Why step 8 is a step at all: join the lines even when the result changes not one file — keep the contents already standing and let the record of the meeting be all the step produces. Two checks confirm it took: production sits in the branch’s own history, and a trial combination of a feature branch raises nothing.

For the developers

The point being moved is the merge base. Where the target branch already holds the content you want, join the histories without touching the tree: git merge -s ours production — it records the merge commit and keeps the current side’s tree verbatim. Do not confuse it with -X ours, which resolves conflicts file-by-file inside a real merge and does change the result.

The two checks:

  • git merge-base --is-ancestor production sandbox-pre — exits 0 once production is an ancestor. That is the assertion, and it belongs in the pipeline, not in someone’s memory.
  • git merge --no-commit --no-ff feature/x on a throwaway copy, then git merge --abort — a feature branch must now merge with no conflicts. If it still reports hundreds, the join did not take.

What step 5 preserves: four kinds, plus people. Step 5 keeps five categories of setting in the lower environment rather than carrying production’s version down.

  • Connection settings — the stored definitions of how the org reaches another system, and any configuration record holding an address or a target. Carry production’s version down and the lower environment starts calling the live systems, then writing test data into them. The measured case on this programme is TargetRecruit, which stores production record identifiers inside its own configuration records: re-pointing them is most of the reset’s two days, and it repeats every time an environment is copied or realigned.
  • Secrets and certificates — a capture never returns the secret itself, so what arrives in the branch is a setting with an empty secret. Leave the environment’s own in place.
  • Application registrations — an external application signs in with a key and a return address, and both can differ per environment.
  • Switches that turn things on — anything enabling email, notifications or automatic exchanges with another system.
  • References to particular people — the easiest to miss, because both routes carry it: the user a dashboard or report runs as, record owners, queue and group membership, and rules that show or hide part of a screen depending on who is looking. A refresh makes it obvious, since accounts arrive disabled. A back-promotion is quieter — it copies no people, but it still carries down configuration that names them. Preserve or re-point those references either way.
The test is what the value holds, not what kind of component it is. If it points at a system, an identifier or a particular person, or it switches something on, the lower environment keeps its own version. If it is a rule, a mapping, a business threshold or anything else functional, it aligns with production. So a category of configuration is not frozen wholesale — only the part of it that describes the environment. Everything else — code, automations, objects, screen layouts, access rights — aligns with production as normal.

So the name is not the test. Two configuration records can sit side by side under the same naming, one holding an address that differs per environment and the next differing only by the platform version it was written against — and the second aligns with production like anything else functional. Open the value.

The reset is what retires the extra branches. Once the pre-production line reflects production, one branch cut from production merges cleanly into both and one review covers it. That is the test of whether the reset worked — and the point to drop the temporary arrangement rather than keep it out of habit.

One case inside step 4 deserves naming. On a few components version control does not choose a side at all — it stitches both versions into one file, taking some lines from each. Sometimes joining both edits is exactly right; sometimes it produces a file that is valid, deployable and wrong. Those need reading one at a time, whichever side the record says should win.

For the developers

Cut from the target and combine production in, then impose the recorded decision on every differing path rather than only the conflicted ones:

  • git checkout -b backpromotion/prod-to-pre origin/sandbox-pre then git merge origin/production
  • production’s version → git checkout origin/production -- <path>; the environment’s → git checkout origin/sandbox-pre -- <path>; where the winning side no longer has the file, git rm
  • list the differing set with git diff --name-only origin/production origin/sandbox-pre — that, not the conflict list, is the worklist

Two traps measured here. Rename detection pairs byte-identical files that have nothing to do with each other — it silently dropped eighteen .cls-meta.xml companions and moved four fields to a different object. Assert every .cls has its .cls-meta.xml before opening the request. And a batch git checkout fails on paths containing accented characters, so those files go missing without an error; the merge itself handles them, so prefer it over scripted checkouts where you can.

3 · Roles and rules

A Release Manager in the in-house IT team groups changes into releases and coordinates deployments. Everything below holds whichever of the two processes is in force.

  • No partner releases to production without an in-house review. Nobody approves their own change. The release itself needs no second review — it is a handover, not a fresh change. This rule is settled.
  • One owner per complex shared component. Components built through the Salesforce screens — Flows, layouts, screen configurations — cannot be safely combined afterwards, so two changes touching the same Flow are never independent however their branches are arranged. One person makes or coordinates those changes.
  • Evolutions share a development environment; only genuinely new work gets an isolated one. Clashes are then resolved together on screen rather than reconciled at promotion time.
  • Deploy the merged result, never the branch. The merge may not surface every clash, so the deployment and tests must exercise the combination.
  • Check for overlap before raising a request, and document any dependency between changes up front rather than leaving it in a verbal “wait for my OK”.

Three settings, each needing an owner

  • Stop access rights combining on their own. Twenty-two profile and permission-set files changed on both lines; six combine silently, the administrator profile among them, granting access nobody chose. Mark these types so a person must always decide.
  • Allow only a true combination when a request is completed, on the production and pre-production branches. The alternatives leave the branches looking apart, so the same decisions get made twice.
  • Let version control remember resolutions, so the same clashes are not re-resolved by hand on every promotion. Switch it on before the reset.

Automation comes in stages: stage one is pull requests and the mandatory review; stage two adds automated checks on each request; stage three, only if volume justifies it, a dedicated deployment platform.

Data-access seam during coexistence — repository confinement, not full ACL

ADR · Data-Access Seam during Coexistence Proposed
Epic ATS-RB · Canonical Model·Solution

During the months the new native system runs alongside TargetRecruit, rebuilt code still has to read and write the old package's objects. This decision sets how: code that touches the package splits into two kinds, treated in opposite ways. Throwaway bridge code — dual-writes and syncs whose only job is to keep the package fed until switch-off — is written directly, kept cheap, and deleted at cutover. Surviving logic — the controllers and services that read jobs, applications and candidate data today and will keep doing so afterwards — has all of its old-package queries penned into one small repository class per business entity, so at cutover that single class is re-pointed at the native object and the business logic above it never moves.

The rebuild once planned for two recruitment vendors sitting behind one shared, vendor-neutral model, which justified a full translation layer at every seam. The programme then chose a single custom build, and the new model became the neutral model. With no second vendor to translate to, a translation layer on a natively-owned entity would map a record to an identical copy of itself — ceremony for no gain. The seam still needs discipline; it no longer needs the ceremony.

A full translation layer everywhere was rejected because, under one model, the native-side translation is an identity map — extra classes, indirection and test surface for zero portability. Direct package access scattered through the logic was rejected because it turns cutover into a rewrite inside the very code that must not move on the switch-off weekend. The two-kinds rule was chosen because it matches the treatment to the code's lifespan: throwaway code stays cheap, surviving logic pays one small confinement cost and collects the whole payoff at cutover as a one-line re-point.

The decisive factor is that what makes cutover cheap is confinement, not abstraction: one named place per entity for the package's queries means cutover edits that place and stops. The cost accepted is honest — each seam must be tagged correctly, and a bridge mistaken for surviving logic (or the reverse) is coupling debt. A separate, unavoidable item is schema coupling: the lookup fields on new objects that point at package objects cannot be hidden by any code pattern and are re-pointed at cutover as a new field plus data migration, tracked as model work rather than code work. The coupled-code metric is restated as two action lists — delete at cutover, re-point at cutover — so it reads as a runbook.

For developers, the surviving-logic classes are named after the entity with a Repository suffix and deliberately carry no ACL prefix, keeping them visually distinct from the full translation-layer components that are now reserved for a genuine second vendor only. A repository holds the package SOQL and DML and returns platform records and fields — no wrapper types, no mappers. This is the Selector/Repository pattern used for its intended purpose: isolate the query, not translate the schema.

Ownership boundary doctrine — governance, naming convention, and business-logic decoupling

ADR · Ownership-Boundary Doctrine Proposed
Epic ATS-RB · Foundation — Design Decisions & Requirements·Governance + Solution

This decision establishes the ownership boundary as the governance unit: a line that defines who has autonomous change rights over a set of components and who must approve changes that cross it. A component belongs to exactly one boundary — brand and product together (the commercial platform, the recruitment platform, the back-office platform, for Marlex and for Axxon). No component in one boundary reads another boundary's data directly; cross-boundary access goes through a documented service interface, and the canonical model is the one layer every boundary may share. Marlex-shared components are owned by the Centre of Excellence and inherited as-is by all regions; a region may hold its own override, and a shared component must never depend on a regional override.

The Marlex Spain org was built Spain-only. As the programme moves to a shared org that becomes the template for other countries and that Axxon adapts referentially, the codebase must structurally enforce who owns what. Without this, cross-boundary object access, division-hardcoded logic, and dozens of near-duplicate division-specific process copies would propagate into every derived org. The 2026-05-21 coupling analysis confirmed product separation is emergent, not enforced, and that both vertical and region logic are hardcoded.

The boundary was set by brand and product because that maps to how ownership actually works at Marlex — the Centre of Excellence owns the shared components and each country's product team owns its own — whereas splitting by vertical or division was rejected, since no team is organised that way. Vertical variation is therefore configuration, carried by metadata records rather than by separate components, collapsing the hardcoded per-division logic and the near-duplicate division processes into a single configurable pattern with a routing table.

On naming, the settled rule (2026-07-23) is that new native components use a plain English API name with no owner prefix. An owner marker stamped on almost every component partitions nothing — the old org already shows this, where the historical Marlex prefix sits on the large majority of fields and no longer signals anything — and true cross-org ownership, when a component is promoted to another Marlex Group org, is carried by the platform's packaging namespace applied automatically, which makes a hand-typed prefix redundant. A shared group prefix is added to a component only when the Centre of Excellence confirms genuine group-wide scope, as a deliberate choice rather than a default. Existing production objects that already carry the historical prefix or Spanish names are not retro-renamed; a carried-over field keeps its prefix only to avoid breaking live dependencies. What endures from the original scheme is the governance content — who owns a component and what it may depend on — enforced now by folder organisation, documentation, and pull-request review rather than by a mandatory prefix on every name.

The doctrine is topology-independent. It holds unchanged whether regions live as overrides inside one shared Marlex org or as brand-orgs (Axxon and the Philippines) that run their own orgs and consume the standard referentially — only where a component physically lives differs. Under the native rebuild the ownership boundary and the cross-boundary coupling rules survive intact; the earlier requirement to wall the recruitment platform off behind a mandatory product prefix relaxes, because once the vendor package is gone there are no vendor objects left to isolate at the naming layer.

Capability classification and promotion model (scope ladder)

ADR · Package-free Deployment & Manifests Accepted

Dependency management (governance-driven, package-free)

ADR · Dependency Management Accepted
Epic ATS-RB · Foundation — Design Decisions & Requirements·Technical

Dependencies are managed through governance, manifests, and the deployment pipeline: understand relationships, define deployment order, validate deployability, and prevent uncontrolled cross-dependencies. A future move to unlocked packages is a change of deployment mechanism, not the moment modular architecture begins. The core rule is that a group-wide shared component depends on nothing org-local or country-specific; the reverse is allowed.

Going package-free avoids the mechanics of packaging but not the architectural work that packaging would otherwise force.

Doing the dependency work by governance from day one enforces modular discipline regardless of mechanism, rather than deferring dependency management until packaging (the dependencies already exist) or adopting packages now for enforcement (which the package-free deployment decision defers).

The cost is that governed tracking is weaker than package-enforced tracking and depends on the governance catalogue and review (mitigated by the governance catalogue). The payoff is modular discipline from the start.

Enforcement model and governance catalogue

ADR · Enforcement Model & Governance Catalogue Accepted
Epic ATS-RB · Foundation — Design Decisions & Requirements·Technical

Enforcement is governance: code review (a purely Marlex release must not touch a group-wide shared component), release-process validation, and Centre of Excellence ownership and arbitration. A governance catalogue is mandatory from the start, with one row per component or group recording repository/scope, owner, functional area, Salesforce layer, dependencies, consuming orgs, and configuration dimensions. The pipeline overwriting local edits is a reactive aid, not enforcement.

Without packaging there is no platform-level "do not touch", and the naming prefix enforces nothing on its own.

Governance-based enforcement works without packaging and is auditable, and the catalogue is the source of truth precisely because prefixes are optional, rather than trusting the prefix (which enforces nothing) or adopting managed packages for a platform lock (which the package-free deployment decision defers, to be revisited only if review proves insufficient).

The cost is that it depends on a human process and the catalogue can go stale (mitigated by updating the row on every pull request). The payoff is enforcement that works without packaging and stays auditable.

Component scope strategy: Group-first vs Local-first and the promotion/downgrade cycle

ADR · Component-Scope Strategy (Group vs Local) Proposed
Epic ATS-RB · Foundation — Design Decisions & Requirements·Solution

The programme designs local-first: everything is born a Marlex Standard component (config-driven) in its owning brand and rises to a group-wide shared component (cross-brand) only under the proven-reuse gate defined in the capability scope ladder. Only a small technical and governance core is born group-shared (frameworks, the canonical and common-integration model, logging and error handling, the anti-corruption-layer pattern, configuration schemas, governance); the sharing and security layer and functional components are not. A downgrade process is added, along with a cost model that explains why the default works.

Marlex is multi-brand (Marlex Spain, Italy, and Portugal plus the Axxon and Philippines brand-orgs consuming referentially), with no external deadline forcing components up to group-wide. The capability scope ladder set the tiers and the Marlex Standard default but never modelled the cost or defined the reverse process. Orgs split by brand, not region, so the real axis is the breadth of reuse on the ladder.

Local-first was chosen over group-first (born cross-brand) because of the downgrade risk, and this decision quantifies why: promotion is additive and gated, while downgrade is subtractive across every consumer that holds a "group-owned" contract, plus the sunk standardisation cost. That asymmetry justifies the conservative default.

The cost is a duplication risk if nothing is promoted, an expensive downgrade path (the very cost the default avoids), and dependence on a human process and a Centre of Excellence whose members are not yet confirmed. The payoff is no premature globalisation, a complete up-and-down cycle, an explicit safeguard against a Spain-default bias, and brand divergence absorbed without forced refactoring.

Data Cloud (Data 360) and Marketing Cloud Next architecture

ADR · Data Cloud & Marketing Cloud Architecture Draft
Epic MKT · Marketing Cloud — Wave A·Solution

The draft direction captures the Marketing Cloud Wave B target architecture for ratification: a home Data Cloud in the Spain org pinned to the EU Operating Zone (Hyperforce EU), a hub-and-spoke topology via Data Cloud One and Companion Connections with Spain as home plus one companion (Axxon), Spain, Italy, and Portugal as Data Spaces inside the home and the Philippines out of scope for now, a Consent Data Model per space, identity resolution over Individual, Data Kit for the software development lifecycle, and Data Cloud as the group's cross-org reporting layer. The positions are illustrative, pending ratification.

The Marketing Cloud sequencing decision (closed 2026-05-13) decided only the sequencing into two waves (finite campaigns in TargetRecruit first, rebuilt after cutover). The roughly ten target-architecture decisions in the considerations document are not yet ratified, and that document predates both the sequencing decision and the decision to put the Philippines out of scope, so its topology and licensing are outdated.

This topology was chosen over one Data Cloud per org (which breaks consolidated reporting), Marketing Cloud Engagement/Pardot (rejected in favour of Marketing Cloud Next), and deferring all architecture to build (GDPR rework risk). The reasoning is that residency, consent, and identity resolution are GDPR-load-bearing and hard to reverse after ingestion, and the topology is the answer to cross-org reporting.

The cost is unquantified companion and credits licensing, an open edition choice (Growth versus Advanced), and obsolete figures in the considerations document (to be recomputed without the Philippines). The payoff is a GDPR-correct home and consent, one profile per person across brands, and cross-org reporting via the companion.

Under the custom-native rebuild the home Data Cloud moves from the Spain packaged org to the Spain custom-native org (the same in-place org); the hub-and-spoke topology is unchanged. The rebuild is a source-connector change for Spain, not a change to the Data Cloud model: the candidate stays a standard Contact record, so identity resolution and the consent model are untouched, and only the recruitment-activity data streams (jobs, applications, placements, interviews) re-point onto the rebuilt object names at cutover. Because of this split, the person and consent layer can be built now, independent of the rebuild, while the activity streams follow the cutover — and any marketing flow built now on recruitment-activity data carries a re-point at cutover, which belongs on the cutover plan.

AI-assistant data governance (MarlexOne / Groq) and data residency

ADR · AI-Assistant Data Governance Draft
Governance

The draft direction treats the MarlexOne AI assistant as a compliance gate before cutover: confirm what data leaves and where (Groq in the US); then either remediate (a data-processing agreement plus standard contractual clauses plus data minimisation plus an EU LLM region or EU provider), retire the feature, or formally risk-accept with legal sign-off. The flow is not carried forward as-is without one of the three. It also defines the residency policy for future AI features, aligned to the EU home Data Cloud.

The functional inventory flags the MarlexOne AI assistant for data-governance review: business data (potentially personal, EU) may be sent to a US-hosted LLM, and the data-processing basis for that transfer needs to be confirmed. The programme treats this flow as one to review and remediate before it is carried forward, and it is a possible legal gate before cutover.

Gating the feature was chosen over carrying it forward as-is (unresolved GDPR question), retiring it (losing the AI capability), remediating with an EU provider/region and a data-processing agreement (rework cost), or risk-accepting with legal sign-off. The reasoning is that an EU personal-data flow to a US-hosted LLM needs a confirmed data-processing basis, cheap to decide now but costly if carried into the new org and propagated to Axxon and the Philippines.

The cost is that it needs legal input (data-processing agreement, legal basis), remediation may delay or re-cost the feature, and it depends on EU AI provider alternatives. The payoff is closing an open GDPR question, setting a reusable AI residency policy, and a cheap decision made before cutover.

Target-state reporting and BI strategy — native SF plus Data Cloud plus external Power BI

ADR · Reporting & BI Target-State Draft
Solution

The draft direction defines three reporting layers: native Salesforce reports and dashboards for in-org operational reporting, respecting the per-country sharing model; Data Cloud Companion as the group's consolidated cross-brand and cross-region reporting layer; and external Power BI kept outside Salesforce as corporate business intelligence, not moved. The programme inventories current reports and decides which move to native Salesforce, get rebuilt, or are retired, treating reporting as its own wave.

The programme has no target-state reporting decision. The facts are that Spain's roughly seven-million-row Power BI table is external to Salesforce and out of scope for the data move, Data Cloud Companion is the group's cross-org reporting layer, and reporting has no epic of its own, appearing only as a "reports respect scope" item in the data-dependent activation wave.

Three defined layers were chosen over all-reporting-in-Salesforce (ignores corporate Power BI), all-in-external-Power BI (underuses Data Cloud), or not deciding (reporting lost at cutover). The reasoning is that without an explicit strategy, reporting is either lost in the cutover or rebuilt ad hoc, and the three planes have distinct owners and mechanisms.

The cost is that it requires a current reports inventory (which does not exist), coordinates three tools and owners, and carries the Data Cloud Companion cost. The payoff is reporting that survives the cutover, clear boundaries between Salesforce, Data Cloud, and Power BI, and respect for per-country sharing.

Field-level security in rebuild code — enforced where a person acts, explicit where automation writes

ADR · Field-Security Enforcement by Execution Context Proposed
Epic ATS-RB · Native Build·Technical

Salesforce code runs with security checks switched off unless the developer switches them on, and the setting that governs which records a user can reach is a different setting from the one that governs which fields they can open. A read of the live platform found that of the code Marlex owns, roughly a third touches the objects being rebuilt, and only one class checks field access at all.

The rule now depends on who is acting. Where a person clicks something — a screen, a button, an action they trigger — the code checks that person's field and object access and respects it. Where the platform writes on its own — automation that fires on save, scheduled jobs, and the doors that inbound feeds arrive through — the code keeps writing without those checks, and says so in a comment explaining why.

That split is not a compromise, it is what the evidence supports. Testing every user's real field access against the fields each piece of code writes, across the three busiest objects, found no case where switching the checks on in the screens would take away something a user can do today. It also found the opposite risk is real: a handful of fields are written only by automation and appear in no user's access at all, so switching checks on there would break the write.

One narrow exception is allowed and was already being used correctly: where a tool is reachable only by holding a specific access grant, that grant can be the control, and the code records which grant it relies on.

SecurityMaintainabilityCorrectness
Still open: Extend the field-access evidence to the remaining objects in scope; this can add exceptions to the list but does not change the rule. Owner: the architecture team, before the first change that touches those objects.

Access grants that add nothing are not rebuilt — the test is what a user can actually do

ADR · Empty Access Grants Are Not Rebuilt Proposed
Epic ATS-RB · Native Build·Technical

The plan for moving users onto the new objects was to copy every existing access grant one for one, so that nothing could be missed. Measuring what those grants actually deliver showed that copying them literally would carry across empty containers.

One grant covering four placement fields is held by thirty people. The base access their role already carries makes all four fields editable, so for twenty-four of the thirty the grant delivers nothing. Comparing what a holder can do against what a non-holder with the same base access can do returns an identical result across every field on the object.

So the test changes from what a grant says to what a user can actually do. A grant is rebuilt only where it adds something on top of the access its holders already have, measured per holder. Where it adds nothing, it is not rebuilt, and the measurement that showed so is recorded rather than the grant being quietly dropped. Where it adds something for only some of its holders, it is rebuilt for those people alone.

This is deliberately not a redesign. Real differences are still copied faithfully — including the ones that are easy to round off, such as the core recruitment population being able to create and edit jobs and the talent pool but not delete them. The only thing discarded is what is demonstrably empty.

MaintainabilitySecurityOperability
Still open: Apply the same test to the remaining cross-cutting grants, including the near-universal candidature field filter and a personnel-integration grant held by several hundred users that opens an object without opening any field on it. Owner: the architecture team, during the extension to the remaining objects.

Business rules live on the record, not on the screen

ADR · Business Rules Live on the Record Proposed
Epic ATS-RB · Foundation — Infrastructure & Governance·Architecture (build standard)

A rule that protects a process only governs the people who arrive through the door it was written on. Salesforce record pages let a rule be attached to the screen itself: show this button only once the record is approved, reveal this section only in that state. That is a reasonable way to build when the screen is the only way in.

Reading the current system shows where those rules were written. The record pages carry a large number of small conditions that decide whether something appears. Most are ordinary housekeeping: they hide a field or a section that is not relevant yet, which is exactly what a screen is for. A meaningful minority are different. They decide whether a button appears, and the button is how work moves forward.

The clearest case is an offer. Sending it for signature, accepting it, making it current, marking it expired: each is a button, and each button is shown or hidden by a condition on the offer's state and its approval. The offer does carry rules of its own, so this is not an unguarded record. But those rules freeze the price and the margin after an offer is approved, and require a bank account before it becomes current. None of them stops an unapproved offer being sent for signature. That protection exists only as a hidden button.

The screens are no longer the only way in. Applications already arrive from the careers landing pages and the job boards over a direct connection, the payroll and staffing systems exchange records through the integration layer, and the data migration itself writes millions of records without a screen ever opening. None of those are subject to a condition that exists only on a page.

So the placement of a rule is now decided by what kind of rule it is. Anything that protects the integrity of a process — what must be filled in, which state may follow which, what needs approval before it moves, what may no longer change once closed — is written onto the record, where it applies to a person, an integration and a data load alike. Anything the business calculates and others rely on is derived on the record too. What genuinely belongs on the screen stays there: showing the right fields at the right moment, hiding what is irrelevant, guiding the person through the work. A screen may repeat a rule to make the experience better; what it may not do is be the only place the rule exists.

Assembling pages from the platform's own building blocks remains the right way to build them — that is settled separately and is not reopened here. The change is narrower: the page presents the rule, it no longer holds it.

The rule binds new work at full strength from the moment it is accepted. Rules carried over from the current system as each capability is rebuilt are recorded as work still to do rather than treated as defects, because deciding what to do with the existing rules is a question of effort and sequence that has not been costed yet. Recording them is what makes that cost visible.

CorrectnessInteroperabilityGovernability
Still open: Size the carried-over rules, grouped by the record they sit on, separating those that collapse into a single shared rule from those needing to be moved one at a time. That figure decides whether the work travels with each rebuilt capability at little extra cost or needs a place of its own in the plan. Owner: the architecture team. Also open: how the historical data move satisfies the new rules or is granted a documented, time-limited exception; and whether a screen condition may ever stand alone when the concern is confidentiality rather than integrity — the starting position is that confidentiality is governed by the access model instead. Owner: the architecture team, with the build team on the data move.

Rebuild Sequencing Strategy

PDR · Rebuild Sequencing Strategy Accepted
Epic ATS-RB · Data Migration·Solution

The rebuild is delivered capability by capability, not in rigid domain-sized waves. The functional areas — CRM, back office, recruitment — give the working order (the endorsed sequence is CRM, then back office, then recruitment), but that order is a guide, not a hard rule that a whole area must be finished before the next is touched. Foundation and design work — the canonical model, the integration-edge layer, the integration strategy, governance — is done once up front for the whole rebuild; only the build itself is sequenced.

Each capability is built, tested and validated as a self-contained unit and switched on when it is ready, so several capabilities across areas can be in flight at once and each area's most critical capabilities go first. This replaces the earlier close-one-area-before-opening-the-next framing.

The order is a working sequence to confirm with the business, and the exact set of capabilities is set by the requirements gate (the functional inventory and buy-versus-build) rather than fixed in advance.

Deprecation of Lead-Object Business Logic and Customisations

PDR · Lead-Object Deprecation Proposed
Epic ATS-RB · Deprecation·Technical

Every piece of business logic and customisation built on the Lead object — custom fields, automations, Apex classes, Flows, validations — is removed during the rebuild. Nothing built on Lead is carried into the new model or moved to another object. The decision is firm: Lead ends up with no customisations.

The Lead object accumulated logic and customisations during the TargetRecruit implementation that have no continuation in the target model. Keeping them through and after the rebuild would needlessly enlarge the surface to move, raise maintenance cost, and risk interfering with the new processes.

The alternatives were to keep the Lead customisations and move them onto another object in the canonical model, or to leave the logic untouched out of caution. Both drag obsolete logic into the new model. Deprecating instead removes a whole slab of technical debt, simplifies the rebuild, and gives the new build a cleaner starting point. A prior dependency analysis to find hidden references to Lead logic is treated as a safe-execution requirement, not a precondition for the decision itself.

The benefit is a direct cut in technical debt and a smaller surface to migrate and maintain. The cost is the required dependency analysis: references to Lead logic elsewhere must be found first so that removing it does not break anything in production.

MaintainabilityRisk
Still open: Under the rebuild direction the logic deprecation still holds and the object is left clean in place, with no change to the decision.

Cleanup and Refactor of the Current Org as a Foundational Pre-Migration Initiative

PDR · Foundational Org Cleanup Proposed
Epic ATS-RB · Deprecation·Solution

Cleanup becomes a foundational initiative that runs and finishes before the canonical model and anti-corruption-layer work, not in parallel with the rebuild. The implementation partner executes it under Marlex IT sponsorship, covering org hygiene unrelated to the anti-corruption layer: deprecating obsolete functionality, removing dead code, general technical-debt remediation, and legacy naming cleanup.

At the 2026-04-17 meeting Nuvolar recommended cleaning up the current org first so an already-optimised system is carried forward. Marlex Spain's current org is the base from which the group standard is derived, and that standard then propagates to Axxon and the regional orgs (Portugal, Italy, Philippines). Any unresolved technical debt in the source is inherited by the standard and multiplied across every derived org. The only way to guarantee the standard is born clean is to close cleanup before the build starts.

Folding cleanup inside the rebuild would have made it compete with the anti-corruption-layer and data-migration work and get deprioritised to the end; running it in parallel on the same org introduces costly coordination and the risk that the rebuild touches dirty components. Deferring it until after cutover would mean carrying debt into the new model, cleaning two orgs instead of one, and propagating debt onward. Sequencing cleanup as a foundational phase — the rebuild foundation and the first-pass functional inventory as prerequisites, cleanup closing before the canonical model and anti-corruption-layer work opens — avoids all three. The former testing scope (Lead deprecation, tech-debt remediation, portal deprecation, pre-migration prefix cleanup, retired-metadata removal) moves into cleanup; automation modernisation moves into a dedicated cleanup deliverable; the post-cutover naming pass moves to the standardisation and expansion phases. That testing scope is emptied and its slot later reused for a quality, testing and UAT scope.

The buy is a clean org before the canonical model and anti-corruption-layer work, no concurrent contention over the same components, Telefónica applied where its org knowledge helps most, and a clear cleanup then anti-corruption-layer refactor then rebuild sequence that propagates a clean base to Axxon and the regions. The cost is schedule: the canonical model and anti-corruption-layer work cannot start until cleanup closes, which puts pressure on the NET4 January 2027 deadline and requires Marlex either to confirm the window or accept the extension risk. A slip in the first-pass functional inventory cascades into cleanup and the whole rebuild, and the implementation partner must commit full capacity without cannibalising run-the-business maintenance.

MaintainabilityModifiabilityRisk
Still open: Confirm with Marlex IT and Marlex Product the shift from parallel to foundational, the cleanup window between the first-pass inventory and the canonical model and anti-corruption-layer work, and the NET4 January 2027 impact (accept the risk or renegotiate). Under the rebuild direction cleanup survives in a reduced form — pre-rebuild hygiene mostly absorbed into the native rebuild, and the debt it prevents now protects a native custom standard rather than a Bullhorn one. Absorbs the former minimal-naming-cleanup decision: strip the TargetRecruit and implementer prefixes and reconcile inconsistent prefixes during the native build, keeping the Marlex Standard prefix.

Modernising Workflow Rules in CLEAN (not MIG), Pre-Migration

PDR · Workflow-Rule Modernisation Proposed
Epic ATS-RB · Automation Modernisation·Technical

The active Workflow Rules in the current org are modernised to Record-Triggered Flows as part of the cleanup, before the build — and only the automation that survives the rebuild is converted, since logic rebuilt natively is not converted first. It is a single deliverable: the domain split the original design imagined has no scope, as almost all the rules sit on one object.

Salesforce has retired both Workflow Rules and Process Builder, so anything remaining must move to Flow Builder before the rebuild — otherwise deprecated technology gets dragged into the standard and from there into Axxon and the regions. The inventory was verified against the source repository (February 2026 audit) and against production (2026-05-19): four active Workflow Rules and zero Process Builders.

This follows the cleanup-first doctrine — clean the current org before propagating to new orgs — and matches Salesforce's product retirement of the older automation. The alternatives were to do the conversion in a separate testing scope, to defer it after cutover (dragging the debt forward), or to keep the old automation (not viable, since it is retired). Doing it in cleanup reduces rebuild scope and lets Telefónica work on automations it already knows in the org it already knows; new automations in the rebuild are born as Flows.

The buy is modern automation before the rebuild, a modernised base for the build, and cleanup keeping all hygiene concentrated in one phase. The cost is that Telefónica modernises the four rules knowing the anti-corruption layer may later rewrite parts (the modernisation value is independent of that refactor), the scope reopens if the live-org inventory surfaces additional rules on managed-package objects, and there is regression risk in the current org during cleanup — mitigated with functional tests before closing the deliverable.

Under the rebuild direction the Workflow-to-Flow conversion is deferred and applied only to what survives natively (do not modernise code that will be rebuilt), reframing rather than reversing the decision.

Axxon's recruitment build references the Marlex build in parallel — not gated on a finished hand-over

PDR · Axxon ATS as Marlex-Referenced Build Proposed
Epic AX-STD · ATS Onboarding — Build·Programme

Axxon's recruitment platform is built by replicating the Marlex build and referencing it as the template, running in parallel with the Marlex programme rather than waiting for a finished, fully-standardised package to be handed over. The default is to copy the Marlex components and diverge only where an Axxon process genuinely has to differ.

Axxon is an acquired brand, not a regional rollout — it keeps its own Salesforce org, its own verticals (Business, Technicals, Operational Staff), and French regulation that needs adaptation rather than a blind copy. Maintaining two divergent products in parallel would compound cost and architectural risk, so Axxon adopting the Marlex standard as its template is the right approach; the question this decision settles is the timing, not the direction.

Building in parallel and referencing the Marlex build — rather than waiting for the standard to be fully classified before starting — keeps Axxon's timeline workable. The finance connection to NET4 is independent of the recruitment rebuild and carries its own fiscal target, while the recruitment build waits only for the Marlex rebuild to define the platform it copies. The alternatives were rejected: waiting for a finished template hand-over is incompatible both with the deadline and with Axxon's need to adapt; skipping the standard entirely and building in isolation would regenerate the divergence the programme is trying to avoid; and postponing Axxon's recruitment work until after the Portugal rollout would break the acquisition as a unit and prolong running two systems past the point where it gets expensive.

The pay-off is that the finance connection and the recruitment build become executable without waiting for full standardisation, the fiscal deadline stays reachable, and Axxon's genuine differences are respected while the bulk is replicated from the proven Marlex build. The cost is possible duplicated effort if the Marlex standard matures a lot during the build (managed by re-syncing from the shared modules at the right moment), and a dependency on the map of where Axxon's processes differ from Marlex's — if that is not ready in time, the recruitment build has no functional foundation.

Splitting Testing/UAT and Data/Cutover into Four Owner-and-Timing Epics

PDR · Testing/UAT/Data/Cutover Four-Epic Split Proposed
Epic ATS-RB · Testing·Programme

The two combined work areas — quality/testing/UAT, and data/cutover — are split into four epics, each aligned to a single owner and delivery moment: Testing (Telefónica and Nuvolar), Data Migration (Telefónica), Business Acceptance (Marlex Product and Telefónica), and Cutover & Hypercare (Marlex IT and Telefónica). The split adds no work — it separates ownership and timing so each closes at the right moment; the deliverable contents were refreshed in the 2026-07-09 rewrite.

The old taxonomy grouped by discipline (testing versus data), but the deliverables actually run by owner and moment — technical testing, data engineering, business UAT, and production cutover are four distinct flows the old grouping hid. On top of that, the standardisation wave that pre-empts UAT needs the gate between 'data in the sandbox' and 'business UAT' to be visible on the roadmap, and that gate was buried inside the old testing work.

Splitting into four makes each work area match its natural owner and exit contract, so the roadmap becomes self-explanatory — four nodes instead of two hybrid clumps — and the UAT-to-cutover gate becomes an explicit dependency rather than something implicit. Middleware Sequencing by Rebuild Stage — Dual Reading Allowed Early, No Retiring Data at the Final Switch-Over

PDR · Middleware Sequencing by Rebuild Stage Proposed
Epic MULE · Integration Registry·Sequencing

The integration work is scheduled against the stages of the recruitment rebuild rather than against one final go-live. The rebuild does not arrive in a single moment: the capabilities that can be separated from the shared candidate record move first — interviews, then the talent pool, then placements, confirmed on 2026-07-23 — and the tightly-coupled core of candidates, vacancies and applications crosses last, in one rehearsed weekend. Each integration is therefore timed against the stage that first moves the data it reads, not against the end of the programme.

Two rules follow, and they are deliberately different in kind. During the early stages an integration may read the retiring recruitment data and the new model at the same time, because while a stage is in flight both genuinely hold live data — that is a design requirement, not a workaround. At the final switch-over the position is absolute: no integration may read or write any of the retiring product's data at all. The second rule is worth stating plainly because it is a pass-or-fail test rather than a matter of judgement — an integration either still refers to that data or it does not.

No stage carries a committed date, and none is being set. The work starts now, each stage lands when the team on it finishes, and resource and focus are aimed at finishing early rather than at meeting a calendar. That is why every deadline here is expressed as an event rather than a day: "when placements move" is the whole of it. The discipline this demands is knowing which integrations a stage takes with it, so that nothing is discovered after the fact — not tracking dates that would only be invented.

The consequence people find surprising is that several small integrations fall due before the two large ones. The training-certificate exchange reads the vacancy and the placement records, so it is pulled forward by the placement stage. The sourcing connector lands profiles against the talent pool, so it is pulled forward too — and it carries an unresolved question about whether its supplier or Marlex controls the change, which now has to be answered sooner than expected. The analytics extract is harder still: the records it copies are split across both stages, so it either re-points twice or once late, and that choice is still open. The finance-system and job-board integrations, by contrast, are coupled to the candidate, so they move with the core.

An integration may also go live while still reading the retiring data, and that is a finished state rather than a shortcut. What protects it is that the interface published to the outside system does not change afterwards: when the new records arrive, a second implementation behind that same published interface reads those instead, chosen by configuration. The outside system never learns that anything moved. This is the swappable-adapter discipline the programme already relies on, applied to where the data lives rather than to how the connection travels.

The same reasoning sets what an integration has to wait for, decided 2026-08-13. Routing an integration through the layer Marlex owns without changing what it does is a change of transport, not of process — the same data moves between the same two systems for the same reason, and nobody works differently afterwards. So it never waits on a process decision: unless the business has already settled a different target process, the integration is routed exactly as it runs today, and the layer becomes the place a later process change is made, cheaply, because the connection point already exists. Rebuilding an integration as it already runs is treated the same way where live production traffic justifies it. Designing something new on a dormant connection is the case that does wait.

Three alternatives were rejected. Waiting for the rebuild to finish and then building the middleware would force every interface to be built against a data model already being dismantled, and would leave the early-stage integrations still sitting in Salesforce at the moment their records move. Building only against the new model, forbidding dual reading, would stop any interface reaching production before its stage and would pile the work into the one weekend with no slack. Allowing residual reads of the retiring data after the final switch-over was rejected because the old product is uninstalled and uninstalling deletes its data — a reading left in place is a deferred failure, not tolerable debt.
