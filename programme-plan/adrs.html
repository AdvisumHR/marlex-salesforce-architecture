Marlex-owned canonical model — the real schema in the rebuild, a decoupling layer only during transition

ADR · Canonical Model (Marlex-owned schema) Proposed
Epic ATS-RB · Canonical Model·Solution

Marlex defines and owns its own Salesforce objects as the canonical model of the business — objects like Placement and ScratchSheet belong to Marlex, not to a licensed product. How that model is used differs between two moments, and the distinction matters.

Full decision — set out in the recruitment-platform rebuild decision record.

Anti-Corruption Layer (ACL) pattern — integration-edge only

ADR · Anti-Corruption Layer (edge-only) Proposed
Epic ATS-RB · Canonical Model·Technical

Where Apex must touch the vendor's objects — now only at the integration edges and the transitional read seam while the old system coexists — it goes through an Anti-Corruption Layer (ACL) built from ports (Apex interfaces), adapters (translation classes) and mapping DTOs between the vendor's objects and Marlex's canonical model. Under the custom-native rebuild the ATS core is built natively on the canonical model, so the ACL is an edge concern, not a pervasive layer over a packaged vendor.

Full decision — set out in the recruitment-platform rebuild decision record.

Data-access seam during coexistence — repository confinement, not full ACL

ADR · Data-Access Seam during Coexistence Superseded
Epic ATS-RB · Canonical Model·Solution

During the months the new native system runs alongside TargetRecruit, rebuilt code still has to read and write the old package's objects. This decision sets how: code that touches the package splits into two kinds, treated in opposite ways. Throwaway bridge code — dual-writes and syncs whose only job is to keep the package fed until switch-off — is written directly, kept cheap, and deleted at cutover. Surviving logic — the controllers and services that read jobs, applications and candidate data today and will keep doing so afterwards — has all of its old-package queries penned into one small repository class per business entity, so at cutover that single class is re-pointed at the native object and the business logic above it never moves.

The rebuild once planned for two recruitment vendors sitting behind one shared, vendor-neutral model, which justified a full translation layer at every seam. The programme then chose a single custom build, and the new model became the neutral model. With no second vendor to translate to, a translation layer on a natively-owned entity would map a record to an identical copy of itself — ceremony for no gain. The seam still needs discipline; it no longer needs the ceremony.

A full translation layer everywhere was rejected because, under one model, the native-side translation is an identity map — extra classes, indirection and test surface for zero portability. Direct package access scattered through the logic was rejected because it turns cutover into a rewrite inside the very code that must not move on the switch-off weekend. The two-kinds rule was chosen because it matches the treatment to the code's lifespan: throwaway code stays cheap, surviving logic pays one small confinement cost and collects the whole payoff at cutover as a one-line re-point.

The decisive factor is that what makes cutover cheap is confinement, not abstraction: one named place per entity for the package's queries means cutover edits that place and stops. The cost accepted is honest — each seam must be tagged correctly, and a bridge mistaken for surviving logic (or the reverse) is coupling debt. A separate, unavoidable item is schema coupling: the lookup fields on new objects that point at package objects cannot be hidden by any code pattern and are re-pointed at cutover as a new field plus data migration, tracked as model work rather than code work. The coupled-code metric is restated as two action lists — delete at cutover, re-point at cutover — so it reads as a runbook.

For developers, the surviving-logic classes are named after the entity with a Repository suffix and deliberately carry no ACL prefix, keeping them visually distinct from the full translation-layer components that are now reserved for a genuine second vendor only. A repository holds the package SOQL and DML and returns platform records and fields — no wrapper types, no mappers. This is the Selector/Repository pattern used for its intended purpose: isolate the query, not translate the schema.

Release and branching strategy for migration

ADR · Release & Branching Strategy Proposed
Epic ATS-RB · Foundation — Infrastructure & Governance·Technical

The programme uses a production branch and a shared pre-production branch, with feature branches cut from the production baseline and no long-lived development branch. Before each feature starts, the components in that change's scope are retrieved and aligned to production so environmental drift is not carried into the pull request. Review happens at promotion into pre-production, and production release is a controlled handover rather than a second redesign of the change.

Epic MULE · Integration Registry·Technical

Naming and regionalisation strategy (MA_ = Marlex Standard, MG_ = Group, prefixes optional)

ADR · Naming & Regionalisation Strategy Accepted
Epic ATS-RB · Foundation — Design Decisions & Requirements·Solution

The repository a component lives in (global, marlex, axon, ph) is the source of truth for its scope and ownership; prefixes are optional visual aids, not enforced. MA_ means Marlex Standard (ES/IT/PT) and is optional, with existing MA_ names kept and no mass rename. The only prefix applied actively from now on is MG_ (Marlex Group) on new Group-Shared components, so that when deployed in another org they read as group-owned. Per-country override prefixes are deferred until ES/IT/PT have distinct governance teams.

With multiple regions and partners building on the same base, there was no clear way to tell which components are shared and which are region-specific, creating a risk of unauthorised edits to global components. This decision defines the full structural convention for the expansion phase.

MA_ was chosen to stay Marlex Standard (not Group) because MA_ is already in use for Marlex components today; making MA_ mean Group would have mislabelled existing components and forced a mass rename that breaks integrations querying by API name. Using the repo as the scope source avoids that cost and risk, rather than renaming to a scope prefix (a regression bomb that enforces nothing) or relying on repos alone with no in-org marker.

The trade-off is inconsistent naming (MA_, unprefixed, and new components coexist) and ownership that is not always readable from the API name, so it depends on the catalogue and code review rather than platform enforcement. In return there is no renaming regression, the scheme is honest about what a prefix does (visibility, not enforcement), MG_ identifies group-owned components in any org, and the cost is minimal.

Ownership boundary doctrine — governance, naming convention, and business-logic decoupling

ADR · Ownership-Boundary Doctrine Proposed
Epic ATS-RB · Foundation — Design Decisions & Requirements·Governance + Solution

This decision establishes the ownership boundary as the governance unit: a line that defines who has autonomous change rights over a set of components and who must approve changes that cross it. A component belongs to exactly one boundary — brand and product together (the commercial platform, the recruitment platform, the back-office platform, for Marlex and for Axxon). No component in one boundary reads another boundary's data directly; cross-boundary access goes through a documented service interface, and the canonical model is the one layer every boundary may share. Marlex-shared components are owned by the Centre of Excellence and inherited as-is by all regions; a region may hold its own override, and a shared component must never depend on a regional override.

The Marlex Spain org was built Spain-only. As the programme moves to a shared org that becomes the template for other countries and that Axxon adapts referentially, the codebase must structurally enforce who owns what. Without this, cross-boundary object access, division-hardcoded logic, and dozens of near-duplicate division-specific process copies would propagate into every derived org. The 2026-05-21 coupling analysis confirmed product separation is emergent, not enforced, and that both vertical and region logic are hardcoded.

The boundary was set by brand and product because that maps to how ownership actually works at Marlex — the Centre of Excellence owns the shared components and each country's product team owns its own — whereas splitting by vertical or division was rejected, since no team is organised that way. Vertical variation is therefore configuration, carried by metadata records rather than by separate components, collapsing the hardcoded per-division logic and the near-duplicate division processes into a single configurable pattern with a routing table.

On naming, the settled rule (2026-07-23) is that new native components use a plain English API name with no owner prefix. An owner marker stamped on almost every component partitions nothing — the old org already shows this, where the historical Marlex prefix sits on the large majority of fields and no longer signals anything — and true cross-org ownership, when a component is promoted to another Marlex Group org, is carried by the platform's packaging namespace applied automatically, which makes a hand-typed prefix redundant. A shared group prefix is added to a component only when the Centre of Excellence confirms genuine group-wide scope, as a deliberate choice rather than a default. Existing production objects that already carry the historical prefix or Spanish names are not retro-renamed; a carried-over field keeps its prefix only to avoid breaking live dependencies. What endures from the original scheme is the governance content — who owns a component and what it may depend on — enforced now by folder organisation, documentation, and pull-request review rather than by a mandatory prefix on every name.

The doctrine is topology-independent. It holds unchanged whether regions live as overrides inside one shared Marlex org or as brand-orgs (Axxon and the Philippines) that run their own orgs and consume the standard referentially — only where a component physically lives differs. Under the native rebuild the ownership boundary and the cross-boundary coupling rules survive intact; the earlier requirement to wall the recruitment platform off behind a mandatory product prefix relaxes, because once the vendor package is gone there are no vendor objects left to isolate at the naming layer.

Capability classification and promotion model (scope ladder)

ADR · Capability Classification & Promotion (Scope Ladder) Accepted
Epic ATS-RB · Foundation — Design Decisions & Requirements·Solution

Every capability is classified on a nested scope ladder: Country → Marlex Standard → Group Candidate → Group Shared, where Group contains Marlex Standard contains Country. The default is Marlex Standard, and the burden of proof sits on promotion. A component reaches Group Shared only under the proven-reuse gate (Option A): at least two brands consume it, ownership passes to the Group CoE, and there is a common roadmap. Promotion is executed by physically moving the component to the global repo, renaming it to MG_, and running a standardisation pass at that point.

It is not yet known which capabilities Axxon or Philippines will adopt or which will become group standards. A binary Marlex-vs-Global classification would force premature decisions, so the ladder reflects the real "we don't know yet" state.

The nested ladder avoids premature globalisation and gives a clear, auditable promotion path, rather than treating multi-country and cross-org as orthogonal axes, defaulting to Group when in doubt (which pays a reuse cost that may never materialise), or designating standards top-down by leadership instead of by proven reuse.

The cost is more governance than a binary split, a Group Candidate tier that is a watchlist with no deployment semantics, and a risk of ossification if nothing ever gets promoted (mitigated by periodic CoE review). The payoff is no premature globalisation, a clear promotion path, and a conservative, auditable default.

Repository and ownership-boundary strategy (4 repos)

ADR · Repository & Ownership-Boundary Strategy Accepted
Epic ATS-RB · Foundation — Design Decisions & Requirements·Solution

Repositories are organised by ownership, governance, and deployment scope, not by business domain: global, marlex, axon, ph. A component lives in exactly one repo, and CRM/ATS/BO are catalogue attributes rather than repo boundaries. A single Marlex Group CoE governs all four repos and arbitrates both Group scope and Marlex-Standard scope across countries.

CRM, ATS, and BO are governance and classification boundaries under the boundary doctrine, not stable deployment or repository boundaries.

Aligning repos to ownership and org topology gives clear ownership, avoids duplicating or forking, and makes promotion a deliberate repo-move that gates standardisation, rather than splitting repos by business domain (which are not stable deployment boundaries and create a Conway mismatch) or using a single monorepo (which gives no ownership or cross-org deployment separation).

The cost is cross-repo coordination when several orgs consume shared components via manifests, and a risk of duplicating a component across repos (mitigated by the exactly-one-repo rule plus review). The payoff is clear ownership, alignment with the org topology, and deliberate promotion.

Package-free deployment and manifest strategy

ADR · Package-free Deployment & Manifests Accepted
Epic ATS-RB · Foundation — Design Decisions & Requirements·Technical

The programme goes package-free: the global repo has module folders, each with its own deployment manifest (a package.xml deploy list, not a managed package), versioned by git tag. One manifest per org, plus optional manifests, select which modules deploy. Modules can graduate to packages later as a change of mechanism. Brand-specific business-process layers stay referential; only identical modules deploy from global. This refines the boundary doctrine, it is not a reversal of packaging.

Salesforce packaging adds dependency-management cost that is not yet justified, but cross-org reuse still needs a single source of truth, because copying or rebuilding creates drift and forks.

Package-free with manifests gives that single source of truth without the packaging cost and keeps an incremental path to packages, rather than adopting unlocked/2GP packages now (premature dependency and namespace overhead), copying/rebuilding per org (identical modules fork), or deploying the whole global repo to every org (ungovernable manual cherry-picking).

The cost is that without package version identity or a platform edit-lock, enforcement is governance plus review, and manifests and hand-declared dependencies must be maintained. The payoff is a single source of truth without packaging cost, an incremental path, and clear per-org manifests.

Configuration and variability framework (config-driven)

ADR · Configuration & Variability Framework Accepted
Epic ATS-RB · Foundation — Design Decisions & Requirements·Solution

Business variation is data and configuration, not hardcoded logic. Standardisation patterns are defined per layer (Data, Logic, UI, Security, Integration, Reporting, Automation), and a fixed set of dimensions must never be hardcoded: country, brand, region/sub-region, office, business unit, vertical, contract type, legal entity, language, currency, ATS vendor, integration endpoint, and legal basis/consent. Being config-driven for Spain, Italy, and Portugal also makes a component eligible for promotion to a group-wide shared component, so the variability model is treated as a primary architecture artefact.

The decisive architectural lever is the variability model, not the code repository structure. Hardcoded business variation blocks multi-country reuse and promotion.

Treating variation as configuration makes components multi-country-safe and promotion-ready by construction, with one discipline serving both goals, rather than defaulting to country-specific components (which fragments the standard) or over-configuring everything (which creates configuration sprawl; a separate component is used only when a team must own the divergence).

The cost is more build effort than hardcoding, Custom Metadata and record-type machinery to maintain, and a risk of hidden Marlex/Spain assumptions (mitigated by an audit for hardcoded assumptions). The payoff is components reusable across countries and promotable, with a single discipline serving both multi-country and cross-org goals.

On 2026-07-02 this became a binding principle for Marlex's custom-native rebuild: the model is built portable and config-driven by construction (Custom Metadata, Custom Settings, Record Types, Global Value Sets, no hardcoding) so that promotion to a group-wide shared component is parameterisation, not refactoring.

Dependency management (governance-driven, package-free)

ADR · Dependency Management Accepted
Epic ATS-RB · Foundation — Design Decisions & Requirements·Technical

Dependencies are managed through governance, manifests, and the deployment pipeline: understand relationships, define deployment order, validate deployability, and prevent uncontrolled cross-dependencies. A future move to unlocked packages is a change of deployment mechanism, not the moment modular architecture begins. The core rule is that a group-wide shared component depends on nothing org-local or country-specific; the reverse is allowed.

Going package-free avoids the mechanics of packaging but not the architectural work that packaging would otherwise force.

Doing the dependency work by governance from day one enforces modular discipline regardless of mechanism, rather than deferring dependency management until packaging (the dependencies already exist) or adopting packages now for enforcement (which the package-free deployment decision defers).

The cost is that governed tracking is weaker than package-enforced tracking and depends on the governance catalogue and review (mitigated by the governance catalogue). The payoff is modular discipline from the start.

Enforcement model and governance catalogue

ADR · Enforcement Model & Governance Catalogue Accepted
Epic ATS-RB · Foundation — Design Decisions & Requirements·Technical

Enforcement is governance: code review (a purely Marlex release must not touch a group-wide shared component), release-process validation, and Centre of Excellence ownership and arbitration. A governance catalogue is mandatory from the start, with one row per component or group recording repository/scope, owner, functional area, Salesforce layer, dependencies, consuming orgs, and configuration dimensions. The pipeline overwriting local edits is a reactive aid, not enforcement.

Without packaging there is no platform-level "do not touch", and the naming prefix enforces nothing on its own.

Governance-based enforcement works without packaging and is auditable, and the catalogue is the source of truth precisely because prefixes are optional, rather than trusting the prefix (which enforces nothing) or adopting managed packages for a platform lock (which the package-free deployment decision defers, to be revisited only if review proves insufficient).

The cost is that it depends on a human process and the catalogue can go stale (mitigated by updating the row on every pull request). The payoff is enforcement that works without packaging and stays auditable.

Component scope strategy: Group-first vs Local-first and the promotion/downgrade cycle

ADR · Component-Scope Strategy (Group vs Local) Proposed
Epic ATS-RB · Foundation — Design Decisions & Requirements·Solution

The programme designs local-first: everything is born a Marlex Standard component (config-driven) in its owning brand and rises to a group-wide shared component (cross-brand) only under the proven-reuse gate defined in the capability scope ladder. Only a small technical and governance core is born group-shared (frameworks, the canonical and common-integration model, logging and error handling, the anti-corruption-layer pattern, configuration schemas, governance); the sharing and security layer and functional components are not. A downgrade process is added, along with a cost model that explains why the default works.

Marlex is multi-brand (Marlex Spain, Italy, and Portugal plus the Axxon and Philippines brand-orgs consuming referentially), with no external deadline forcing components up to group-wide. The capability scope ladder set the tiers and the Marlex Standard default but never modelled the cost or defined the reverse process. Orgs split by brand, not region, so the real axis is the breadth of reuse on the ladder.

Local-first was chosen over group-first (born cross-brand) because of the downgrade risk, and this decision quantifies why: promotion is additive and gated, while downgrade is subtractive across every consumer that holds a "group-owned" contract, plus the sunk standardisation cost. That asymmetry justifies the conservative default.

The cost is a duplication risk if nothing is promoted, an expensive downgrade path (the very cost the default avoids), and dependence on a human process and a Centre of Excellence whose members are not yet confirmed. The payoff is no premature globalisation, a complete up-and-down cycle, an explicit safeguard against a Spain-default bias, and brand divergence absorbed without forced refactoring.

Data Cloud (Data 360) and Marketing Cloud Next architecture

ADR · Data Cloud & Marketing Cloud Architecture Draft
Epic MKT · Marketing Cloud — Wave A·Solution

The draft direction captures the Marketing Cloud Wave B target architecture for ratification: a home Data Cloud in the Spain org pinned to the EU Operating Zone (Hyperforce EU), a hub-and-spoke topology via Data Cloud One and Companion Connections with Spain as home plus one companion (Axxon), Spain, Italy, and Portugal as Data Spaces inside the home and the Philippines out of scope for now, a Consent Data Model per space, identity resolution over Individual, Data Kit for the software development lifecycle, and Data Cloud as the group's cross-org reporting layer. The positions are illustrative, pending ratification.

The Marketing Cloud sequencing decision (closed 2026-05-13) decided only the sequencing into two waves (finite campaigns in TargetRecruit first, rebuilt after cutover). The roughly ten target-architecture decisions in the considerations document are not yet ratified, and that document predates both the sequencing decision and the decision to put the Philippines out of scope, so its topology and licensing are outdated.

This topology was chosen over one Data Cloud per org (which breaks consolidated reporting), Marketing Cloud Engagement/Pardot (rejected in favour of Marketing Cloud Next), and deferring all architecture to build (GDPR rework risk). The reasoning is that residency, consent, and identity resolution are GDPR-load-bearing and hard to reverse after ingestion, and the topology is the answer to cross-org reporting.

The cost is unquantified companion and credits licensing, an open edition choice (Growth versus Advanced), and obsolete figures in the considerations document (to be recomputed without the Philippines). The payoff is a GDPR-correct home and consent, one profile per person across brands, and cross-org reporting via the companion.

Under the custom-native rebuild the home Data Cloud moves from the Spain packaged org to the Spain custom-native org (the same in-place org); the hub-and-spoke topology is unchanged. The rebuild is a source-connector change for Spain, not a change to the Data Cloud model: the candidate stays a standard Contact record, so identity resolution and the consent model are untouched, and only the recruitment-activity data streams (jobs, applications, placements, interviews) re-point onto the rebuilt object names at cutover. Because of this split, the person and consent layer can be built now, independent of the rebuild, while the activity streams follow the cutover — and any marketing flow built now on recruitment-activity data carries a re-point at cutover, which belongs on the cutover plan.

AI-assistant data governance (MarlexOne / Groq) and data residency

ADR · AI-Assistant Data Governance Draft
Governance

The draft direction treats the MarlexOne AI assistant as a compliance gate before cutover: confirm what data leaves and where (Groq in the US); then either remediate (a data-processing agreement plus standard contractual clauses plus data minimisation plus an EU LLM region or EU provider), retire the feature, or formally risk-accept with legal sign-off. The flow is not carried forward as-is without one of the three. It also defines the residency policy for future AI features, aligned to the EU home Data Cloud.

The functional inventory flags the MarlexOne AI assistant for data-governance review: business data (potentially personal, EU) may be sent to a US-hosted LLM, and the data-processing basis for that transfer needs to be confirmed. The programme treats this flow as one to review and remediate before it is carried forward, and it is a possible legal gate before cutover.

Gating the feature was chosen over carrying it forward as-is (unresolved GDPR question), retiring it (losing the AI capability), remediating with an EU provider/region and a data-processing agreement (rework cost), or risk-accepting with legal sign-off. The reasoning is that an EU personal-data flow to a US-hosted LLM needs a confirmed data-processing basis, cheap to decide now but costly if carried into the new org and propagated to Axxon and the Philippines.

The cost is that it needs legal input (data-processing agreement, legal basis), remediation may delay or re-cost the feature, and it depends on EU AI provider alternatives. The payoff is closing an open GDPR question, setting a reusable AI residency policy, and a cheap decision made before cutover.

Still open: To advance, the real data flow must be confirmed with Marlex IT, legal input obtained (data-processing agreement and legal basis), and a remediate/retire/risk-accept choice made.

Target-state reporting and BI strategy — native SF plus Data Cloud plus external Power BI

ADR · Reporting & BI Target-State Draft
Solution

The draft direction defines three reporting layers: native Salesforce reports and dashboards for in-org operational reporting, respecting the per-country sharing model; Data Cloud Companion as the group's consolidated cross-brand and cross-region reporting layer; and external Power BI kept outside Salesforce as corporate business intelligence, not moved. The programme inventories current reports and decides which move to native Salesforce, get rebuilt, or are retired, treating reporting as its own wave.

The programme has no target-state reporting decision. The facts are that Spain's roughly seven-million-row Power BI table is external to Salesforce and out of scope for the data move, Data Cloud Companion is the group's cross-org reporting layer, and reporting has no epic of its own, appearing only as a "reports respect scope" item in the data-dependent activation wave.

Three defined layers were chosen over all-reporting-in-Salesforce (ignores corporate Power BI), all-in-external-Power BI (underuses Data Cloud), or not deciding (reporting lost at cutover). The reasoning is that without an explicit strategy, reporting is either lost in the cutover or rebuilt ad hoc, and the three planes have distinct owners and mechanisms.

The cost is that it requires a current reports inventory (which does not exist), coordinates three tools and owners, and carries the Data Cloud Companion cost. The payoff is reporting that survives the cutover, clear boundaries between Salesforce, Data Cloud, and Power BI, and respect for per-country sharing.

Field-level security in rebuild code — enforced where a person acts, explicit where automation writes

ADR · Field-Security Enforcement by Execution Context Proposed
Epic ATS-RB · Native Build·Technical

Salesforce code runs with security checks switched off unless the developer switches them on, and the setting that governs which records a user can reach is a different setting from the one that governs which fields they can open. A read of the live platform found that of the code Marlex owns, roughly a third touches the objects being rebuilt, and only one class checks field access at all.

The rule now depends on who is acting. Where a person clicks something — a screen, a button, an action they trigger — the code checks that person's field and object access and respects it. Where the platform writes on its own — automation that fires on save, scheduled jobs, and the doors that inbound feeds arrive through — the code keeps writing without those checks, and says so in a comment explaining why.

That split is not a compromise, it is what the evidence supports. Testing every user's real field access against the fields each piece of code writes, across the three busiest objects, found no case where switching the checks on in the screens would take away something a user can do today. It also found the opposite risk is real: a handful of fields are written only by automation and appear in no user's access at all, so switching checks on there would break the write.

One narrow exception is allowed and was already being used correctly: where a tool is reachable only by holding a specific access grant, that grant can be the control, and the code records which grant it relies on.

SecurityMaintainabilityCorrectness
Still open: Extend the field-access evidence to the remaining objects in scope; this can add exceptions to the list but does not change the rule. Owner: the architecture team, before the first change that touches those objects.

Access grants that add nothing are not rebuilt — the test is what a user can actually do

ADR · Empty Access Grants Are Not Rebuilt Proposed
Epic ATS-RB · Native Build·Technical

The plan for moving users onto the new objects was to copy every existing access grant one for one, so that nothing could be missed. Measuring what those grants actually deliver showed that copying them literally would carry across empty containers.

One grant covering four placement fields is held by thirty people. The base access their role already carries makes all four fields editable, so for twenty-four of the thirty the grant delivers nothing. Comparing what a holder can do against what a non-holder with the same base access can do returns an identical result across every field on the object.

So the test changes from what a grant says to what a user can actually do. A grant is rebuilt only where it adds something on top of the access its holders already have, measured per holder. Where it adds nothing, it is not rebuilt, and the measurement that showed so is recorded rather than the grant being quietly dropped. Where it adds something for only some of its holders, it is rebuilt for those people alone.

This is deliberately not a redesign. Real differences are still copied faithfully — including the ones that are easy to round off, such as the core recruitment population being able to create and edit jobs and the talent pool but not delete them. The only thing discarded is what is demonstrably empty.

MaintainabilitySecurityOperability
Still open: Apply the same test to the remaining cross-cutting grants, including the near-universal candidature field filter and a personnel-integration grant held by several hundred users that opens an object without opening any field on it. Owner: the architecture team, during the extension to the remaining objects.

Business rules live on the record, not on the screen

ADR · Business Rules Live on the Record Proposed
Epic ATS-RB · Foundation — Infrastructure & Governance·Architecture (build standard)

A rule that protects a process only governs the people who arrive through the door it was written on. Salesforce record pages let a rule be attached to the screen itself: show this button only once the record is approved, reveal this section only in that state. That is a reasonable way to build when the screen is the only way in.

Reading the current system shows where those rules were written. The record pages carry a large number of small conditions that decide whether something appears. Most are ordinary housekeeping: they hide a field or a section that is not relevant yet, which is exactly what a screen is for. A meaningful minority are different. They decide whether a button appears, and the button is how work moves forward.

The clearest case is an offer. Sending it for signature, accepting it, making it current, marking it expired: each is a button, and each button is shown or hidden by a condition on the offer's state and its approval. The offer does carry rules of its own, so this is not an unguarded record. But those rules freeze the price and the margin after an offer is approved, and require a bank account before it becomes current. None of them stops an unapproved offer being sent for signature. That protection exists only as a hidden button.

The screens are no longer the only way in. Applications already arrive from the careers landing pages and the job boards over a direct connection, the payroll and staffing systems exchange records through the integration layer, and the data migration itself writes millions of records without a screen ever opening. None of those are subject to a condition that exists only on a page.

So the placement of a rule is now decided by what kind of rule it is. Anything that protects the integrity of a process — what must be filled in, which state may follow which, what needs approval before it moves, what may no longer change once closed — is written onto the record, where it applies to a person, an integration and a data load alike. Anything the business calculates and others rely on is derived on the record too. What genuinely belongs on the screen stays there: showing the right fields at the right moment, hiding what is irrelevant, guiding the person through the work. A screen may repeat a rule to make the experience better; what it may not do is be the only place the rule exists.

Assembling pages from the platform's own building blocks remains the right way to build them — that is settled separately and is not reopened here. The change is narrower: the page presents the rule, it no longer holds it.

The rule binds new work at full strength from the moment it is accepted. Rules carried over from the current system as each capability is rebuilt are recorded as work still to do rather than treated as defects, because deciding what to do with the existing rules is a question of effort and sequence that has not been costed yet. Recording them is what makes that cost visible.

CorrectnessInteroperabilityGovernability
Still open: Size the carried-over rules, grouped by the record they sit on, separating those that collapse into a single shared rule from those needing to be moved one at a time. That figure decides whether the work travels with each rebuilt capability at little extra cost or needs a place of its own in the plan. Owner: the architecture team. Also open: how the historical data move satisfies the new rules or is granted a documented, time-limited exception; and whether a screen condition may ever stand alone when the concern is confidentiality rather than integrity — the starting position is that confidentiality is governed by the access model instead. Owner: the architecture team, with the build team on the data move.

Data access during coexistence — direct access, no repository layer

ADR · Acceso a datos durante la coexistencia Proposed
Epic ATS-RB · Canonical Model·Solution

While the new native system runs alongside TargetRecruit, new code sometimes has to read the old data because the new objects are not populated yet. This decision settles how, and the answer is the plain one: it reads the old objects directly, and at cutover those reads are re-pointed where they sit. No dedicated layer stands between the new code and the old data.

A translation layer is kept in exactly one place — a connection to an outside system, where the boundary is real — and even there only until that connection moves to the integration platform, after which the contract lives in the platform and the layer inside Salesforce stops earning its keep. On Marlex’s own objects there is no layer at all.

This supersedes the earlier seam decision, which asked for every old-system query to be confined to one dedicated class per business object. That earlier rule was itself a reduction of a much heavier translation layer designed when the programme still planned for two recruitment vendors. Once the programme chose a single native build, the heavy layer was removed because it would map a record to a copy of itself; the confinement class survived that pass but is the same ceremony one level down, on code that has to be edited at cutover regardless.

What settled it was evidence of non-adoption. Not one confinement class was ever built, while fourteen prototype classes from the abandoned two-vendor design sit in the repository untouched since 28 May 2026 — before the move to a single native build. A written rule nobody follows is worse than no rule: it invites divergent readings and hides what the real standard is. Marlex confirmed the position on 2 September 2026.

Two consequences are accepted. Old-system queries are now spread across new code rather than gathered in one place, so re-pointing them at cutover depends on a reliable inventory of where they are rather than on a single file — and code review becomes the only guard against an old-system read leaking into logic that has to survive the switch.

A naming corollary follows for the early waves. Placements, interviews and the talent pool cut over before the shared core, but a component in one of those waves usually also reads the candidate and the job, which stay in the old system until the core cutover — so it crosses twice. It stays one component with one name, edited twice; the second edit is an ordinary deployment of Marlex’s own new code, never a change to the untouched legacy component, and never a second or third named version. Reports are the one real exception, because the platform will not re-point a report at another object, so a report spanning both waves is rebuilt in each.
