Rebuild Sequencing Strategy

PDR · Rebuild Sequencing Strategy Accepted
Epic ATS-RB · Data Migration·Solution

The rebuild is delivered capability by capability, not in rigid domain-sized waves. The functional areas — CRM, back office, recruitment — give the working order (the endorsed sequence is CRM, then back office, then recruitment), but that order is a guide, not a hard rule that a whole area must be finished before the next is touched. Foundation and design work — the canonical model, the integration-edge layer, the integration strategy, governance — is done once up front for the whole rebuild; only the build itself is sequenced.

Each capability is built, tested and validated as a self-contained unit and switched on when it is ready, so several capabilities across areas can be in flight at once and each area's most critical capabilities go first. This replaces the earlier close-one-area-before-opening-the-next framing.

The order is a working sequence to confirm with the business, and the exact set of capabilities is set by the requirements gate (the functional inventory and buy-versus-build) rather than fixed in advance.

Time-to-MarketRisk
Still open: Confirm the functional-area order with the business before the build starts; the working sequence is CRM, then back office, then recruitment. The capability breakdown itself comes from the requirements inventory.

Deprecation of Lead-Object Business Logic and Customisations

PDR · Lead-Object Deprecation Proposed
Epic ATS-RB · Deprecation·Technical

Every piece of business logic and customisation built on the Lead object — custom fields, automations, Apex classes, Flows, validations — is removed during the rebuild. Nothing built on Lead is carried into the new model or moved to another object. The decision is firm: Lead ends up with no customisations.

The Lead object accumulated logic and customisations during the TargetRecruit implementation that have no continuation in the target model. Keeping them through and after the rebuild would needlessly enlarge the surface to move, raise maintenance cost, and risk interfering with the new processes.

The alternatives were to keep the Lead customisations and move them onto another object in the canonical model, or to leave the logic untouched out of caution. Both drag obsolete logic into the new model. Deprecating instead removes a whole slab of technical debt, simplifies the rebuild, and gives the new build a cleaner starting point. A prior dependency analysis to find hidden references to Lead logic is treated as a safe-execution requirement, not a precondition for the decision itself.

The benefit is a direct cut in technical debt and a smaller surface to migrate and maintain. The cost is the required dependency analysis: references to Lead logic elsewhere must be found first so that removing it does not break anything in production.

MaintainabilityRisk
Still open: Under the rebuild direction the logic deprecation still holds and the object is left clean in place, with no change to the decision.

Cleanup and Refactor of the Current Org as a Foundational Pre-Migration Initiative

PDR · Foundational Org Cleanup Proposed
Epic ATS-RB · Deprecation·Solution

Cleanup becomes a foundational initiative that runs and finishes before the canonical model and anti-corruption-layer work, not in parallel with the rebuild. The implementation partner executes it under Marlex IT sponsorship, covering org hygiene unrelated to the anti-corruption layer: deprecating obsolete functionality, removing dead code, general technical-debt remediation, and legacy naming cleanup.

At the 2026-04-17 meeting Nuvolar recommended cleaning up the current org first so an already-optimised system is carried forward. Marlex Spain's current org is the base from which the group standard is derived, and that standard then propagates to Axxon and the regional orgs (Portugal, Italy, Philippines). Any unresolved technical debt in the source is inherited by the standard and multiplied across every derived org. The only way to guarantee the standard is born clean is to close cleanup before the build starts.

Folding cleanup inside the rebuild would have made it compete with the anti-corruption-layer and data-migration work and get deprioritised to the end; running it in parallel on the same org introduces costly coordination and the risk that the rebuild touches dirty components. Deferring it until after cutover would mean carrying debt into the new model, cleaning two orgs instead of one, and propagating debt onward. Sequencing cleanup as a foundational phase — the rebuild foundation and the first-pass functional inventory as prerequisites, cleanup closing before the canonical model and anti-corruption-layer work opens — avoids all three. The former testing scope (Lead deprecation, tech-debt remediation, portal deprecation, pre-migration prefix cleanup, retired-metadata removal) moves into cleanup; automation modernisation moves into a dedicated cleanup deliverable; the post-cutover naming pass moves to the standardisation and expansion phases. That testing scope is emptied and its slot later reused for a quality, testing and UAT scope.

The buy is a clean org before the canonical model and anti-corruption-layer work, no concurrent contention over the same components, Telefónica applied where its org knowledge helps most, and a clear cleanup then anti-corruption-layer refactor then rebuild sequence that propagates a clean base to Axxon and the regions. The cost is schedule: the canonical model and anti-corruption-layer work cannot start until cleanup closes, which puts pressure on the NET4 January 2027 deadline and requires Marlex either to confirm the window or accept the extension risk. A slip in the first-pass functional inventory cascades into cleanup and the whole rebuild, and the implementation partner must commit full capacity without cannibalising run-the-business maintenance.

MaintainabilityModifiabilityRisk
Still open: Confirm with Marlex IT and Marlex Product the shift from parallel to foundational, the cleanup window between the first-pass inventory and the canonical model and anti-corruption-layer work, and the NET4 January 2027 impact (accept the risk or renegotiate). Under the rebuild direction cleanup survives in a reduced form — pre-rebuild hygiene mostly absorbed into the native rebuild, and the debt it prevents now protects a native custom standard rather than a Bullhorn one. Absorbs the former minimal-naming-cleanup decision: strip the TargetRecruit and implementer prefixes and reconcile inconsistent prefixes during the native build, keeping the Marlex Standard prefix.

Modernising Workflow Rules in CLEAN (not MIG), Pre-Migration

PDR · Workflow-Rule Modernisation Proposed
Epic ATS-RB · Automation Modernisation·Technical

The active Workflow Rules in the current org are modernised to Record-Triggered Flows as part of the cleanup, before the build — and only the automation that survives the rebuild is converted, since logic rebuilt natively is not converted first. It is a single deliverable: the domain split the original design imagined has no scope, as almost all the rules sit on one object.

Salesforce has retired both Workflow Rules and Process Builder, so anything remaining must move to Flow Builder before the rebuild — otherwise deprecated technology gets dragged into the standard and from there into Axxon and the regions. The inventory was verified against the source repository (February 2026 audit) and against production (2026-05-19): four active Workflow Rules and zero Process Builders.

This follows the cleanup-first doctrine — clean the current org before propagating to new orgs — and matches Salesforce's product retirement of the older automation. The alternatives were to do the conversion in a separate testing scope, to defer it after cutover (dragging the debt forward), or to keep the old automation (not viable, since it is retired). Doing it in cleanup reduces rebuild scope and lets Telefónica work on automations it already knows in the org it already knows; new automations in the rebuild are born as Flows.

The buy is modern automation before the rebuild, a modernised base for the build, and cleanup keeping all hygiene concentrated in one phase. The cost is that Telefónica modernises the four rules knowing the anti-corruption layer may later rewrite parts (the modernisation value is independent of that refactor), the scope reopens if the live-org inventory surfaces additional rules on managed-package objects, and there is regression risk in the current org during cleanup — mitigated with functional tests before closing the deliverable.

MaintainabilityModifiabilityRisk
Still open: Confirm in the live-org inventory pass that the count matches the repository (four active Workflow Rules, zero Process Builders) or widen the scope if more are found, and confirm with Marlex IT that the automation-modernisation work can run before the canonical model and anti-corruption-layer build with Telefónica's available capacity. Under the rebuild direction the Workflow-to-Flow conversion is deferred and applied only to what survives natively (do not modernise code that will be rebuilt), reframing rather than reversing the decision.

Axxon's recruitment build references the Marlex build in parallel — not gated on a finished hand-over

PDR · Axxon ATS as Marlex-Referenced Build Proposed
Epic AX-STD · ATS Onboarding — Build·Programme

Axxon's recruitment platform is built by replicating the Marlex build and referencing it as the template, running in parallel with the Marlex programme rather than waiting for a finished, fully-standardised package to be handed over. The default is to copy the Marlex components and diverge only where an Axxon process genuinely has to differ.

Axxon is an acquired brand, not a regional rollout — it keeps its own Salesforce org, its own verticals (Business, Technicals, Operational Staff), and French regulation that needs adaptation rather than a blind copy. Maintaining two divergent products in parallel would compound cost and architectural risk, so Axxon adopting the Marlex standard as its template is the right approach; the question this decision settles is the timing, not the direction.

Building in parallel and referencing the Marlex build — rather than waiting for the standard to be fully classified before starting — keeps Axxon's timeline workable. The finance connection to NET4 is independent of the recruitment rebuild and carries its own fiscal target, while the recruitment build waits only for the Marlex rebuild to define the platform it copies. The alternatives were rejected: waiting for a finished template hand-over is incompatible both with the deadline and with Axxon's need to adapt; skipping the standard entirely and building in isolation would regenerate the divergence the programme is trying to avoid; and postponing Axxon's recruitment work until after the Portugal rollout would break the acquisition as a unit and prolong running two systems past the point where it gets expensive.

The pay-off is that the finance connection and the recruitment build become executable without waiting for full standardisation, the fiscal deadline stays reachable, and Axxon's genuine differences are respected while the bulk is replicated from the proven Marlex build. The cost is possible duplicated effort if the Marlex standard matures a lot during the build (managed by re-syncing from the shared modules at the right moment), and a dependency on the map of where Axxon's processes differ from Marlex's — if that is not ready in time, the recruitment build has no functional foundation.

Splitting Testing/UAT and Data/Cutover into Four Owner-and-Timing Epics

PDR · Testing/UAT/Data/Cutover Four-Epic Split Proposed
Epic ATS-RB · Testing·Programme

The two combined work areas — quality/testing/UAT, and data/cutover — are split into four epics, each aligned to a single owner and delivery moment: Testing (Telefónica and Nuvolar), Data Migration (Telefónica), Business Acceptance (Marlex Product and Telefónica), and Cutover & Hypercare (Marlex IT and Telefónica). The split adds no work — it separates ownership and timing so each closes at the right moment; the deliverable contents were refreshed in the 2026-07-09 rewrite.

The old taxonomy grouped by discipline (testing versus data), but the deliverables actually run by owner and moment — technical testing, data engineering, business UAT, and production cutover are four distinct flows the old grouping hid. On top of that, the standardisation wave that pre-empts UAT needs the gate between 'data in the sandbox' and 'business UAT' to be visible on the roadmap, and that gate was buried inside the old testing work.

Splitting into four makes each work area match its natural owner and exit contract, so the roadmap becomes self-explanatory — four nodes instead of two hybrid clumps — and the UAT-to-cutover gate becomes an explicit dependency rather than something implicit. It also lets the three-wave standardisation model be expressed cleanly (the post-build wave between the rebuild build close and the testing start, the production-data wave between data-ready and UAT). The alternatives — keeping the current structure (the gate stays implicit), fusing everything into one final-phase work area (too heterogeneous), or three work areas combining UAT and cutover (they have different owners and cycles: UAT iterative, cutover linear) — were all rejected.

The buy is clear ownership, a visible gate per work area, and a self-explanatory roadmap with no added work. The cost is deliverable renumbering (with frozen historical references keeping their old identifiers by policy), the programme growing from 27 to 29 work areas (minor governance overhead), and stakeholders having to learn the new naming.

Organising standardisation by delivery moment — Waves A, B and C (supersedes the earlier thematic structure)

PDR · STD Wave A/B/C by Delivery Moment Proposed
Programme

Standardisation is organised by delivery moment rather than by theme. Wave A is the shared-surface work done inline while the rebuild builds each area — it is folded into the build itself, so the code is born to-standard rather than standardised in a later pass. Wave B is the post-build, data-free step that classifies the finished components (group-shared, Marlex-standard or country-specific) and produces the reporting artefacts the regions consume. Wave C is the small set of gates that need production-shaped data, run in the migration sandbox.

The prior thematic decisions had modelled the wave as an attribute and a visible sub-unit inside five thematic work areas (Decoupling, Sharing, UX and Localisation, Reports and Email, Classification). But each thematic area was still spread across several waves, so a single acceptance deliverable ended up covering outputs from multiple areas — incoherent with the principle that a work area has one delivery contract. The decision inverts the hierarchy so the primary axis is the delivery moment (the real scheduling unit) and the thematic dimension is demoted to a queryable Layer attribute.

The gain is temporal coherence: every deliverable belongs to a single execution band, with no acceptance crossing work areas, and the roadmap and Telefónica's scheduling organise around when work is built. The alternative of keeping the earlier thematic status quo (the wave as a sub-unit inside thematic areas) was rejected for the cross-area contract incoherence; folding the rebuild build work into Wave A was rejected because it violates the rebuild-standardisation boundary and breaks the 'the rebuild is the rebuild' narrative. The thematic lens is preserved as the Layer column so business can still group by capability or ownership.

The cost is explicit and accepted as a deliberate trade-off: loss of thematic and ownership coherence — each Wave mixes skill profiles and owners in one delivery unit, so anyone wanting to see all the sharing and security work must filter by Layer instead of reading one area. This is the exact reverse of what the earlier thematic structure optimised. There is a one-time cost of a broad sweep (31 identifiers, dependencies, 38 files, the client spreadsheet and the roadmap diagram), and historical records are kept with a 'was standardisation sub-unit' banner.

UnderstandabilityMaintainabilityTime-to-Market
Still open: The delivery-moment organisation is settled; the wave contents were leaned in the 2026-07-09 rewrite (Wave A folded into the build, Wave B reduced to classification and reporting, Wave C to the data-dependent gates).

Hybrid topology — Spain/Italy/Portugal share one org, Axxon and the Philippines are referential brand-orgs; the multi-org pipeline is retired

PDR · Hybrid Topology Accepted
Programme + Solution

The multi-org deployment pipeline that an earlier standardisation decision introduced is withdrawn, and standardisation is refocused around the resolved hybrid topology. Spain, Italy and Portugal share one Marlex org with in-org regional rollouts; Axxon and Philippines are brand-orgs that consume the standard referentially. Because there is no template-to-many-orgs deployment, there is no deployment machinery to build.

The org-topology decision closed on 2026-06-04 as a hybrid split by business-unit category: brand-orgs with their own org consumed referentially (Axxon and Philippines), and one shared Marlex Standard org with in-org regional rollouts for Spain, Italy and Portugal. The earlier standardisation decision had reintroduced a multi-org pipeline (substrate, change-propagation, cross-environment regression) on the assumption of full multi-org with a group template deployed to many orgs. The hybrid resolution invalidates that premise — the Marlex regions share one org, and the brand-orgs deploy the Group-Shared modules from the group repository while rebuilding their brand-specific layers referentially, never receiving replicated Marlex Standard deployment.

Under referential consumption plus a single org for the Marlex regions, the cost of a deployment substrate (Unlocked Packages, Copado, Gearset, Flosum) is not justified — there is nothing to automate. The CI/CD-maturity concern that ruled out packaging under single-org still holds. The portable standard stays valuable as a reference library the brands adapt, not as a deployed artifact. So the pipeline deliverables are retired, the group repository reverts to an optional read-only reference repository, and standardisation keeps its in-org focus plus a cheap classification sub-product identifying the Spain-agnostic core. The alternatives — narrowing the pipeline to brand-orgs (they consume referentially, so there is no deployment target), editing the earlier decision rather than superseding its pipeline scope (against the supersede-not-edit policy), and promoting sharing to its own work area — were all rejected.

The buy is a smaller standardisation scope closer to the original single-org design, no pipeline cost or CI/CD-maturity dependency, a cheap portable core, and brand-orgs decoupled (reference, not deployment) which lowers operational coupling. The cost is that brand-orgs rebuild more instead of inheriting — more build effort per brand-org and less automatic consistency — and cross-org coherence now depends on reference discipline and governance rather than an enforcing pipeline; if any region or brand later needs replicated deployment, the pipeline re-enters scope.

Standardisation Programme Governance (scope ladder, package-free, no epic re-cut)

PDR · Standardisation Programme Governance Accepted
Programme

Standardisation adopts a programme-level frame: a scope ladder with a Marlex-standard default, package-free manifests deployed per org, and no mass-rename — the legacy prefixes are stripped and the Marlex-standard prefix applied inline during the rebuild rather than in a separate rename pass. The wave structure it sits over was itself leaned in the 2026-07-09 rewrite (standardisation is now inline discipline plus a classification step), which does not change this governance frame.

The standardisation work needed a programme-level framework that would not disturb the wave structure already ratified.

Rather than re-cut, the decision keeps the three waves and labels the deliverables with a concern-and-scope tag — the concerns are already in the right place (the anti-corruption layer in the rebuild, Marlex Standard along the standardisation spine, group-shared in the post-build classification plus Axxon and expansion). Re-cutting standardisation by concern or scope was rejected because it would break the wave dependency gates and repeat the broad identifier churn of the last reorganisation. Traceability comes from tags instead of renumbering.

The buy is no renumbering, tag-based traceability, and programme stability while respecting the waves' dependency gates. The cost is having to populate and maintain the concern-and-scope classification in the catalogue.

Marlex Group Programme Execution and Parallelisation Model

PDR · Programme Execution & Parallelisation Model Draft
Programme

The recommended execution model is central architecture and governance first, then parallel workstreams (Foundation and Architecture, the rebuild, Middleware, Axxon Discovery, Data and Marketing). This is a draft direction that validates the lean model implicit in the roadmap; the staffing analysis is still pending.

The programme spans roughly ten initiatives (the rebuild, standardisation, group-shared work, MuleSoft integration, Axxon, Philippines, Data Cloud, Marketing Cloud, and the Portugal and Italy rollouts), but the execution model is only implicit in the roadmap today. The programme risks flag that the sequencing has not been validated by bottleneck analysis, that the roadmap is logical order rather than an estimated timeline, and — most sharply — that around 11 of 14 critical-chain work areas depend on a single implementation partner with no fallback.

A Foundation-first spine lets the reuse and standardisation decisions land before the brands build, avoiding divergence, while parallelising the non-blocking tracks (integration, Axxon discovery, marketing) to compress the calendar. The alternatives were pure sequential (least coordination but an excessively long programme and single-team dependency) and fully parallel (maximum speed but incompatible decisions, rework, and unworkable governance). The hybrid model balances the two.

The buy is speed with control, reuse identified before building, and parallel tracks absorbing business demand. The cost is that it requires mature governance and clear decision rights, it does not resolve the single-partner concentration risk, and it demands staffing beyond the current team — business analysts, Salesforce and integration architects, and specialists in the ATS, MuleSoft and Data Cloud.

Composition and governance of the Marlex Group Centre of Excellence

PDR · CoE Composition & Governance Proposed
Epic ATS-RB · Foundation — Design Decisions & Requirements·Governance

A single Center of Excellence governs Marlex, Axxon and Philippines. Its identified members (2026-06-15) are the Axxon voice, the architecture lead (Nuvolar), Marlex IT, and the ATS Product Owner. The CoE presides over scope decisions (group candidate to group shared), reviews the governance catalogue, and arbitrates ownership disputes between repositories.

The prior global-versus-regional governance model is superseded, leaving no live decision on the governing body — yet pull-request approvals, the release catalogue and validation, boundary approval and promotion arbitration all depend on a Marlex Group CoE as their enforcement mechanism. The governing-body decision was open with only a de-facto membership note.

Every governance decision leans on the CoE — without a ratified body, the review-based, package-free enforcement model has no owner. The alternatives were fully centralised approval (a bottleneck), fully distributed approval (no protection of the shared core), or leaving it de-facto (the state before this decision, with no accountability). A single ratified CoE is the middle path.

The buy is enforceable governance, clear promotion arbitration, and catalogue ownership. The cost is a permanent time commitment from a two-person Marlex IT team and the overhead of cross-brand arbitration.

No pre-locked group standard — the standard is defined after the rebuild, on proven components

PDR · No Pre-Locked Group Standard Proposed
Epic ATS-RB · Foundation — Design Decisions & Requirements·Programme

The standardisation-foundations phase is not a gate that locks a group-wide standard before the build. It is the solution-design decisions and requirements the rebuild needs to start — the naming convention, the ownership and configurable-by-design rules, the data-privacy doctrine, and the business processes each area must follow. It does not pre-define what is shared across the group.

The earlier framing risked treating standardisation-foundations as the moment the cross-brand group standard is fixed. But what is genuinely shared between Marlex and Axxon can only be known once real, proven components exist. Deciding it up front would either over-commit to sharing things that turn out to be brand-specific, or freeze a standard against an unbuilt system.

So the group standard — what is shared group-wide versus Marlex-specific versus country-specific — is defined after the rebuild, when the finished components are classified and proven reusable across at least two brands. The rebuild is instead built reusable-by-construction: configuration-first, no hard-coded values, a global-ready schema, so that promoting something to the group later is a matter of parameterising it, not rebuilding it.

The pay-off is that the standard reflects what actually proved reusable rather than a guess made before the build, and nothing is prematurely globalised. The cost is that Axxon and the country rollouts cannot consume a finished group standard until the post-build classification is done — which is why their adoption tracks are sequenced after the Marlex rebuild.

Axxon Does Not Start as a Block — Each Track Has Its Own Start Prerequisite Against Marlex

PDR · Axxon Per-Track Start Prerequisites Draft
Programme

The decided principle is that Axxon's tracks do not share a single start date — each one starts when its minimum Marlex input is available, no earlier and no later. This operationalises the Marlex-referenced build decision (no hard standardisation dependency) and the parallel-workstreams execution model. The per-track start prerequisites are a consequence of the principle, not the decision itself.

When Axxon starts directly affects coexistence cost, the ability to reuse Marlex capabilities, and the risk of duplicating architecture. Both extremes are bad. Waiting until Marlex is fully rebuilt and standardised (around 2028 or later) prolongs the legacy-system coexistence window past the 12 to 24 month industrial cliff, makes the NET4 fiscal deadline (January 2027, slip accepted to March 2027) impossible, and leaves Axxon unmodernised for years of regulated French operation. Starting Axxon with no Marlex input risks building on a data model and reuse patterns that later diverge, generating rework multiplied by the number of shared capabilities. The execution model named Axxon Discovery as a parallel workstream but did not define per-track start prerequisites; the Marlex-referenced build decision fixed the build model and softened the hard standardisation dependency but did not specify the minimum Marlex inputs needed before building.

Legacy Axxon coexistence (the Eolia ATS, the e-Oer ERP, the legacy Axxon Salesforce org) is the dominant driver: starting too late raises the coexistence risk and parallel-licensing cost exponentially. Splitting by track compresses the calendar without compromising architecture — the Marlex-independent tracks (NET4 via the swappable adapter, and Discovery) start now, while the reusable tracks (CRM, Back Office) wait for the minimum Marlex input that cuts rework. Concretely: Axxon Discovery starts now (no Marlex input; sandbox access opened 2026-06-16); the Axxon ATS needs a stable canonical model plus a closed Marlex-versus-Axxon functional delta (standardisation classification soft); the Axxon NET4 track needs a frozen ATS model plus a confirmed NET4 provider (independent of Marlex via the swappable adapter); Axxon CRM and Back Office need the standardisation classification and the Back Office rebuild pattern respectively — the most reusable tracks, which benefit most from waiting. The group repository starts small (only group-shared frameworks and sharing and anti-corruption-layer patterns); no functional capability enters until the standardisation classification places it, and Axxon references the Marlex repository as a pattern rather than importing Marlex Standard components.

Activation Rule for the Rebuild — Refactor-Now vs Dark-Ship Behind a Feature Flag

PDR · Activation & Feature-Flag Rule Proposed
Epic ATS-RB · Foundation — Infrastructure & Governance·Programme

How each rebuilt capability is switched into production follows a hybrid rule, read directly off the functional inventory. A capability may be refactored in place and cut over immediately — retargeting the existing component to the canonical model and moving its data now — only when it can cut over independently: its records live on a Marlex-owned object with no live TargetRecruit package automation, and nothing still on TargetRecruit shares or depends on it. Everything else is built new, inactive, behind a feature flag, dark-shipped with the flag off, its data moved, then activated at that domain's cutover.

The reason the default is dark-ship, not refactor, is a hard platform fact: a feature flag gates only Marlex's own code. It does not silence the TargetRecruit managed package's own triggers, record-triggered flows, or validation rules, which fire on every save through Salesforce's single order of execution. Running new custom logic side by side with live TargetRecruit on the same business concept is dual logic — the dangerous case. So completing a decoupling always ends with deactivating the TargetRecruit automation on the moved object, which the flag itself cannot do. One concept lives in one system at a time.

The inventory sizes this precisely: of 168 custom features, 86 do not touch TargetRecruit (they stay as built), and 76 are in rebuild scope — plus four already isolated behind the anti-corruption layer (Placement plus an Interview slice, which re-point their adapter), and two dropped. A handful of the rebuild set are narrow single-reference re-points; the rest re-target TargetRecruit-coupled logic to the native model. The feature-flag framework: Custom Metadata Types as the default carrier (they deploy with the release), Custom Settings only for per-profile or per-user override; these are short-lived release toggles removed at cutover, one per capability grouped by domain, so activation can proceed capability by capability and domain by domain. A flag only gates a component that reads it and branches at runtime — Apex, Flows, and (via $CustomMetadata or the hierarchy $Setup) Validation Rules and Formula fields. What cannot read a flag — the data model's existence, UI surfaces, roll-up summaries and native sharing and OWD — is not flagged at all: it is built dark and revealed at cutover through deployment plus field-level security, Permission Sets, and layout and Lightning-page assignment. Business logic takes a flag; structure, UI and access are withheld until the cutover reveal. These 168 are reverse-engineered from the org's customisations — they do not cover the requirements served natively by the TargetRecruit managed package (matching and search, portals, standard recruiting features Marlex never customised). So the 76-feature rebuild scope is the custom-code surface, not the full ATS scope; the TargetRecruit-package-native requirements are a separate, larger unknown that only the ATS product owner's requirements inventory surfaces.

Agile Capability Epics for the Rebuild — Design, Build, Test and UAT Inside Each Capability

PDR · Agile Capability Epics Proposed
Epic ATS-RB · Foundation — Infrastructure & Governance·Programme

The delivery unit for the rebuild is the capability — finer than a domain. Each rebuilt capability is a self-contained epic that carries its own design, development, end-to-end test and capability-level UAT, following the six-part template (data model, data migration, UI, sharing, security, business logic). There are no standalone up-front-design or downstream-testing epics, with two exceptions: the canonical spine is designed and frozen first where it would otherwise block dependent capabilities, and the requirements inventory comes first of all.

UAT runs at two levels. Each capability is validated by the business as it is rebuilt, so gaps surface during the build rather than only at the end; and a single consolidated business sign-off remains the gate before cutover, so the business formally signs the exact state it receives in production. The technical testing work shrinks to cross-cutting quality gates — Apex coverage, static analysis, the with-sharing gate — rather than being 'the testing phase'.

This keeps the deliberate UX and process redesign honest: because current TargetRecruit adoption is failing, acceptance is capability parity plus improved adoption, not a faithful replica, and building capability by capability with its own validation is how that is achieved. When the HR team comes onto the platform — at the switch, or after it

PDR · HR Onboarding Timing Proposed
Epic SHARE · HR Rollout + Sharing-Model Refactor·Sequencing

Bringing the internal HR team onto the recruitment platform and making the access model private are one decision, not two, because HR's work is confidential by nature — a hiring process can be to replace a specific manager, and must not be visible to the person being replaced. An open model, where everyone can see everything, is fine while nothing confidential lives on the platform; the moment HR is on it, that stops being true. So wherever HR onboarding lands, the private model has to land with it.

That turns the timing into a single business choice with two clean paths. By default, the HR team comes on after the platform switch: the switch itself moves no privacy boundary and stays as simple as possible, and the tightening runs afterwards as its own rehearsed stage. The alternative is to bring HR on at the switch, which means the private model must be in place from day one — safe, but it loads the most sensitive window with the access work. The recommendation is the after-the-switch path, because HR has no existing users or data on the platform, so there is nothing lost by standing them up a few weeks later, and the switch stays clean.

Either way, everything HR needs is built on the new owned platform, never on the rented product being retired. The decision belongs to the person responsible for People, who is best placed to judge how urgent HR's need really is; if it is genuinely immediate, a lightweight temporary bridge is preferable to building the full model on the product that is on its way out.

How internal HR work stays private while external hiring stays open

PDR · Internal-vs-External Access Model Proposed
Epic SHARE · HR Rollout + Sharing-Model Refactor·Solution design

The platform has to do two opposite things at once: keep external hiring visible to the whole recruitment team exactly as it is today, and keep the HR team's internal processes private and seen only up their own management line. The way to do that cleanly is to mark every record as internal or external at the data level — not just by which screen it uses — and drive visibility off that mark. External records stay shared with everyone; internal records are closed and open only to the HR team and to a manager above the person who owns them. Every record that exists today is marked external in the switch, so nobody loses the visibility they have now.

Because HR is a corporate function rather than a recruitment office, it has no place in today's management structure, so a small internal management line is built fresh for them — which is straightforward precisely because there are no existing internal users to move. The one thing to watch is that a private internal process does not leak through a related record — an interview, a note, an attachment — so the design has to cover those related records too, not just the main one.

Several details still depend on requirements the HR team has not yet given: exactly which fields count as confidential, whether internal work reuses the same kind of record as external hiring or needs its own, and what onboarding-specific screens are needed. Those are captured as open questions rather than assumed.

PO Specification & Analysis Process

PDR · PO Specification & Analysis Process Proposed
Epic ATS-RB · Foundation — Infrastructure & Governance·Programme

Before any change is built, it is first analysed and given a clear disposition — keep it, drop it, or merge it into something else — decided against the target way of working, not against how the current tool happens to do it today. Only once that analysis produces an agreed specification does the work move on to be built, tested and released. The two stages are kept deliberately separate: one place to decide what should change and why, a second to build and ship it.

The yardstick for every decision is a single business objective — fill vacancies with the right candidate as quickly and cost-effectively as possible, covering more vacancies faster. A change earns its place only if it moves that objective; otherwise it is dropped rather than rebuilt out of habit. The current-state map doubles as a coverage checklist, so nothing quietly falls through, while the target-state map is the lens each decision is made against.

Work is described in business-meaningful units — a capability the business would recognise — rather than one entry per underlying technical component, which would produce thousands of meaningless items. Each specification captures the information involved, the rules and automations, the screens, and above all the what and the why; the how is a separate technical step taken only after the specification is accepted.

Delivery traceability uses a rebuild label rather than a new issue type. Roughly seven or eight capability epics provide the backbone, rebuild stories sit underneath them, and labels or components distinguish phase and sub-package. This keeps every production change traceable to what must be activated at cutover without creating another Jira workflow.

Delivery continues without a long freeze

PDR · No-Freeze Delivery Model Proposed
Epic ATS-RB · Delivering While Rebuilding·Programme

Business delivery continues while the rebuild is under way. New work is built native-first where its capability can live safely on the owned model; where the live TargetRecruit path must also change, the ticket carries an explicit twin obligation so the temporary legacy change and its native successor stay linked.

The model avoids a programme-long freeze, which would leave the business unable to evolve, without pretending that changes to the retiring platform are free. Every legacy-side change must declare whether it is temporary, how it will be represented in the rebuilt capability, and when the legacy part is retired.

Release review separates evolution work from rebuild work because they have different acceptance criteria, dependency order and rollback behaviour. The default is one functional unit per issue and one traceable change set per release unit.

Characterise behaviour before replacing it

PDR · Behaviour-Parity Testing Proposed
Epic ATS-RB · Testing·Programme

Before a TargetRecruit-dependent capability is replaced, its observable behaviour is captured as executable characterisation tests. Those tests describe inputs, outputs, side effects and important failure cases without treating the package's internal implementation as the specification.

The rebuilt capability must pass the agreed behaviour-parity baseline before the old path is retired. Where the target process deliberately changes, the test and its acceptance criterion change through an explicit business decision rather than by silently accepting a regression.

Characterisation uses synthetic or anonymised data and is complemented by capability-level user acceptance. Destructive package-behaviour probes are handled as separately controlled experiments in an appropriate sandbox.

Shared entry points switch one route at a time

PDR · Shared-Entry-Point Switching Proposed
Epic ATS-RB · Native Build·Programme

When a Marlex-owned object is reused but its existing automation is coupled to TargetRecruit, the existing entry point becomes a thin dispatcher. Per-object configuration selects exactly one path — legacy or native — so activation and rollback can happen by domain without deploying two competing triggers or running both implementations.

The router is deliberately narrow. It applies only to reused custom objects whose live handler depends on the retiring model. New native objects do not need it, and platform-native activation remains preferable for flows or schedules where Salesforce already provides a clean switch. A global emergency bypass remains separate from the route selector.

Each routed object needs legacy characterisation tests, native tests, a configuration-flip test, an exclusive-route guard, rollback rehearsal and logging that makes the active route visible. Once native writes have created divergent data, rollback follows the wider cutover decision rather than assuming a configuration flip alone is sufficient.
