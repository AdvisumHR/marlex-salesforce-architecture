Project MULEThe integration layer (MuleSoft)

The integration layer — cross-cutting foundations, then the per-system lanes consolidated into one track, built one lane at a time so no single integration blocks the others; systems that only need a secure direct link connect straight to Salesforce.

4
Epics
23
Deliverables

How it fits together

This project provides the integration layer for the systems that need orchestration — transforming, routing and combining data between Salesforce and external systems. MuleSoft is confirmed as the middleware (the analysis and the selection are done, made on a MuleSoft vendor demo rather than a Marlex-run proof of concept), and the architecture is API-led. Not every external system is routed through it: systems that only need a straightforward, secure link — for example reporting or monitoring tools connecting over a Connected App with secure authentication — connect directly to Salesforce. MuleSoft is the layer for the integrations that genuinely need orchestration, not a mandatory gateway for everything.

The organising principle is lanes: cross-cutting foundations first, then one lane per external system, so that a slow or blocked integration never holds up the rest. It opens with two foundational pieces — confirming the platform and licensing plus the cross-cutting groundwork (the API-led architecture, the canonical contract drafts, a reusable authentication pattern), and provisioning the middleware itself (the API gateway, the environments, Salesforce connectivity, and the re-authentication approach reusable per org).

The per-system lanes then run in priority order. The NET4 finance lane can start without waiting because it is the risk-heavy near-term flow, and anchoring it on the shared data model lets its contracts survive the recruitment cutover; it is reused by Axxon's NET4 lane. The job-board lane (InfoJobs) comes before portals because it exists today whereas the portals do not. The portals lane builds only the connection — the portal front-end itself is out of programme. LinkedIn is a special case: the rebuild loses the recruitment vendor's built-in LinkedIn connection, so Marlex must become a certified LinkedIn partner before the middleware can carry that traffic.

A cross-cutting lane holds the integration work not tied to one system: deciding what to do with the small carried-over integrations, retiring the temporary direct connections once the middleware is live, keeping the register of integration assets, and the process for onboarding a new region's integrations. It also produces the coverage map that reconciles every external system to a lane, proving nothing was missed.

The key relationship with the rebuild is the swappable-connection pattern: the rebuild ships simple direct connections by default, and a setting swaps in the MuleSoft version when each lane is ready, with no redeployment. That is what lets this whole layer run in parallel with the rebuild without ever holding up its go-live.

Epics, in order

MULE · Platform Confirmation & Foundations
6 deliverables

MuleSoft is selected, so this epic collapses to platform confirmation, licensing, and the cross-cutting foundations — the integration architecture rules, the API-led design, canonical contract drafts for NET4, InfoJobs and the portals, and a reusable per-org authentication pattern. The selection was made on a MuleSoft vendor demo rather than a Marlex-run proof of concept. It precedes all the per-system lanes.

Show 6 deliverables
  • Platform / Integration architecture foundations
    Lock the foundational rules for the integration layer before any platform work begins: the API-led architecture with middleware, the canonical contracts and how Salesforce integrates with the middleware, the portal scope and responsibilities, the swappable-adapter pattern that decouples the rebuild from the platform decision, and the regional middleware extensions. It also sets the naming convention for integration assets, the governance for changing a canonical contract, and how integration boundaries align with the ownership-boundary doctrine — an integration consumes a canonical contract rather than coupling to a specific Salesforce boundary. It is decision-and-document work, no code, and it unblocks the platform evaluation.
  • Platform / Integration requirements mapping & platform evaluation
    Map the integration requirements across all flows — protocols, volumes and authentication — and evaluate candidate middleware platforms against cost, the Marlex IT team's own skill set, and the feasibility of the Axxon-to-NET4 connection.
  • Platform / Platform proof of concept
    Not performed. The platform was selected on a MuleSoft vendor demo; no Marlex-side proof of concept was run and none is now planned — the selection is closed. Any live exercise of the API-led pattern and Salesforce-to-NET4 connectivity happens inside the NET4 lane build, not as a separate pre-decision proof of concept.
  • Platform / Platform decision & feasibility confirmation
    The final platform decision, capturing the selected middleware, confirmation that the Axxon connectivity is feasible, the cost model and the risk assessment.
  • Platform / Reusable per-org authentication pattern
    Extract the platform-agnostic part of the re-authentication procedure — Connected App configuration, a Named Credential template and certificate management — as a reusable per-org pattern, documented early so the Axxon foundation and its NET4 connectivity can consume it.
  • Platform / Canonical contract drafts
    Draft API contracts for the three foundational System APIs — NET4, InfoJobs and the portals — written to be independent of the platform decision, using the shared canonical entities. They are drafted so that the lane builds can start the day the middleware is provisioned.
MULE · Middleware Provisioning
3 deliverables

Provisions the middleware itself: the API gateway, the development, pre-production and production environments, the Salesforce connectivity layer, and a re-authentication strategy reusable per org. This is the infrastructure the lanes are built on.

Show 3 deliverables
  • Infra / Middleware foundation
    Deploy the middleware foundation: the API gateway, the development, pre-production and production environments, the authentication configuration, monitoring and alerting (dashboards, error-rate alerts, log aggregation), and the deployment pipeline.
  • Infra / Salesforce connectivity layer
    Build the connectivity layer between Salesforce and the middleware: the Named Credential holding the middleware URL and authentication, the Connected App for the middleware's access to Salesforce, and the platform-event channels.
  • Infra / Re-authentication strategy per org
    Document the reusable per-org re-authentication procedure — Named Credentials, Connected Apps, certificates and OAuth trust — so that Axxon and each expansion country can reuse it when they onboard.
MULE · Integration Lanes (per system)
9 deliverables

The per-system integration lanes, consolidated into one epic and built one at a time so no single integration blocks the others. NET4 (the risk-heavy near-term finance lane, reused by Axxon), InfoJobs (before portals, since it exists today), the portals pipe (front-end out of programme), LinkedIn (a certified-partner prerequisite the rebuild loses), and the Axxon-to-NET4 routing. Each lane ships a middleware System API and a Salesforce adapter that the swappable selector switches in when ready.

Show 9 deliverables
  • Lane / Axxon-to-NET4 middleware routing
    The middleware-side configuration that routes Axxon's traffic to the NET4 System API, with multi-tenant routing distinguishing Spain from Axxon traffic and reusing the regional onboarding process. It ships as a simplified Experience API at build — basic routing without full canonical-contract validation, which can be added later as the Spain NET4 process and experience APIs mature. This is the Axxon-NET4 transport pipe, reusing the Marlex NET4 lane, not the ERP build in the Axxon onboarding.
  • Lane / NET4 System API
    Build the NET4 System, Process and Experience APIs on the middleware, with multi-tenant routing that serves both Marlex Spain and Axxon. This is the pipe the finance flows run on, and the pre-condition for the Axxon NET4 lane if the middleware path is chosen there.
  • Lane / NET4 Salesforce adapter
    The Salesforce-side adapter that calls the NET4 System API through the middleware. It is added alongside the direct NET4 connection built during the rebuild — the runtime selector chooses between them, so this is additive rather than a rewrite of existing callouts.
  • Lane / InfoJobs System API
    Build the InfoJobs System API — a SOAP/XML adapter — and the Process API that handles posting offers and retrieving CVs on the middleware.
  • Lane / InfoJobs Salesforce adapter
    The Salesforce-side adapter that reaches InfoJobs through the middleware, added alongside the direct InfoJobs connection built during the rebuild.
  • Lane / Portal System API
    The Experience and Process APIs on the middleware that carry candidate and recruiter portal traffic. This delivers the integration pipe only — the portal front-end is out of the programme, and the portal replacement is a separate future initiative.
  • Lane / Portal Salesforce adapter
    The Salesforce-side adapter that reaches the portals through the middleware, added alongside the direct portal connection built during the rebuild. Pipe only — the portal front-end stays out of the programme.
  • Lane / LinkedIn partner certification & entitlement
    Become a certified LinkedIn Recruiter System Connect partner — a gated, non-trivial prerequisite that the recruitment vendor used to supply natively and the custom rebuild loses. It covers enrolment in the LinkedIn partner program, an approved app, and the connection entitlement.
  • Lane / LinkedIn transport adapter
    Once the LinkedIn Recruiter System Connect entitlement is in place, build the LinkedIn transport on the middleware — candidate sync, in-recruitment-system profiles, and status write-back over the certified channel. The middleware carries transport only after the partner certification, and the adapter is anchored on the shared canonical model.
MULE · Integration Registry
5 deliverables

The cross-cutting integration work not specific to one lane: deciding what to do with the small carried-over integrations, retiring the direct connections once the middleware is live, the integration asset registry, the regional onboarding process, and the regional-ERP variance pattern. It also produces the coverage map that reconciles every external system to a lane and a disposition, proving full inventory coverage.

Show 5 deliverables
  • Registry / Carry-over integration decisions
    Decide what happens to the carried-over integrations that are not full lanes — LinkedIn coverage in the current system, where the e-signature integration fits, and the consumers of the existing point integrations — resolving each flow individually.
  • Registry / Direct connections retired
    Once the middleware adapters are live in production and proven stable, retire the direct connections to NET4, InfoJobs and the portals that the rebuild shipped as the default. This is optional — the direct connections can remain as a configurable fallback indefinitely.
  • Registry / Integration asset registry
    A catalogue of the integration assets for the delivery teams. At go-live this is a versioned spreadsheet or wiki; evolving it into a searchable developer portal is planned afterwards and does not block the regional onboarding.
  • Registry / Regional integration onboarding process
    A step-by-step process for onboarding a new regional integration — define the canonical contract, get governance approval, build it in the middleware, and expose it through the gateway — reusable for Axxon and each expansion country.
  • Registry / Regional ERP variance pattern
    A reference pattern for plugging a different ERP into each region without changing Salesforce or breaking the canonical contract. It defines a new System API per regional ERP — absorbing that ERP's authentication, payload shape and idempotency quirks entirely at that layer — plus an extension to the canonical process flow that inspects the country already present in the payload and routes to the right System API without changing the contract, and a small routing registry that maps country to target System API so adding a region is a configuration change rather than a redeploy. It also sets the authentication, secret-rotation and monitoring guidelines per regional System API.
